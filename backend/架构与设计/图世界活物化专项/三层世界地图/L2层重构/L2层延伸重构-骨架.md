## 一、设计理念

> 来自架构方向文档 §一：
> "把玩家和 Agent 放入一个真正的游戏世界。抽象层隔开上层与底层，底层对所有上层实体透明，无非权限高低。"

```
┌─────────────────────────────────────────┐
│  上层：居民（Players / Agents）          │
│  GM / NPC / 队友 / 玩家                  │
│  只看到"我能做什么"，通过统一接口行动      │
├─────────────────────────────────────────┤
│  中层：World API（本文主角）             │
│  权限控制 / 动作验证 / 结果包装 / 审计    │
│  对上层暴露统一工具，对下层转发操作         │
├─────────────────────────────────────────┤
│  底层：World Engine                      │
│  SessionRuntime + WorldGraph + Behavior  │
│  + 导航 + 经济 + 时间 + 事件 + 战斗     │
│  机械真理源，零 AI，纯规则/状态/计算       │
└─────────────────────────────────────────┘
```

**L2 的核心交付物**：`WorldAPI` 类——L1 到 L3 的唯一通道。

**L1 不应该知道的**：SessionRuntime、WorldGraph、BehaviorEngine、StatOps……
**L1 应该知道的**：`api.heal(50)`、`api.activate_event("rescue")`、`api.recall(...)`

## 二、现状摸底

> 2026-02-23 增量复核：`app/world/` 根目录 L1 文件已迁至 `app/agentic/`，但生产与测试仍残留大量 `app.world.*` 旧导入（当前首要断裂点）。

### 2.1 L1→L3 穿透现状（核心问题）

`immersive_tools.py`（L1）通过 `AgenticContext.session: Any` 直接持有 SessionRuntime（L3）引用，16 处直穿调用：

| 操作域 | 直穿调用 | 命中 P5+P7 Helper |
|--------|---------|-------------------|
| 玩家数值 | heal, damage, add_xp, add_item, remove_item | StatOps（5 个） |
| 事件状态机 | activate_event, complete_event, fail_event, advance_stage, complete_event_objective | EventMachine（5 个） |
| 叙事操作 | advance_chapter, complete_objective, update_disposition | NarrativeOps（3 个） |
| 记忆系统 | recall, record_memory | MemoryOps（2 个） |
| 裸穿透 | `session.flash_results[k] = v` | 直接字典访问（1 个） |

**关键事实**：P5+P7 已把 SessionRuntime 内部拆成 4 个 helper。WorldAPI 只需在外面再包一层。

### 2.2 PipelineOrchestrator L3 耦合（1580 行，跨三层）

**静态 import（3 个 L3 runtime）**：
- `GameRuntime` — 获取 WorldInstance 注册表
- `SessionRuntime` — 创建/恢复/持久化会话
- `ContextAssembler` — 组装结构化上下文

**Lazy import（~20 个 L3 world + 3 个 L1 agentic）**：
- L3 world：scene(×8处), intent.resolver, intent.executor, npc.reactor, graph.models, player.ability_check, memory_graphizer
- L1 agentic：AgenticExecutor(×3处), AgenticContext, gm_extra_tools

**Pipeline 对 SessionRuntime 的操作分类**：

| 类别 | 操作 | 性质 |
|------|------|------|
| 会话生命周期 | 构造→restore()→persist() | 编排（可门面化） |
| 上下文组装 | ContextAssembler.assemble() + 属性读取 | 编排（已是门面） |
| 行为 Tick | run_behavior_tick("pre"/"post") | 直接操作（已被 SR 封装） |
| 状态变更 | game_state.metadata 字典写入, narrative.rounds_in_chapter, flash_results.clear() | **直接内部操作（违规）** |
| SceneBus | publish(×8处), get_round_summary(), clear() | 散布各处（可收拢） |
| 时间管理 | advance_time(10) | 直接操作（可门面化） |
| 历史记录 | history.record_round/npc_response/teammate_response | 编排（已是委托） |
| Intent 引擎 | IntentResolver.resolve() → IntentExecutor.dispatch() | 直接操作（可门面化） |

**关键发现**：Pipeline 对 SessionRuntime 的"直接内部操作"只有少数几处。大部分已通过方法调用或委托完成。Pipeline 暂不纳入 WorldAPI 范围——它是 L2 内部编排，不是 L1 消费者。

### 2.3 AdminCoordinator（1226 行，比较健康）

| 维度 | 评估 |
|------|------|
| 职责 | 入口协调器：依赖注入 + 委托到 Pipeline + 会话/队伍/战斗管理 |
| 状态操作 | **不直接修改 GameState**——全部通过 Service 委托 |

| 结论 | **已经是门面**，问题不大 |

### 2.4 FlashCPUService 层级错位

- 静态 import `LLMService`——实质是 L1 组件（LLM 调用），却放在 `admin/`
- 与 Pipeline 的 L1 耦合不同（Pipeline 是 lazy import），FlashCPU 是硬依赖
- 架构方向文档 §2.2 已将其归类为上层（Agent 层）

## 四、WorldAPI 设计

### 4.1 调用链路

```
L1 (immersive_tools)       L2 (WorldAPI)              L3 (SessionRuntime)
─────────────────────     ─────────────────           ──────────────────────
ctx.api.heal(50)      →   WorldAPI.heal(50)       →   session._stat_ops.heal(50)
ctx.api.recall(...)   →   WorldAPI.recall(...)    →   session._memory_ops.recall(...)
```

AgenticContext 改为持有 `api: WorldAPI`（替代 `session: Any`）。

### 4.2 操作面（当前 16 个，对齐 immersive_tools）

```python
class WorldAPI:
    """L2 统一接口 — L1 居民（Agent/玩家）能看到的全部操作。"""

    def __init__(self, session: SessionRuntime, role: str, agent_id: str):
        self._session = session  # 私有，L1 不可触碰
        self._role = role        # "gm" / "npc" / "teammate"
        self._agent_id = agent_id
        self._audit: list = []   # 操作审计日志

    # --- 玩家数值 ---
    def heal(self, amount: int) -> dict: ...
    def damage(self, amount: int) -> dict: ...
    def add_xp(self, amount: int) -> dict: ...
    def add_item(self, item_id, name, qty) -> dict: ...
    def remove_item(self, item_id, qty) -> dict: ...

    # --- 事件状态机 ---
    def activate_event(self, event_id) -> dict: ...
    def complete_event(self, event_id, outcome_key=None) -> dict: ...
    def fail_event(self, event_id, reason=None) -> dict: ...
    def advance_stage(self, event_id, stage_id) -> dict: ...
    def complete_event_objective(self, event_id, obj_id) -> dict: ...

    # --- 叙事 ---
    def advance_chapter(self, target, transition_type) -> dict: ...
    def complete_objective(self, objective_id) -> dict: ...
    def update_disposition(self, npc_id, deltas, reason) -> dict: ...

    # --- 记忆 ---
    async def recall(self, role, actor_id, seeds, ...) -> list: ...
    def record_memory(self, owner_id, type, ...) -> str: ...

    # --- Flash ---
    def set_flash_result(self, prompt, result) -> None: ...
```

### 4.3 WorldAPI 可做的花活

**角色权限控制**：
- GM 可以做所有操作
- NPC 只能 update_disposition（且只能改自己）、record_memory
- 队友只能有限操作
- RoleRegistry 已有工具级过滤（L1 看不到不该看的工具），WorldAPI 加操作级拦截（L1 就算调了也会被挡）——**双保险**

**参数校验**：
- LLM 传来的参数可能类型错误（字符串 "50" 而不是 int 50）
- 范围检查（治疗量 > 0，不超上限等）
- 在 L3 之前拦住坏数据

**操作审计**：
- 每个操作记录：谁、什么时候、做了什么、参数、结果
- 回合级事务追踪——这个回合内 GM 做了哪些操作
- debug 利器

**回合事务（探索方向）**：
- 一个 agentic turn 的操作打包
- 可审查"这回合发生了什么"
- 远期：可能支持回滚

### 4.4 与架构愿景的对齐

架构方向文档 §4.2 规划的 World API 更大：

```
World API（愿景）
├── 动作接口       move / talk / examine / use_item / rest
├── 交易接口       buy / sell / haggle
├── 查询接口       get_location / get_inventory / get_stats / get_shop_stock
├── 战斗接口       trigger_combat / combat_action / resolve_combat
├── 社交接口       update_disposition / start_dialogue / end_dialogue
└── 权限层         根据调用者身份过滤可用操作和可见信息
```

当前 16 个方法是这个愿景的**第一批落地**——覆盖 immersive_tools 的操作面。后续随着系统建设（经济、商店、升级等），WorldAPI 会按需扩展。

## 五、Pipeline 与 WorldAPI 的关系

Pipeline 不走 WorldAPI。原因：

1. **Pipeline 是 L2 内部编排**，不是 L1 消费者
2. Pipeline 需要的操作面和 L1 不同——它需要 restore/persist/tick/SceneBus 等 L1 不需要的能力
3. 强行让 Pipeline 走 WorldAPI 会把 WorldAPI 撑成另一个 god class

**边界**：

```
                    WorldAPI（L1 → L3 的门）
                   ╱
L1 (Agent/Tools) →
                   ╲
                    （AgenticExecutor 本身由 Pipeline 驱动，但工具通过 WorldAPI 操作世界）

Pipeline（L2 内部编排，直接操作 SessionRuntime）
  ├── restore / persist（生命周期）
  ├── run_behavior_tick（事件驱动）
  ├── advance_time（时间推进）
  └── SceneBus（回合消息总线）
```

Pipeline 的少数"直接内部操作"（metadata 写入、flash_results 清除）可以后续收进 SessionRuntime 的方法中，但这是 L3 内部优化，不是 L2 的事。

## 六、与 L3 重构的关系

L3 重构（P1-P7）做了什么：
- 文件归位（36 个文件 → 11 子目录）
- SessionRuntime 瘦身（2104 → 999 行，29 方法提取到 4 helper）

L2 重构需要利用的 L3 成果：
- P5+P7 的 4 个 helper（StatOps/EventMachine/NarrativeOps/MemoryOps）恰好定义了 WorldAPI 的操作面
- SessionRuntime 的薄委托层本身就是一个准门面——WorldAPI 只需再包一层

L2 重构不同于 L3 的地方：
- **L3 是搬文件，L2 是建边界**
- L3 的产出是"文件在正确的位置"，L2 的产出是"调用走正确的路径"
- L3 几乎零风险（薄委托透明转发），L2 需要改调用方（immersive_tools）

## 七、延伸扩展时再定的事项

> 以下事项已明确用法，具体落地推迟到 L1 延伸扩展阶段。

### 7.1 权限矩阵

**用法**：WorldAPI 构造时接收 `role`（gm/npc/teammate），每个方法入口检查权限。

**初版全放行**：第一批落地时所有角色可调所有方法（与当前 immersive_tools 行为一致）。

**收紧时机**：L1 扩展出多角色差异化行为时（例如 NPC 商人有专属交易工具、普通 NPC 只能社交）。

**预期矩阵草案**（待定，仅供参考）：

| 操作 | GM | NPC | 队友 | 说明 |
|------|:--:|:---:|:----:|------|
| heal / damage / add_xp | ✓ | ✗ | ✗ | 只有 GM 能改玩家数值 |
| add_item / remove_item | ✓ | ✗ | ✗ | 同上 |
| activate/complete/fail_event | ✓ | ✗ | ✗ | 事件控制权在 GM |
| advance_stage | ✓ | ✗ | ✗ | 同上 |
| complete_event_objective | ✓ | ✗ | ✗ | 同上 |
| advance_chapter | ✓ | ✗ | ✗ | 章节推进权在 GM |
| complete_objective | ✓ | ✗ | ✗ | 同上 |
| update_disposition | ✓ | ✓（仅自己） | ✗ | NPC 可改自己的好感度 |
| recall | ✓ | ✓ | ✓ | 所有角色可召回记忆 |
| record_memory | ✓ | ✓ | ✓ | 所有角色可写入记忆 |
| set_flash_result | ✓ | ✗ | ✗ | GM 专用 |

### 7.2 审计日志

**用法**：WorldAPI 内部维护 `_audit: list`，每个操作追加一条记录。回合结束后可提取用于 debug / 回放。

**日志格式草案**：

```python
{
    "op": "heal",               # 操作名
    "actor": "gm",              # 调用者 agent_id
    "role": "gm",               # 角色
    "args": {"amount": 50},     # 入参
    "result": {"hp": 80},       # 返回值摘要
    "ts": 1708700000.0,         # 时间戳
}
```

**落地时机**：WorldAPI 骨架建好后即可加，不依赖外部系统。

### 7.3 AgenticContext 改造

**用法**：`AgenticContext.session: Any` → `AgenticContext.api: WorldAPI`。

**改造步骤**（机械替换）：
1. WorldAPI 实例在 PipelineOrchestrator 构造 AgenticContext 时创建
2. `AgenticContext` dataclass 新增 `api: WorldAPI` 字段
3. `immersive_tools.py` 中所有 `ctx.session.xxx()` → `ctx.api.xxx()`
4. **不删除** `AgenticContext.session` 字段，先标记内部字段并仅保留给闭包/运行时透传使用

**风险**：极低。immersive_tools 的 16 个调用全部是方法调用，1:1 映射到 WorldAPI。

### 7.4 后续操作面扩展路线

**用法**：新系统建设时，在 WorldAPI 上追加对应方法。

**预期扩展批次**：

| 批次 | 触发条件 | 新增方法（预估） |
|------|---------|----------------|
| 第一批（当前） | immersive_tools 对齐 | 16 个 |
| 经济/商店 | 建设 ShopService 时 | buy / sell / get_shop_stock / haggle |
| 导航 | 需要 L1 级导航时 | move / enter_area / get_location |
| 战斗 | 战斗系统对接时 | trigger_combat / combat_action / resolve |
| 查询 | L1 需要世界状态查询时 | get_inventory / get_stats / get_party |

每批扩展时同步更新权限矩阵。
