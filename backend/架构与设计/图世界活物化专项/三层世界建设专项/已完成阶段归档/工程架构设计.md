## 一、参考架构：博德之门 3

BG3（Divinity Engine 4.0）的完整游戏系统可以分为 6 层：

```
┌─────────────────────────────────────────────────────────────┐
│ ❻ 表现层                                                     │
│   3D 渲染、UI（角色面板/背包/地图/日志/对话框/商店/骰子动画）   │
├─────────────────────────────────────────────────────────────┤
│ ❺ 叙事/脚本层                                                │
│   对话树（手工编写分支）、任务脚本（手工触发器）、               │
│   同伴剧情线（预设审批事件）、过场动画                          │
├─────────────────────────────────────────────────────────────┤
│ ❹ AI/行为层（非 LLM）                                        │
│   战斗 AI（敌人战术，规则驱动）、同伴战斗 AI、                  │
│   NPC 日程/行为树、同伴审批触发                                │
├─────────────────────────────────────────────────────────────┤
│ ❸ 游戏状态层                                                 │
│   角色状态（HP/条件/法术位）、世界标记/变量、队伍管理、          │
│   任务进度、好感度/关系系统、背包状态、时间/日夜循环、           │
│   地图探索（迷雾/已发现）                                      │
├─────────────────────────────────────────────────────────────┤
│ ❷ 规则引擎层（纯机械）                                       │
│   D&D 5e 规则集：d20 系统、战斗引擎（先攻/行动经济/回合）、    │
│   伤害计算（类型/抗性/易伤/暴击）、状态效果系统、               │
│   角色升级（XP/职业特性/ASI/专长）、装备系统（AC/槽位/熟练）、  │
│   背包经济（交易/定价/重量）、法术位管理、炼金                  │
├─────────────────────────────────────────────────────────────┤
│ ❶ 内容/数据层（静态，只读）                                   │
│   世界地图（区域/子地点/连接）、NPC 模板、怪物数据库、           │
│   物品数据库、法术/技能数据库、任务定义、对话树数据              │
└─────────────────────────────────────────────────────────────┘
```

**关键特征**：
- BG3 的 ❺叙事/脚本层 是**手工编写**的——对话树、任务触发器、剧情脚本全是人写的
- NPC 行为通过**行为树**定义，不是 AI 生成
- 288 个任务全部预先设计，不存在动态生成
- 同伴审批事件是预设的触发条件 + 预写的反应

## 二、当前实际架构

当前代码的实际分层（5 层 + 基础设施）：

```
┌─────────────────────────────────────────────────────────────┐
│  HTTP 入口 (routers/)                                        │
│  FastAPI game_v2_router + 5 子路由模块                        │
│  ⚠️ 有直连 runtime/world 的捷径（应走编排层）                  │
├─────────────────────────────────────────────────────────────┤
│  应用编排 (services/admin/)                                   │
│  AdminCoordinator（入口单例）→ PipelineOrchestrator            │
│  V4 三阶段管线：A 上下文组装 → B Agentic 会话 → C 后处理       │
│  + NpcInteractionCoordinator / CombatCoordinator              │
├─────────────────────────────────────────────────────────────┤
│  L1 AI 层 (agentic/)                                         │
│  AgenticExecutor（统一 Agent 执行器）                          │
│  immersive_tools（30 个工具 + RoleRegistry 按 role/traits）    │
│  GM 有 16 个状态变更工具、NPC 有角色特定工具（商人/治疗师等）   │
│  teammate/ 队友响应服务                                       │
├─────────────────────────────────────────────────────────────┤
│  L2 会话门面 (runtime/)                                       │
│  SessionRuntime（restore/persist/dirty tracking）             │
│  StatOps / MemoryOps / NarrativeOps / EventMachine            │
│  ContextAssembler / WorldInstance                             │
│  ⚠️ memory_ops 有反向依赖到 agentic                           │
├─────────────────────────────────────────────────────────────┤
│  L3 世界引擎 (world/)                                         │
│  12 个子系统包，~15,900 行，全部零 LLM 依赖                    │
│  player/ graph/ events/ combat/ npc/ memory/                  │
│  narrative/ intent/ scene/ time/ party/ item/                 │
│  ⚠️ npc/instance_manager 有 lazy import 到 agentic            │
├─────────────────────────────────────────────────────────────┤
│  基础设施                                                     │
│  LLM SDK / Firestore / MCP Client / 图片生成                  │
└─────────────────────────────────────────────────────────────┘
```

### 已知问题

- routers 有直连 runtime/world 的代码（绕过编排层）
- L2 memory_ops → agentic（反向依赖）
- L3 npc/instance_manager → agentic/memory_graphizer（lazy import）
- GM 持有 16 个状态变更工具（职责越界）
- IntentResolver 做 AI 该做的事（猜意图）

## 三、核心洞察：BG3 vs 我们

**唯一本质差异**：BG3 用手工脚本驱动叙事，我们用 AI Agent。

| BG3 | 我们 | 差异原因 |
|-----|------|---------|
| 对话树（预编写分支） | NPC Agent 实时生成 | AI 替代手工编写 |
| 任务脚本（手工触发器） | 编排层 LLM + 事件状态机 | AI 生成剧情方向 |
| 预设同伴审批事件 | 记忆图谱 + 共同经历 | 关系自然生长 |
| 固定 NPC 行为树 | NPC Agent 自主响应 | AI 替代行为树 |
| 旁白文本（预编写） | GM Agent 实时叙述 | AI 替代预写文本 |

**不变的部分**：规则引擎、游戏状态、内容数据、非 LLM 行为 AI——这些和 BG3 完全一样。

**架构结论**：我们的 L3 应该 = BG3 的 ❶❷❸❹ 层（内容数据 + 规则引擎 + 游戏状态 + 非 LLM 行为）。L1 替代 BG3 的 ❺ 叙事/脚本层。如果把 L1 砍掉，L3+L2 应该能用脚本驱动跑起来。

## 四、目标架构

### 4.1 分层总览

```
┌─────────────────────────────────────────────────────────────────┐
│  API 层 (routers/)                                               │

│  = 游戏主循环                                                     │
```

### 4.2 已确定的架构决策

#### D1. 两种输入通道

| 通道 | 形式 | 走向 |
|------|------|------|
| **按钮动作** | 前端发送结构化 action type + params | → 引擎 pre-tick 机械执行 → SceneBus → Agent 叙述 |
| **文字输入** | 玩家打字说话 | → SceneBus → NPC Agent 回应 → GM 观察 → 队友旁观 |

不需要 IntentResolver——前端发的就是明确的 action type，引擎直接执行。

对话中的能力检定以**选项按钮**呈现（`[说服 DC14] 让守卫通融`），点击后引擎掷骰。

#### D2. 四种角色的权限模型

| 角色 | 能做什么 | 不能做什么 |
|------|---------|-----------|
| **引擎** | 按钮动作的全部机械执行（HP/XP/金币/移动/时间/事件...） | 叙述 |
| **GM Agent** | 叙述环境、渲染氛围、生成选项 | **任何**世界状态变更（纯只读） |
| **NPC Agent** | 对话 + **角色权限内**操作（商人调价、治疗师治疗、任务发布...） | 超出角色权限的操作 |
| **队友 Agent** | 对话 + **队友权限内**操作（表达需求、评估局势...） | 超出队友权限的操作 |

核心原则：

> **GM 是叙述者，不是执行者。** GM 的叙述是对已发生事实的反应。
>
> **NPC/队友是 Agentic 的。** 他们在自己角色权限内有真正的行动能力，通过 RoleRegistry 按 (role, traits) 分配工具。
>
> **引擎是看不见的手。** 处理所有按钮动作的机械操作。

#### D3. SceneBus = 共享感知通道

SceneBus 不是单向的"引擎写→GM 读"，而是**一轮内所有角色的共享感知通道**：

```
┌─ SceneBus（一轮的生命周期）─────────────────────────────────┐
│                                                               │
│  [ENGINE]  玩家移动到酒馆（引擎 pre-tick 执行结果）            │
│  [PLAYER]  "有什么新消息吗？"（玩家文字输入）                  │
│  [NPC:tavern_keeper] "听说西边牧场出事了..."（NPC Agent 回应） │
│  [GM]      酒馆昏暗的灯光映照着众人忧虑的脸（GM 环境叙述）     │
│  [TEAMMATE:goblin_slayer] "...哥布林。"（队友旁观后发言）      │
│                                                               │
│  可见性：public / private                                      │
│  成员：permanent（队友）+ active（当前子地点 NPC）              │
│  关键机制：后发言的人能看到前面所有人说了什么（顺序感知）       │
└───────────────────────────────────────────────────────────────┘
```

#### D4. 管线结构——一条管线，两个入口

不是两条独立管线，而是共用 SceneBus 的统一流程：

```
按钮入口                           文字入口
    │                                  │
    ↓                                  ↓
引擎 pre-tick                     玩家发言写入 SceneBus
（机械执行 + 结果写入 SceneBus）        │
    │                                  ↓
    └──────────→ SceneBus ←────────────┘
                    │
                    ↓
            NPC Agent 读 SceneBus
            回应 + 角色权限内工具调用
            结果写入 SceneBus
                    │
                    ↓
            GM Agent 读 SceneBus
            叙述环境（大多数时候 [PASS]）
            结果写入 SceneBus
                    │
                    ↓
            队友依次读 SceneBus
            决定是否发言，后发言者看到先发言者
            结果写入 SceneBus
                    │
                    ↓
            Post-tick
            （事件再评估 + FEELING_MAP + 记忆提取 + 持久化）
```

#### D5. GM 不扮演 NPC

子地点里的 NPC 各自有 Agent，自己说话。GM 只描述环境和世界，不替任何人说话。

#### D6. 按钮动作列表与时间成本

| 按钮动作 | 引擎做什么 | 时间成本 |
|---------|-----------|---------|
| 移动到区域 | 扣时间格 + 遭遇检定 | 1-3 格 |
| 进入子地点 | 切换位置 | 0 |
| 离开子地点 | 切换位置 | 0 |
| 短休息 | 恢复 25% HP | 1 格 |
| 长休息 | 恢复全部 HP，跳到次日 05:00 | 剩余格 |
| 发起对话 | 动作计数 +1（每 6 次扣 1 格）| 0 或 1 |
| 使用物品 | 执行物品效果 | 0 |
| 交易（买/卖）| 金币 + 背包变动，动作计数 +1 | 0 或 1 |
| 搜索/调查 | 能力检定，动作计数 +1 | 0 或 1 |
| 装备/卸下 | 背包 ↔ 槽位 | 0 |
| 查看信息 | 纯读取 | 0 |

每个动作都依赖世界数据支撑（地图连接、NPC 日程、商店库存、区域危险度等）。

## 五、当前 → 目标的关键变化

| 变化点 | 当前 | 目标 | 影响范围 |

| GM 工具 | 16 个状态变更工具 | 零变更，纯只读 | immersive_tools 重构 |
