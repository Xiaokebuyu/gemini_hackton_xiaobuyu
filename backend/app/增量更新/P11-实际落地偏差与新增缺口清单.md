# P11 实际落地偏差与新增缺口清单

## 1. 目的

这份文档不是重复 `P11-NPC在场语义、队伍系统与长休表现分块计划.md` 的原始目标，
而是记录：

1. `P11` 执行后，哪些块已经完成
2. 哪些块只完成了一半
3. 执行过程中主动做了哪些取舍
4. 现在新增确认的一条设计缺口：**Agent 侧没有“加入队伍 / 离开队伍”工具**

后续如果继续推进，不应该再拿原始 `P11` 当实际状态，而应该以这份“偏差清单”作为现状基线。

---

## 2. 总体判断

`P11` 没有完整落地，但也不是停在原点。

当前更准确的状态是：

- `Block A`：功能上基本完成，结构上未完全收口
- `Block B`：大体完成，并且执行中改了行为策略
- `Block C`：后端主体完成
- `Block D`：前端完整队伍面板与招募入口已完成
- `Block E`：长休主目标已完成
- `Block F`：Agent 侧队伍工具与内容层招募资格已接通

### 3.2 Block B - NPC 日程与在场解释层

#### 已完成

- `NpcScheduleHook` 现在不再只是“回 town / 回 home”的粗粒度逻辑。
- 当前 schedule 已支持更细的 `(area, location)` 目标。

参考：

- [`app/game_core/orchestration/hooks/npc_schedule.py`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/game_core/orchestration/hooks/npc_schedule.py)

#### 主动取舍

- **舍弃了移动上限**  
  之前调查阶段的默认 provider 带 `_MOVE_LIMIT = 2`，执行后这层限制被拿掉了。
- 现在策略变成：
  - 到 period 切换时
  - 只要角色 `schedule` 有目标
  - 就全部收集到 `moves`

#### 为什么这是重要偏差

这不是小实现细节，而是世界表现策略变化：

- 好处：
  - 世界状态更一致
  - 角色更像按 schedule 真实移动
- 代价：
  - 场景里会在 period 切换后一次出现更多 NPC 位移
  - 如果前端没有解释层，玩家会更容易觉得“随机冒出了一批人”

#### 已补上

- `present_npcs` 已包含 `presence_source`
- 当前已经能区分：
  - 常驻 NPC
  - 日程移动 NPC
  - planner 投递 NPC
  - companion 跟随 NPC
  - 事件型出现

#### 结论

`Block B`：**部分完成，且执行中改成了“schedule-driven 全量移动”**

## 4. Block F 实际落地结果：Agent 侧队伍工具已接通

这是当前比 `P11` 更重要的一条新增问题。

### 4.1 现状

当前系统里：

- `CompanionManager` 仍然是唯一真相源：
  - `recruit`
  - `dismiss`
  - `force_leave`
- `join_party` / `leave_party` 已作为 NPC / teammate 工具接入对话系统
- `companion_recruited` / `companion_dismissed` 继续作为前后端同步事件

### 4.2 当前完成状态

1. 工具层  
- `JoinPartyTool`
- `LeavePartyTool`

2. Prompt 规则  
- NPC prompt 已明确：
  - 玩家明确邀请且角色同意时，调用 `join_party`
  - 不能只口头答应、不调工具
- 队友 prompt 已明确：
  - 玩家明确要求离队或角色主动离队时，调用 `leave_party`

3. 内容层

  - `priestess`

4. 前端

  - 候选列表只看 `present_npcs[].recruitable`
  - 不再维护前端硬编码名单

### 4.3 与设计文档的偏差

设计文档已经有：

- `CompanionManager`
- recruit / dismiss / force_leave
- 队友加入队伍后锁定为跟随玩家

参考：

- [`app/博德之门3架构设计规范/❺ NPC与队友运行时规范.md`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/博德之门3架构设计规范/❺ NPC与队友运行时规范.md)
- [`app/博德之门3架构设计规范/状态层设计规范（已读）.md`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/博德之门3架构设计规范/状态层设计规范（已读）.md)

但当前缺的是这一步桥接：

**对话 Agent 知道自己可以调用“加入队伍 / 离开队伍”工具，并在合适条件下真正调用它。**

### 4.4 为什么这条很重要

这会直接影响你现在最在意的体验：

- 邀请 NPC 入队时
  - 现在最多只能得到一段文本态度
  - 不能形成真正的队伍状态变化
- 同样地，NPC 或队友也不能在对话中主动执行离队
  - 只能靠关系 Hook 或显式管理入口

所以这不是“锦上添花”，而是：

**队伍系统没有真正进入对话语义层。**

### 4.5 建议新增为 P11-F

建议把这条单独立为：

`Block F - Agent 侧队伍工具接入`

范围：

1. 新增工具
   - `join_party` / `recruit_to_party`
   - `leave_party`

2. 作用角色
   - 至少 NPC 可用
   - 是否允许 teammate 主动 `leave_party`，按设计约束决定

3. 工具执行底层
   - 走 `CompanionManager.recruit/dismiss`
   - 不能绕开现有前置检查

4. Prompt 规则
   - 当玩家明确邀请入队时，NPC 可调用加入队伍工具
   - 当 NPC 明确拒绝、或主动离队时，可调用离队工具

5. 前端配套
   - 对 `companion_recruited/companion_dismissed` 继续沿用现有事件消费
   - 如果由对话触发，玩家就能看到“说完 -> 真入队”的闭环

### 4.6 当前实现和设计文档的精确差口

这条缺口不是“文档没写、实现也没做”的空白，而是：

1. 文档已经有队伍管理运行时  
   - `CompanionManager.recruit / dismiss / force_leave`
   - 队友加入后跟随玩家
   - HTTP 端点可直接招募/解散

2. 当前实现已经有管理壳和 HTTP 壳  
   - 后端有 [`app/game_core/orchestration/companion_manager.py`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/game_core/orchestration/companion_manager.py)
   - 路由有 [`app/routers/gameplay.py`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/routers/gameplay.py) 里的：
     - `POST .../companion/recruit`
     - `POST .../companion/dismiss`

3. 但叙事层工具集没有把这套能力暴露给 Agent  
   - NPC/队友工具定义仍停留在：
     - 说话、表情、记忆、好感、战术建议、请求行动
   - 不存在：
     - `join_party`
     - `leave_party`
     - `invite_player_to_recruit`
     - `accept_join_request`
     这类会真正改 PartySlice 的工具

这意味着当前实际状态是：

- 队伍管理能力存在
- 对话 Agent 能表达态度
- 但对话 Agent 不能把态度落成队伍状态变化

这和设计文档想要的“队友/NPC 既是叙事角色，也是会真实加入/离开队伍的运行时角色”之间，仍然隔着一层关键桥接。

### 4.7 Block F 的建议实现边界

为了不把这块做成新的脏口子，建议 `Block F` 一开始就按下面的边界实现：

1. 工具不直接改 `PartySlice`
   - 工具内部必须委托 `CompanionManager`
   - 不允许绕开现有：
     - `recruitable` tag
     - 关系阶段
     - approval
     - 队伍容量

2. 工具语义分两层
   - 执行型工具：
     - `join_party`
     - `leave_party`
   - 叙事型工具仍然保留：
     - `refuse`
     - `request_action`
     - `express_opinion`

3. 角色权限收紧
   - NPC：
     - 可 `join_party`
     - 可 `leave_party`
   - Teammate：
     - 至少可 `leave_party`
     - 是否允许主动 `join_party`，视是否把“队友=已在队内”语义固定

4. 触发规则收紧
   - 只有玩家明确邀请、或 Agent 明确作出入队/离队决定时，才调用工具
   - 不允许把普通寒暄自动升级成入队动作

5. 前端不新造协议
   - 继续吃：
     - `companion_recruited`
     - `companion_dismissed`
   - 也就是说，这块主要是后端叙事层与现有队伍管理层的桥接，不需要新发明前端事件名

### 4.8 为什么 Block F 应该排进高优先级

这块不是“等 UI 做完再说”的增强项，而是现在系统层级断开的地方：

1. 玩家已经可以在对话里自然提出“加入我们”
2. Agent 也已经能理解这类意图并口头回应
3. 但口头回应后不会形成真实状态变化

这会直接造成一种很差的体验：

- 叙事层说“我愿意加入你”
- 运行时层却没有任何入队结果

也就是：

**当前系统已经具备表达能力，但缺执行闭环。**

因此，`Block F` 的优先级不应该低于：

- `Block D` 的 recruit UI

因为如果 Agent 侧能直接完成入队，玩家甚至不一定需要先依赖单独的 recruit 面板。

## 5. 现在的真实状态总结

如果用一句话概括当前实际落地：

- `P11` 修掉了最明显的 presence bug
- 把后端队伍跟随和长休 quiet slot 处理推进了一大截
- 但前端队伍闭环、长休表现压缩、以及 Agent 侧队伍工具，仍然没有真正收口

所以后续不该再说“P11 已全部完成”，而应该说：

**P11 已完成一部分主干，剩余尾项应按以下顺序补：**

1. `Block D` 剩余：party 前端刷新恢复
2. `Block F` 新增：Agent 侧加入/离开队伍工具
3. `Block D` 补完：recruit UI（若仍需要显式管理入口）
4. `Block E` 剩余：长休前端压缩展示
