# P15 - 统一发言语义与输入主链设计

状态：已落地（首版）
日期：2026-03-08

实施记录：见 `P16-统一Utterance主链实施完成.md`、`P17-party静默兜底与private语义收口.md`

## 1. 背景

最近的实机问题暴露出一个更底层的设计漂移：

- 点“与 `xx` 对话”时，玩家发言会进入完整公开对话链，NPC 和队友都可能回应
- 不点“与 `xx` 对话”时，同一句自然语言会因为前端状态不同，被分流成完全不同的后端语义
- 结果是：`direct_say`、`public_say`、`party free chat`、`private chat`、`text command` 这些概念被混在一起，路由和 UI 状态反而成了事实真相源

这不是 SceneBus 本身失效，而是“玩家说一句话”没有被建模成统一领域动作。

本设计文档的目标是把这件事重新定义清楚：

1. 统一“玩家发言”的领域模型
2. 明确 `receive` 与 `respond` 是两层语义
3. 把“定向公开发言”和“普通公开发言”收口为同一主链，只用 `focus` 区分
4. 让路由成为传输层适配，而不是领域语义分叉点

## 2. 调研结论

### 2.1 当前实现不是一条发言链，而是四种不同语义

当前代码里，玩家在输入框输入文本后，实际会落到四种完全不同的行为：

| 当前行为 | 前端触发条件 | 当前后端入口 | 实际语义 |
|------|------|------|------|
| 定向 NPC 对话 | `activeNpcId != null` | `/interact/stream` | 公开对某个 NPC 说话 |
| 队友闲聊 | `!activeNpcId && hasParty` | `/interact/stream` + `party_chat` | 只对队友说话 |
| 私聊 | 显式私聊 UI | `/private_chat/stream` | 只对目标 NPC 说话 |
| 文本命令 | `!activeNpcId && !hasParty` | `/input/stream` | 命令别名解析，不是说话 |

对应证据：

- 前端输入分流见 `frontend/src/game/OptionPanel.tsx`
- 文本命令解析见 `app/game_core/adapters/inbound.py`
- NPC 交互入口见 `app/routers/gameplay.py`
- 队友闲聊执行见 `app/game_core/orchestration/npc_interaction.py`
- 私聊执行见 `app/game_core/orchestration/private_chat.py`

### 2.2 当前最不合理的点：输入语义被 UI 状态改写

当前 `OptionPanel.handleSend()` 的逻辑是：

1. 有 `activeNpcId` 就当作 NPC 对话
2. 否则只要 `hasParty` 就自动当作队友闲聊
3. 否则走 `/input/stream`

这意味着“我输入一句自然语言”这件事的语义，不取决于我想对谁说，而取决于：

- 当前有没有锁定 NPC
- 队伍里是否至少有一个成员

这是典型的实现偏移。UI 状态不应该决定领域动作的本质。

### 2.3 `free_chat` 当前把“收到消息”和“决定回应”混成了一层

`execute_free_chat()` 当前会先把玩家发言写入公开 SceneBus，然后只遍历队友，且每个队友先经过 `_should_teammate_respond()` 概率门。

问题不在“有概率沉默”，而在于：

- 没过门的队友会直接 `continue`
- 他们不会进入后续处理链
- 当前轮次的上下文窗口写入也只覆盖实际有响应的人

于是系统语义就从“听见了，但没开口”滑成了“这一轮几乎像没收到消息”。

这和设计文档强调的语义不一致。设计文档写的是：

- 先通过 SceneBus 接收公共上下文
- 再决定是否发言

而不是“没打算发言，就当成没收到”。

### 2.4 `direct_say` 和 `public_say` 在领域上不是两条主链

这次讨论里最重要的结论是：

- “公开说一句话”
- “当众对某个 NPC 说一句话”

本质上是同一个领域动作，只是第二种多了一个 `focus_target`。

二者的差异不该体现在：

- 是否走另一条路由
- 是否写入不同可见性的 SceneBus
- 是否换一套完全不同的编排器

二者真正应该不同的地方只有：

- 谁拥有第一响应权
- 后续对话选项锚定到谁

### 2.5 当前实现与既有设计文档的关系

这次调研后的判断是：

- `SceneBus` 作为共享临时语境的总体思想仍然正确
- `private_chat` 作为私有可见性分支也是合理的
- 真正漂移的是“自由输入的公开发言语义”与“队友闲聊的默认分流”

与设计文档的对照结论：

1. `编排层设计规范` 仍把 `/input/stream` 写成“自由文本，对话、自由描述行为”的总入口  
   但当前实现里的 `/input/stream` 已经退化成命令别名解析器
2. `叙事层设计规范` 与 `NPC/队友运行时规范` 强调 SceneBus 先提供共享上下文，再由队友决定是否发言  
   但当前 `free_chat` 的非响应者几乎没有真正进入“接收后沉默”的语义
3. `编排层设计规范` 已经把 `execute_free_chat()` 标成一条存在的实现偏差  
   说明文档本身也意识到当前路径并不是理想主模型

## 3. 设计目标

本次统一发言语义的设计目标如下：

1. 玩家所有“说一句话”的行为，先统一成一个领域动作
2. `public` 与 `public + focus_target` 共享一条主链
3. `private` 和 `party` 只作为作用域差异，不再伪装成完全不同的产品类型
4. `receive` 与 `respond` 分层
5. `/input/stream` 不再承担自然语言发言语义
6. 尽量保留现有 HTTP 路由，对外以适配层迁移，内部先统一

## 4. 统一领域模型

推荐把玩家发言统一建模为一个内部请求：

```json
{
  "text": "我们先谈谈那封信。",
  "scope": "public",
  "focus_target": {
    "kind": "npc",
    "id": "merchant_tom"
  },
  "check": {
    "skill": "persuasion",
    "dc": 14
  }
}
```

建议的内部类型：

```ts
type UtteranceScope = "public" | "private" | "party"

type UtteranceRequest = {
  text: string
  scope: UtteranceScope
  focus_target?: {
    kind: "npc"
    id: string
  }
  check?: {
    skill: string
    dc: number
  }
}
```

### 4.1 语义映射

| 语义 | 统一模型 |
|------|------|
| 普通公开发言 | `scope="public"` + 无 `focus_target` |
| 定向公开发言 | `scope="public"` + `focus_target=npc` |
| 私聊 | `scope="private"` + `focus_target=npc` |
| 队友频道 | `scope="party"` + 无 `focus_target` |
| 带检定的对话 | 在任意 utterance 上附加 `check` |

### 4.2 非法组合

以下组合建议直接禁止：

- `scope="private"` 且无 `focus_target`
- `scope="party"` 且有 `focus_target`
- `scope="public"` 且 `focus_target.kind != "npc"`

## 5. 核心语义定义

### 5.1 `scope` 决定 audience，不决定主链类型

`scope` 的职责应该只有一个：决定谁能接收到这句话。

建议定义：

- `public`
  - 玩家、同场景队友、同场景 NPC 都能接收
  - GM/系统可作为编排观察者读取
- `private`
  - 只有玩家和目标 NPC 接收
  - 仍写入 SceneBus，但 `visibility="private"`
- `party`
  - 只有当前队伍成员接收
  - 不对场景普通 NPC 公开

这意味着：

- `public` 与 `public + focus_target` 的 `audience` 相同
- `focus_target` 只影响“谁优先回应”，不影响“谁能听见”

### 5.2 `focus_target` 决定响应优先级，不决定可见性

`focus_target` 的职责应该是“对谁说”，不是“只让谁听见”。

建议语义：

- `scope="public"` 且有 `focus_target`
  - 所有人都能听见
  - `focus_target` 拥有第一响应权
  - 后续选项默认锚定到该目标
- `scope="public"` 且无 `focus_target`
  - 没有保底主回应者
  - 编排器可选择 0 或 1 个主要回应者，也可以 GM 先 PASS

### 5.3 `receive` 与 `respond` 必须拆开

这是本设计的硬约束。

#### `receive`

表示该角色是否进入本轮可见语境。

最低要求：

- 发言写入正确可见性的 SceneBus
- 合法 audience 中的角色都被视为“收到”
- 即使角色不发言，也应允许其在会话记忆 / 上下文摘要层感知这条 utterance

#### `respond`

表示该角色是否在本轮开口或出手。

决定因素可以包括：

- `response_tendency`
- 关系强度
- 场景标签
- `focus_target`
- 最近是否说过话
- 当前游戏模式约束

但 `respond = false` 绝不能等于 `receive = false`。

### 5.4 对话检定只是 utterance 的附加属性

带检定的对话不再被视为“另一种动作”，而是：

- 玩家说了一句话
- 这句话附带一个 `check`
- 规则层先结算 `check`
- 然后把结果交还给同一条 utterance 编排链

这和 P13 已经回正的方向保持一致。

## 6. 推荐主链设计

## 6.1 领域真相源：`UtteranceOrchestrator`

建议在内部建立一个统一的发言编排器：

```text
UtteranceOrchestrator.process(UtteranceRequest)
    1. 校验 scope / focus_target / check
    2. 计算 audience
    3. 写入 SceneBus
    4. 如有 check，先结算 check
    5. 选择 primary responder
    6. 执行响应编排
    7. 生成 dialogue_options / stream_end
```

这条链才是“玩家说一句话”的真相源。

### 6.2 响应编排建议

#### A. `scope="public"` + `focus_target=npc`

推荐顺序：

1. 玩家 utterance 写入公开 SceneBus
2. 如有 `check`，先结算检定并把结果写入 SceneBus
3. 焦点 NPC 优先响应
4. GM 观察是否需要补叙述
5. 队友决定是否插话
6. 其他在场 NPC 是否插话，初期可默认关闭或限制为最多 1 人
7. 生成锚定该 NPC 的后续选项

#### B. `scope="public"` + 无 `focus_target`

推荐顺序：

1. 玩家 utterance 写入公开 SceneBus
2. 可选：GM 判定是否存在最相关主回应者
3. 若有主回应者，则先由其响应；若无，则 GM 可 PASS
4. 队友决定是否插话
5. 其他在场 NPC 是否插话，初期建议保守实现
6. 若无人回应，则回落到 GM narration / comment 或空过

#### C. `scope="private"` + `focus_target=npc`

推荐顺序：

1. 玩家 utterance 写入私有 SceneBus
2. 如有 `check`，先结算并保持私有可见性
3. 目标 NPC 响应
4. 跳过 GM / 队友 / 普通 NPC
5. 生成锚定该 NPC 的私聊选项

#### D. `scope="party"`

推荐顺序：

1. 玩家 utterance 写入 party 可见语境
2. 只允许队友成为响应候选
3. 不拉入普通在场 NPC
4. 不默认生成 NPC 导向的选项

### 6.3 对 `party` 的设计立场

`party` 应该保留，但只能是显式模式，不该再由“队伍里有人”自动替代普通公开发言。

推荐原因：

- 它确实是合理语义：只对队友说话
- 但它不是输入框的默认语义
- 否则玩家只要带着队友，就永远失去“在公共场景里说一句话”的能力

## 7. 路由与 API 映射建议

本设计不要求立刻新增公开 API，但要求先统一内部语义。

### 7.1 推荐映射

| 路由 | 角色 |
|------|------|
| `/action/stream` | 机械动作主链，不处理 utterance |
| `/input/stream` | 文本命令 / 别名解析，不处理 utterance |
| `/interact/stream` | 过渡期保留，对外适配到 `UtteranceOrchestrator` |
| `/private_chat/stream` | 过渡期保留，对外适配到 `UtteranceOrchestrator(scope=private)` |

换句话说：

- 未来的领域真相源不是 `/interact/stream`
- 而是内部的 `UtteranceOrchestrator`
- 现有路由只是 adapter

### 7.2 是否需要新增 `/utterance/stream`

当前不强制。

建议分两步看：

1. 先统一内部模型和前端分流
2. 若后续发现 `/interact/stream` 命名持续误导，再考虑新增 `/utterance/stream` 并把旧路由保留为兼容别名

这样可以避免先做一次纯命名迁移，再做一次真正语义迁移。

## 8. 前端交互建议

### 8.1 默认输入框语义

默认输入框不应再根据 `hasParty` 自动变成队友频道。

推荐规则：

1. 若当前处于显式私聊模式
   - 发送 `scope="private"` + `focus_target=npc`
2. 否则若当前有显式焦点 NPC
   - 发送 `scope="public"` + `focus_target=npc`
3. 否则
   - 发送 `scope="public"` + 无 `focus_target`

### 8.2 `party` 应改为显式切换

如果保留队伍闲聊，建议只通过以下方式进入：

- 明确的“只对队友说”按钮
- 输入框频道切换器
- 或者对话选项里显式出现“和队友商量一下”

不再允许：

- 仅因为 `hasParty == true` 就自动改写输入语义

### 8.3 私聊模式不应只靠 `activeNpcId`

当前前端状态里，`gameMode="private_chat"` 和 `activeNpcId` 是两个不同维度。

建议后续实现时把“当前 utterance scope”也显式纳入分流判断，否则会再次发生：

- 视觉上已经处于私聊模式
- 但文本发送仍误走普通公开对话链

## 9. 与既有设计文档的统一建议

这次设计落地后，建议同步修正以下文档：

1. `编排层设计规范`
   - 不再把 `/input/stream` 继续描述为当前对话主入口
   - 明确 utterance 主链与 action 主链分离
2. `叙事层设计规范`
   - 把“玩家发言”统一成 utterance 概念
   - 把“对 NPC 说话”和“公开发言”改为 `focus_target` 差异
3. `游戏初始化流程`
   - 修正输入框默认语义
   - 区分“自然语言说话”和“文本命令”
4. `NPC与队友运行时规范`
   - 明确 `receive != respond`
   - 队友 silent 仍属于已接收场景上下文

## 10. 分阶段落地建议

### Phase A：语义收口

- 引入 `UtteranceRequest`
- 引入内部 `UtteranceOrchestrator`
- 把 checked dialogue 继续保持为 utterance + check

### Phase B：前端分流回正

- 去掉 `hasParty -> chat` 的隐式分流
- 把默认输入改为 `public`
- 新增显式 `party` 入口

### Phase C：接收与回应分层

- audience 内角色统一视为已接收
- silent recipient 也要获得最小上下文同步
- 概率门只决定是否回应，不决定是否收到

### Phase D：次级路径清理

- `execute_free_chat()` 改名或下沉为 `party` 特化分支
- 私聊前端状态机单独修正
- 统一文档中的旧入口和旧术语

## 11. 本文的核心结论

一句话总结：

`direct_say` 和 `public_say` 不应该是两条主链，它们是同一个 `utterance` 动作的两种形态；真正需要区分的是 `scope` 和 `focus_target`，而不是“当前有没有锁定 NPC”或“队伍里有没有人”。

本设计因此给出三个硬结论：

1. 玩家发言统一建模为 `UtteranceRequest`
2. `focus_target` 影响响应优先级，不影响公开可见性
3. `respond` 与 `receive` 必须拆开，不能继续混成一层
