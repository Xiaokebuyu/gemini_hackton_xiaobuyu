## 二、核心架构亮点

### 亮点 1：六边形内核 + 可注入的 LLM 降级设计

`game_core/` 的 159 个 Python 模块不 import 任何应用层代码。LLM、数据库、SSE 输出全部通过 Port Protocol（`LlmPort`、`PersistencePort`、`PresentationPort`）在外部注入。

**工程决策背后的思考**：这让整个游戏逻辑层可以在无 API Key 的 CI 环境中跑完 1291+ 测试，不需要 mock LLM；同时所有 LLM 点都有确定性 fallback，生产环境 API 超时不影响游戏运行。这不是"架构洁癖"，而是直接解决了"LLM 不稳定如何保证游戏可玩性"的实际问题。

### 亮点 2：StateDelta 原子状态机 + 完整审计链路

游戏的全部可变状态分布在 10 个 `StateSlice` 中（玩家/时间/区域/任务/关系/旗帜/事件/队伍/场景/叙事规划）。所有变更不直接修改 slice，而是描述为 `StateDelta`（`StateChange` 列表），通过 `StateContainer.apply()` 这唯一路径原子写入。

**这意味着**：任意时刻可以打快照回放，任意 Handler 的副作用完全可追溯，Settlement Hook 链里的 27 个 hook 可以安全并发读状态而不用担心竞态。

```python
# 每个 Handler 的输出都是纯数据描述
delta = StateDelta(changes=[
    StateChange("player", "set", "hp", 45),
    StateChange("relations", "add", "npc_dispositions.goblin_chef.approval", -10),
], reason="combat_attack")
state.apply(delta)  # 唯一写入点
```

### 亮点 3：三角色 LLM Agent + traits 驱动工具路由

GM、NPC、Teammate 三个角色各有独立工具集（`gm_tools.py` / `character_tools.py`），通过 `RoleToolRegistry` 按角色 + NPC `applicable_traits` 过滤：

- `OfferQuestTool.applicable_traits = ["receptionist"]` — 只有接待员 NPC 能发布任务
- `OfferTradeTool.applicable_traits = ["merchant"]` — 只有商人 NPC 能触发交易
- `update_feeling` 限 NPC，`express_opinion` 限 Teammate

同时 `InstanceManager`（LRU，max 200）为每个 NPC 维护独立的 `ContextWindow`（FIFO，32K token 上限）和 `directive_queue`（规划层指令队列），确保每个 NPC 的对话连续性和记忆跨 session 持久。

### 亮点 4：NetworkX 知识图谱 + BFS 扩散激活记忆

世界知识图谱分两层：

- **全局静态图**：从内容层 seed（角色→区域/角色→派系/物品→商店等11种边），启动时一次性构建
- **per-actor 私有图**：NPC 每次对话结束，LLM 从对话历史中提取三元组 `[subject, relation, object, weight]`，写入该 NPC 的私有图（5种动态边：KNOWS_ABOUT/INTERACTED_WITH/MADE_PROMISE 等）

查询时两图合并，BFS 扩散激活（每层 decay=0.8），返回 top-K 相关记忆注入 NPC system prompt。**效果**：NPC 真的"记得"之前的对话和玩家的行为，而不是靠无限堆 context。

### 亮点 5：Settlement Hook 链 + 涌现叙事

20+ 个 Hook 按优先级 P20→P80 链式执行，每个 hook 通过 `SettlementContext.execute_command()` 调用 RulesEngine 产生状态变更。新功能 = 在合适优先级插入一个 hook，核心循环零修改。

几个有意思的 hook：
- **RelationshipHook（P65）**：双维度（approval + trust）驱动6阶段关系跃迁，负向路径（cold→hostile→enemy）自动触发 `force_leave_companion`，派对成员真的会因为积累的负面关系离队
- **CampfireHook（P63）**：长休时对共同经历评分（今日重大战斗+100，今日任意+50，critical moment+30），选最高分记忆生成篝火对话，+5 好感，模拟真实的队友情感积累
- **PassivePerceptionHook（P45）**：位置变化时自动计算 `10 + WIS修正` 被动感知，对比 `visibility_dc`，自动揭示隐藏交互物/陷阱/发现，不需要玩家主动触发

## 四、面试问答框架

### "你们的 AI Agent 怎么工作的？"

```
三角色各自独立：
- NPC：build_npc_full_context() 一次调用组装 L0-L7 上下文（L6 记忆召回），
  AgenticExecutor 最多 5 轮 LLM 循环，按 applicable_traits 过滤工具，
  protocol 约束（max 1 speak，max 1 emote），有可见输出即停止
- GM：Settlement 阶段调用，读 change_log 摘要 → 模板或 LLM 生成叙事，
  维护 ContextWindow 跨 tick 连续性
- Teammate：观察 NPC 对话场景条目，概率性响应，共同经历写入 event_log

所有角色都有确定性 fallback，LLM 崩了游戏继续跑。
```

### "六边形架构的好处体现在哪？"

```
最直接的好处：1291 个测试在没有 API Key、没有数据库的 CI 环境里全部通过。
game_core 内只用标准库，外部能力通过 Protocol 注入：
- 想换 LLM 供应商 → 只换 LlmPort 实现
- 想换数据库 → 只换 PersistencePort 实现
- 想测试 Hook 行为 → 直接传 ThrowingLlmProvider，不需要 mock

副作用：每层职责强迫你想清楚边界，State 只管数据，Rules 只管计算，
Orchestration 只管时序，Narrative 只管 LLM，代码不会堆成泥球。
```

### "StateDelta 为什么不直接改 State？"

```
三个实际收益：
1. 可审计：每个 StateDelta 带 reason 字段，知道是哪个 Handler 改了什么
2. Settlement Hook 安全并发读：27 个 hook 在结算阶段读 state，
   写入都在 execute_command() 串行完成，无竞态
3. 可快照回放：StateContainer.snapshot() 是纯数据，
   可以在 dry_run 模式下走完整管线不产生副作用（用于验证前置条件）

这不是过度设计，而是 1291 个测试里每个 handler 测试都能独立跑的根本原因。
```

### "知识图谱和 Context Window 怎么结合的？"

```
分两个维度：
1. Context Window（工作记忆）：每个 NPC 实例维护 32K token FIFO 缓冲，
   存最近的对话历史，直接拼到 LLM history
2. 知识图谱（长期记忆）：溢出时触发 write_episode()，LLM 从对话提取三元组
   写入 per-actor 私有图；每次对话前 BFS 扩散激活查 top-5 相关记忆，
   注入 system_prompt 的 "## Relevant world knowledge" 节

效果：NPC 短期靠 context，长期靠图谱，两者互补，不会无限堆 token。
```

### "SSE 流式是怎么做到低延迟的？"

```
两条路径分开处理：
1. 状态变更事件（离散）：tick 结束后 SSEPresentationPort.drain()，
   一次性 flush 所有积累的事件

2. 叙事文本（连续流）：最终轮 GM 叙事通过 text_chunk_sink 回调直接透传，
   不缓存，浏览器看到字一个一个出来

后端模式：background task 生成事件 → asyncio.Queue → foreground generator drain → SSE response
per-session asyncio.Lock 防止两个请求并发改同一 session 的 state。
```
