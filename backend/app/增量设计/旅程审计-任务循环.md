### Step 2: Planner 布置 Clue（核心问题区）

**代码路径**：`world_builder.py:120 _apply_plant_environmental()` → Path A `_translate_environmental_clue_payload()` (line 214)

**现状 — Path A 翻译逻辑（line 214-301）**：

当 LLM 的 plant_environmental payload 中有 `clue_id` + `location_id` 可解析时，翻译为 fill_location。构造的 clue interactable 结构：

```python
functional = {
    "type": "investigate_clue",
    "params": {
        "clue_id": clue_id,
        "options": options,      # 2-4 个选项，LLM 未提供时默认 ["仔细检查", "听听队友判断"]
        "outcomes": outcomes,    # 按 option_id 索引的三分支效果，LLM 未提供时默认空 {}
        "hide_on_resolve": True,
        ...
    }
}
```

**问题**：
1. **LLM 生成不出有效 outcomes**：outcomes 需要 `{option_id: {always: [...], on_pass: [...], on_fail: [...]}}` — LLM 很少能正确生成这个嵌套结构
2. **默认 options/outcomes 为空**：当 LLM 不提供时，`_translate_environmental_clue_payload` 给的默认 options 是 `["仔细检查", "听听队友判断"]`，但 outcomes 是空 `{}` — 意味着选任何选项什么效果都不会发生
3. **on_first_inspect 无默认**：LLM 通常不会提供 `on_first_inspect` 效果列表，调查后没有即时反馈

**验证校验层（clue_investigation.py:83-140）**：
- `validate_clue_definition()` 要求：options 2-4 个、每个有 id+label、outcomes 必须有每个 option_id 对应的 bundle
- 这个校验在 `directive_contracts.py:520-533` 的 fill_location 合约中被调用
- **校验失败 → 整个 clue interactable 被 strip 掉** → LLM 辛苦生成的线索直接消失

**这是 Clue 系统最大的断裂点。**

**设计文档目标（简化后）**：
```
clue = {
    "clue_id": "xxx",
    "base_effects": [set_flag / grant_item / advance_quest / ...],  # 必定触发
    "check": {"skill": "investigation", "dc": 12},                 # 可选
    "check_effects": [额外收益],                                    # check 成功时
    "narrative": "调查发现的叙事信息",                                # 注入上下文
}
```

**调整清单（Clue 简化）**：

#### 2a: Schema 层（clue_investigation.py）
- 新增 `base_effects` 字段（替代 `on_first_inspect` 的功能，但改为调查时必定触发）
- 新增 `check` 字段（单个可选 skill check，替代 per-option check）
- 新增 `check_effects` 字段（check 成功的额外效果）
- 新增 `narrative` 字段（调查后注入上下文的叙事文本）
- `normalize_clue_definition()` 适配新 schema
- `validate_clue_definition()` 放宽：不再要求 2-4 options + outcomes 结构
- **保留旧 schema 兼容**：如果 clue 有 options/outcomes 就走旧流程，没有就走新简化流程

#### 2b: Handler 层（clue.py）
- `_compute_investigate()` 改为：
  1. 应用 `base_effects`（必定触发）
  2. 如果有 `check` → 骰点 → 成功则应用 `check_effects`
  3. 如果有 `narrative` → 写入 area_events / scene_bus（供 NPC/GM 读取）
  4. 直接标记 `resolved_option_id`（不再需要二阶段 resolve）
  5. **不再返回 options 列表给前端** — 调查即完成
- `_compute_resolve()` 保留用于旧 schema 兼容
- 新增 `_compute_investigate_simple()` 处理新 schema

#### 2c: WorldBuilder 翻译层（world_builder.py）
- `_translate_environmental_clue_payload()` 构造新 schema 的 clue interactable
- LLM payload 中的 `base_effects` / `check` / `narrative` 直接透传
- 不再需要构造 options/outcomes 复杂结构

#### 2d: 合约校验层（directive_contracts.py）
- `fill_location` 中对 clue interactable 的校验放宽
- `validate_clue_definition()` 已在 2a 中适配

#### 2e: 任务条件联动
- `clue_investigated` condition 检查方式不变（看 `resolved_option_id` 是否有值）
- 新流程在 `_compute_investigate` 中就设置 `resolved_option_id`，所以条件自然满足
- **无需改动 QuestObjectiveTrackingHook 和 EventEngine**

## Clue 简化的向后兼容策略

**关键决策**：新 schema（base_effects + check + narrative）和旧 schema（options + outcomes）共存。

```python
def _is_simple_clue(clue: dict) -> bool:
    """检测是否为新简化 schema 的 clue"""
    return "base_effects" in clue and "options" not in clue

# ClueHandler._compute_investigate:
if _is_simple_clue(clue):
    return self._compute_investigate_simple(cmd, state, world, entry, clue, clue_state)
else:
    # 保留旧流程
    return self._compute_investigate_legacy(cmd, state, world, entry, clue, clue_state)
```

这样：
- 现有测试中的旧 schema clue 继续工作
- 新的 Planner 输出使用简化 schema
- 不需要迁移任何存量数据
