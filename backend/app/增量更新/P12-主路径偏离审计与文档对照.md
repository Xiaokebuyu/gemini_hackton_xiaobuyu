# P12 主路径偏离审计与文档对照

## 1. 目的

在 `Companion` 招募/离队链路迁回 `Command` 主路径之后，需要重新审计：

1. 当前后端还有哪些功能偏离了“`Command -> RulesEngine -> StateDelta`”主路径
2. 这些偏离是：
   - 真实实现问题
   - 设计文档内部冲突
   - 还是已被子系统文档明确允许的内部写入
3. 后续修正应该按什么顺序推进

这份文档不是直接给出所有修复方案，而是先建立一个**当前基线**，避免后续继续在“总设计 / 子系统设计 / 实际代码”三者之间来回漂移。

### 2.3 本文计为“偏离”的情况

满足任一条即计为偏离：

1. 设计文档明确要求经 `Command` / `RulesEngine` / 既有服务，但实现直接写状态
2. 设计文档要求复用既有运行时服务，但实现另起一条旁路
3. 直接写状态不在受控例外总表中，且跨越了子系统边界
4. 文档内部互相冲突，已经无法作为可靠边界说明

## 3. 已确认高优先级偏离

| ID | 严重度 | 功能 | 设计预期 | 当前实现 | 影响 |
|---|---|---|---|---|---|
| D1 | 高 | `NarrativePlanner.escalate` | 产生 `set_flag / modify_danger / modify_reputation` 命令并交给 ❷ | 只修改 `NarrativePlanSlice.escalation_level` | 世界态势没有被真正升级，后续 Hook 看不到设计预期的变化 |
| D2 | 高 | 动态任务 objective 完成 | `on_trigger` 应执行真实 command | 发出内部伪 command `complete_objective`，再直接手改 `QuestSlice.dynamic_quests` | 绕过校验、dry-run、delta 审计 |
| D3 | 高 | 敌对子地点状态切换 | 走主路径，至少通过统一 command/settlement 处理 | 路由内直接 `upsert_hostile()` 并保存 session | 绕过 `TickCoordinator`、`change_log`、Hook 链 |
| D4 | 中 | `spawn_quest_npc` | 复用 `PasserbyService.spawn()` | 直接写 `temporary_npcs + move_npc` | 临时 NPC 生命周期与 passerby 体系分叉 |
| D5 | 中 | 主路径/例外边界文档 | 总表应能说明所有合法绕行 | 受控例外表明显落后于实现，且 NPC 文档内部自相矛盾 | 以后继续出现边界型 bug 的概率很高 |

### 3.1 D1 - `NarrativePlanner.escalate` 没有落到世界状态

设计预期：

- [`叙事规划子系统设计规范（粗读）.md#L524`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/博德之门3架构设计规范/叙事规划子系统设计规范（粗读）.md#L524)

文档明确写的是：

- `escalate` 产生命令列表
- 命令交给 `❷ RulesEngine.batch_execute()`
- 可用命令是 `set_flag / modify_danger / modify_reputation`

当前实现：

- [`narrative_planner.py#L1028`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/game_core/orchestration/hooks/narrative_planner.py#L1028)

- `context.state.narrative_plan.adjust_escalation(delta)`

没有：

- `Command`
- `RulesEngine`
- `modify_danger`
- `set_flag`

结论：

- 这不是“实现细节不同”，而是**行为语义已经变了**
- 当前 `escalate` 更像“Planner 内部计数器”，不是“升级世界态势”

### 5.4 SceneBus / 被动回音专项审计（2026-03-08）

结合实机现象“未点击 `与xx对话` 时几乎收不到 NPC/队友回音”，本轮补扫确认：

1. `Stage B` 主链路本身是接通的
   - `GameRuntime.create_session()/resume_session()` 会安装 `run_post_action_round`
   - `PipelineOrchestrator._run_stage_b()` 会把 `npc_response / teammate_response` 回传给 `/action/stream`
   - 因此问题**不在 SSE 路由丢事件**

2. 真正的第一处实现偏差在“附近 NPC 收集逻辑”
   - `location_overview` 与交互校验使用的是 `presence.get_area_npcs()`，支持 `CharacterRegistry -> current_area/current_location` fallback
   - 但 `AgentOrchestrationService._collect_nearby_npcs()` 旧实现只看 `AreaSlice.npc_locations`
   - 结果会出现：
     - 画面里能看到 NPC
     - 明确点击“与其对话”也能成功
     - 但被动反应阶段认为“附近没人”
   - 这已在 [`agent_orchestration.py`](/home/xiaokebuyu/workplace/gemini-hackton/backend/app/agent_orchestration.py) 修正为复用 `presence.get_area_npcs() + is_colocated()`

3. 第二处实现偏差在“发言概率修正看不到 ENGINE 语义标签”
   - `TickCoordinator._emit_action_tags_for_record()` 把 `COMBAT_END / CRISIS / TRIVIAL` 等标签写入 `SceneBus visibility="system"`
   - 但 `run_post_action_round()` 旧实现把 `shared.scene_bus.get_for_role("gm")` 传给 `_should_character_respond()` / `_should_teammate_respond()`
   - `gm` 视图会过滤掉 `system`
   - 结果这些标签虽然存在，却不会参与 NPC/队友的发言概率修正
   - 当前已改为“内部决策视图读取 `public + system`，但仍不把 `system` 条目暴露给 Agent L5 上下文”

4. 第三处是一个次级实现 bug
   - `_should_character_respond()` 旧实现用 `source == char_id` 统计最近发言次数
   - 实际被动反应写入源是 `NPC:{npc_id}`
   - 导致 NPC 的“最近说太多要降频”抑制始终失效
   - 当前已修为识别 `NPC:{id}` 前缀

5. 修正后的当前结论
   - `SceneBus` 本身不是坏的，主问题在于**Stage B 决策侧使用了与 UI/交互不同的 presence 口径**
   - 同时又**拿不到内部语义标签**
   - 这两点叠加后，实际体感就会接近“除非显式点对话，否则周围人像没活着”

6. 仍然存在的剩余风险
   - 被动反应仍是概率型，不会保证每步都有回应
   - NPC 被动 prompt 仍允许 `do nothing`
   - passive 模式下，LLM 若返回空 tool call，会被执行器折叠成 `pass_turn`
   - 所以这次修正解决的是“本来应该有机会响应却根本没进入正确判定面”的问题，不是把系统改成“永远有人插话”

### 5.5 对话检定主链 / 结果语义专项审计（2026-03-08）

结合实机现象“GM 给出的四个选项里，带检定的对话点击后经常看不到角色回复”，本轮确认这不是单一 UI 漏渲染，而是两层实现漂移叠加：

1. `NPC 定向的检定对话` 被错误路由到了 `/action/stream`
   - `dialogue_options.dispatch` 旧实现会把 checked NPC 选项序列化成 `kind="action"` + `action_type="skill_check"`
   - 前端收到后直接调用 `sendAction()`，不会先把玩家原话写入对话流
   - 结果 NPC 只会在 Stage B 被动反应里看到“玩家做了一个 skill_check”，而不是“玩家刚对你说了这句话”

2. `success` 同时承担了两种语义
   - 规则层里，很多 outcome 型 handler 用 `metadata.passed / winner / metadata.success` 表达领域结果
   - 但 `ExecuteResult.success -> PipelineResult.success -> action_result.success` 又一直被当作“命令执行是否成功”
   - 对 failed check 来说，这会退化成：
     - 命令执行成功（`success=True`）
     - 但领域结果失败（`passed=False`）
   - 后续 GM/NPC/前端如果只读 `success`，就会误判

3. 设计预期与当前修正后的落点
   - 设计上，两条主链并不重复：
     - `/action/stream` = 通用结构化机械动作
     - `/interact/stream` = NPC 定向对话/交互
   - 因此 **带检定的 NPC 对话选项** 应保留对话语义，走 `interact` 主链，在其中执行 `skill_check`
   - 本轮已回正为：
     - GM checked NPC 选项 → `dispatch.kind="interact"`
     - payload 保留 `message + check_skill + check_dc`
     - `/interact/stream` 先掷骰，再把 `player_message + check_result` 送入完整 NPC 对话链

4. 结果契约的回正策略
   - 采用“**双字段过渡**”而非硬切：
     - `success` 继续保留一版，含义固定为 `executed`
     - 新增显式 `executed`
     - 新增标准化 `outcome`
   - `outcome` 当前规范为：
     - `category = check | contest | binary_action`
     - `passed? / winner? / margin?`
   - 这样：
     - 编排层仍可用 `executed` 判断能否继续结算
     - GM/NPC/前端可用 `outcome` 判断“过检 / 失败 / 对抗胜负”

5. 当前状态
   - 这条漂移已进入已修正状态，不再只是待审计项
   - 但文档层此前存在三处陈旧表述，已同步回正：
     - 对话检定 transport 说明
     - `action_result` 语义
     - 规则层 `skill_check` 返回值表述

## 7. 当前结论

当前系统不是“只有一两个遗留点没走主路径”，而是已经形成了三类并存状态：

1. **真正回到主路径的功能**
2. **子系统文档明确允许的内部直写**
3. **总设计要求经主路径，但实现已经旁路的功能**

真正危险的不是“有几个没走 command”，而是：

- 哪些能绕
- 为什么能绕
- 哪些属于合法例外

现在已经没有一份单一文档能稳定回答这三件事。

这就是后续最需要先收口的地方。
