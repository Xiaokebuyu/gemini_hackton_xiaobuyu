创建时间：2026-02-26
状态：参考文档（持续补充）

> 目标：彻底吃透 BG3（Divinity Engine 4.0）的底层架构，提取可直接指导我们 AI-CRPG 系统设计的核心原理。

---

## 一、总体哲学

BG3 的底层设计哲学可以浓缩为一句话：

> **机械层绝对确定，叙事层纯粹包装。**

这意味着：
- 规则引擎决定"发生了什么"（确定性）
- 叙事/脚本层决定"怎么呈现"（表现力）
- 两者**绝不混淆**——不存在"叙事层决定 HP 扣多少"这种事

推论：如果把叙事层整个砍掉，游戏的机械核心仍然可以纯数据驱动地运行——战斗能打，状态能变，存档能存。叙事层是"皮肤"，不是"骨骼"。

## 二、六层架构详解

```
┌─────────────────────────────────────────────────────────────┐
│ ❻ 表现层                                                     │
│   3D 渲染、UI、镜头调度、情感标签驱动的自动化动画              │
├─────────────────────────────────────────────────────────────┤
│ ❺ 叙事/脚本层                                                │
│   Osiris 脚本引擎、对话树、任务脚本、同伴审批事件、过场动画    │
├──── Osiris 是 ❸ 与 ❺ 的核心纽带 ────────────────────────────┤
│ ❹ AI/行为层（非 LLM）                                        │
│   效用评分 + 行为树（战斗 AI）、NPC 日程、同伴审批触发         │
├─────────────────────────────────────────────────────────────┤
│ ❸ 游戏状态层                                                 │
│   角色属性、世界标记/变量、队伍、任务进度、好感度、背包、       │
│   营地系统（休息 = 时间推进 + 叙事触发器）                     │
├─────────────────────────────────────────────────────────────┤
│ ❷ 规则引擎层（纯机械）                                       │
│   D&D 5e 规则集、d20 系统、战斗引擎、伤害计算、状态效果、     │
│   角色成长、装备系统、经济循环、法术位管理                     │
├─────────────────────────────────────────────────────────────┤
│ ❶ 内容/数据层（静态，只读）                                   │
│   世界地图、NPC 模板、怪物数据库、物品数据库、技能/法术库、    │
│   任务定义、对话树原始数据                                    │
└─────────────────────────────────────────────────────────────┘
```

### ❶ 内容/数据层——世界的 DNA

**性质**：静态只读。游戏启动时加载，运行时不可变。

**包含什么**：
- **世界地图**：区域定义、子地点、区域间连接关系（有向带权图）
- **NPC 模板**：每个 NPC 的基础属性、阵营、职业、可用对话树 ID、行为树 ID
- **怪物数据库**：属性、抗性、技能列表、掉落表、经验值
- **物品数据库**：名称、类型、属性加成、重量、价格、稀有度、特殊效果
- **技能/法术库**：施法条件、消耗、伤害公式、范围、持续时间、状态效果
- **任务定义**：任务 ID、各阶段条件、奖励、关联 NPC/地点
- **对话树数据**：节点 ID、文本、分支条件（引用 ❸ 层的标记/变量）、后果（写入 ❸ 层的操作）

**关键设计**：
- 数据和逻辑分离——对话树数据只是数据，驱动它的是 Osiris 引擎
- 所有数值都是结构化的，不存在"自由文本描述伤害"
- 模板 vs 实例：❶ 层存模板，❸ 层存实例化后的运行时状态

#### Tag 系统——❶ 层最重要的设计

BG3 的 Tag 系统是 Divinity Engine 中**最适配 AI 的特性**。世界中的每个实体（物品、NPC、地点、场景物件）都携带一组语义标签：

```
短匕首:       [WEAPON, DAGGER, SIMPLE, METAL, LIGHT, FINESSE]
治疗药水:     [CONSUMABLE, POTION, HEALING, MAGICAL]
神庙祭品:     [QUEST_ITEM, SACRED, TEMPLE_OF_X, VALUABLE]
酒馆老板:     [NPC, MERCHANT, TAVERN, CIVILIAN, FRIENDLY]
火药桶:       [OBJECT, EXPLOSIVE, ENVIRONMENTAL, DESTRUCTIBLE]
哥布林营地:   [LOCATION, HOSTILE, CAMP, GOBLIN, OUTDOORS]
冒险者公会:   [LOCATION, SAFE, GUILD, QUEST_HUB, URBAN]
```

Tag 是**所有层的通用语言**，每一层都消费它：

| 层 | 怎么用 Tag |
|----|-----------|
| ❷ 规则引擎 | `if item.has(FINESSE) → 可用 DEX 修正攻击`；`if target.has(UNDEAD) → 治疗法术造成伤害` |
| ❸ 状态层 | 实体的标签组合 = 它的身份描述和规则属性 |
| ❹ 战斗 AI | `场景中有 EXPLOSIVE 标签物件？→ 评估引爆效用` |
| ⊕ AI Osiris | `偷了 SACRED 物品 → 推理宗教阵营后果`（比读 item_id 推理质量高得多） |
| ❺ NPC Agent | `对方有 MERCHANT 标签 → 可以交易`；`有 HOSTILE → 拒绝对话` |

**Tag 对 AI 特别友好**：LLM 天然擅长处理语义标签。AI Osiris 看到 `[SACRED, TEMPLE_OF_X, VALUABLE]` 能自然推理出偷窃的宗教和经济后果，比看原始 ID 好得多。

**Tag 的分类维度**（BG3 参考）：
- **物理属性**：METAL, WOOD, LIQUID, LIGHT, HEAVY
- **功能类型**：WEAPON, ARMOR, CONSUMABLE, TOOL, QUEST_ITEM
- **战斗属性**：FINESSE, VERSATILE, RANGED, MAGICAL, EXPLOSIVE
- **阵营/归属**：SACRED, CURSED, GUILD_PROPERTY, STOLEN
- **角色属性**：MERCHANT, GUARD, HEALER, HOSTILE, ESSENTIAL
- **地点属性**：SAFE, DANGEROUS, URBAN, WILDERNESS, DUNGEON, CAMP

**对我们的启示**：
- 我们的 `WorldInstance`（世界静态数据注册表）= BG3 的 ❶ 层
- 当前数据完整度不足：缺少结构化的物品效果、法术公式、任务定义模板
- **物品/怪物/技能不应该只是"文本描述"，必须是可计算的结构化数据**
- **Tag 系统应作为 ❶ 层的核心基础设施**——所有实体在数据层就携带标签，上层系统统一消费。这直接影响世界书提取管线（提取时就要生成 Tag）和 WorldInstance 的数据结构设计

### ❷ 规则引擎层——世界的物理定律

**性质**：纯机械计算，零副作用。输入数据→输出结果，不关心"为什么"。

**核心子系统**：

| 子系统 | 输入 | 输出 | 特征 |
|--------|------|------|------|
| **d20 判定** | 属性修正 + 熟练 + DC | 成功/失败 + 骰值 | 一切检定的原子操作 |
| **战斗引擎** | 战场快照 + 动作选择 | 伤害/状态变化/位置变化 | 先攻→行动经济→回合循环 |
| **伤害计算** | 攻击类型 + 抗性 + 骰子 | 最终伤害值 | 类型→抗性/易伤/暴击 |
| **状态效果** | 效果 ID + 持续时间 | Buff/Debuff tick | 每回合/每触发结算 |
| **角色成长** | 当前 XP + 职业 | 可用特性/ASI/专长 | 经验值→等级→解锁 |
| **装备系统** | 物品 + 槽位 + 熟练 | AC/属性修正 | 装备约束（单手/双手/重甲熟练） |
| **经济循环** | 买卖操作 + 好感修正 | 金币变动 + 库存变动 | 价格 = 基础价 × 好感系数 |
| **法术位管理** | 施法操作 | 法术位消耗/恢复 | 短休/长休恢复规则 |

**核心原则**：

> **规则引擎是无状态的纯函数。** 它不持有状态，只读取 ❶ 的模板和 ❸ 的当前值，计算出结果，由调用方写回 ❸。

这意味着规则引擎可以：
- 被独立测试（给定输入，必得确定输出）
- 被 AI 层和引擎层共用（NPC 商人调价用同一套经济公式）
- 被"假执行"用于 AI 评分（❹ 层效用评分需要"如果我这样做，结果会怎样"）

**对我们的启示**：
- 我们的 `combat/` 已有战斗引擎（d20 + 距离带），但其他子系统（经济、装备效果、法术位）还是空壳
- **规则引擎应该可以脱离 LLM 独立运行和测试**
- 当前 `player/operations.py` 部分承担了规则引擎职责，但混杂了持久化逻辑

### ❸ 游戏状态层——世界的"当前现实"

**性质**：可变的运行时状态。是所有系统读写的**唯一真理来源**。

**核心内容**：

```python
WorldState = {
    # 世界标记——Osiris 的核心驱动数据
    flags: {
        "goblin_camp_destroyed": True,
        "rescued_halsin": False,
        "player_stole_idol": True,
        ...
    },

    # 角色实例（从 ❶ 模板实例化）
    characters: {
        "player": {hp: 45, max_hp: 52, level: 4, xp: 3200, ...},
        "shadowheart": {hp: 38, approval: 72, location: "camp", ...},
        "astarion": {hp: 29, approval: 45, location: "camp", ...},
        ...
    },

    # 任务状态机
    quests: {
        "rescue_halsin": QuestState.IN_PROGRESS,
        "find_mushroom": QuestState.COMPLETED,
        ...
    },

    # 背包
    inventory: {
        "player": [Item(id="longsword_+1", equipped=True), ...],
        ...
    },

    # 关系/好感度
    relationships: {
        ("player", "shadowheart"): 72,
        ("player", "merchant_guild"): 55,
        ...
    },

    # 时间（营地系统驱动，非实时）
    time: {day: 3, rests_taken: 2},

    # 地图探索
    exploration: {
        "forest_cave": ExplorationState.DISCOVERED,
        "goblin_camp": ExplorationState.CLEARED,
        ...
    },
}
```

**BG3 时间模型的关键纠偏**：

BG3 **没有**连续的实时日夜循环（不像巫师 3 或天际）。时间推进被抽象为**营地休息机制**：

| 机制 | 时间效果 | 规则效果（❷） | 叙事效果（❺） |
|------|---------|--------------|--------------|
| **短休息** | 不推进日期 | 恢复部分资源 | 无 |
| **长休息** | 推进到下一天 | 完全恢复 HP/法术位 | **核心叙事触发器**——几乎所有重要同伴对话和剧情推进都绑定在长休的营地过场中 |

这意味着：
- 长休 = 时间推进 + 规则重置 + 叙事节拍——三合一
- 玩家可以通过控制长休频率来控制剧情节奏
- "一天"不是 24 小时，而是"两次长休之间的冒险"

**世界标记（Flags）的核心地位**：

BG3 的标记系统是整个状态层的脊柱。几乎所有系统间通信都通过标记：
- 规则引擎写标记：`player_killed_goblin_leader = true`
- Osiris 读标记触发脚本：`if player_killed_goblin_leader → 解锁德鲁伊营地和平路线`
- AI 行为层读标记：`if camp_under_attack → 切换守卫行为树到战斗模式`
- 对话树分支读标记：`if rescued_halsin → 显示感谢对话选项`

标记不只是布尔值，也可以是枚举、计数器、时间戳。

**对我们的启示**：
- 我们的 `WorldGraph` 承担了状态容器角色，但缺少 BG3 标记系统的**结构化变量机制**
- 当前 NPC 的"记忆"分散在上下文窗口和记忆图谱两处，需要明确：**图谱 = 真理，上下文窗口 = 缓存**
- 时间模型：我们选择了 24 时间格制（比 BG3 更细粒度），这是合理的差异化——但要注意，BG3 用长休绑定叙事节拍的设计值得借鉴（我们可以在长休时触发同伴营地对话）

### Osiris 脚本引擎——❸ 与 ❺ 的核心纽带

**这是 Divinity Engine 最独特的技术。** 它不是传统 OOP，而是基于**逻辑编程**（类似 Prolog）的事件驱动引擎。

#### 工作原理

```
                    ❸ 状态层发生变化
                         │
                         ▼
              ┌─ Osiris 引擎（持续监听）─┐
              │                           │
              │  事实数据库（Facts）        │
              │  ┌─────────────────────┐  │
              │  │ Item_Stolen(Idol,P1)│  │   ← 新事实写入
              │  │ NPC_Dead(Goblin_01) │  │
              │  │ Area_Entered(Cave)  │  │
              │  └─────────────────────┘  │
              │           │               │
              │     模式匹配（Pattern     │
              │      Matching）           │
              │           │               │
              │  ┌─────────────────────┐  │
              │  │ 规则库（Rules）      │  │
              │  │ IF Item_Stolen(Idol) │  │   ← 预编写的规则
              │  │ AND Area == Druid    │  │
              │  │ THEN SetHostile(ALL) │  │
              │  └─────────────────────┘  │
              │           │               │
              └───────────┼───────────────┘
                          ▼
              触发 ❺ 叙事层响应 + 写回 ❸ 状态层
```

#### Osiris 的三个核心概念

1. **事实（Facts）**：世界中发生的事件或存在的状态，以结构化元组形式存在
   - `CharacterDied(character_id, killer_id, damage_type)`
   - `ItemPickedUp(character_id, item_id, container_id)`
   - `DialogueEnded(character_id, dialogue_id, chosen_node_id)`

2. **规则（Rules）**：`IF 条件组合 THEN 动作序列` 的声明式逻辑
   - 条件可以组合多个事实 + 状态查询
   - 动作可以修改状态、触发对话、播放动画、生成新事实

3. **事件广播（Event Broadcasting）**：状态变化时，Osiris 向全图广播事实，所有匹配的规则同时激活

#### 关键特性

- **网状触发**：一个事实可以匹配多条规则，产生多个后果（蝴蝶效应）
  - 偷神像 → 德鲁伊敌对 + 提夫林被迫参战 + 盖尔好感 -10 + 失去和平路线
- **链式反应**：规则的动作可以产生新事实，触发更多规则
  - 德鲁伊敌对 → 新事实 `FactionHostile(Druid)` → 触发守卫战斗行为树
- **声明式**：编写者不需要管"执行顺序"，只需要声明"什么条件下做什么"
- **确定性**：相同的事实+状态，永远产生相同的结果

#### 288 个任务的秘密

BG3 有 288 个任务，每个任务有多条路线，总分支数以千计。这不是靠"写 if-else"实现的，而是靠 Osiris 的声明式规则：

```
# 伪代码示意
RULE "HalsinRescue_Complete":
    IF CharacterMoved(Halsin, Camp)
    AND QuestState(RescueHalsin) == IN_PROGRESS
    THEN:
        SetQuestState(RescueHalsin, COMPLETED)
        GiveXP(Player, 500)
        SetFlag(halsin_in_camp, true)
        TriggerDialogue(Halsin, "thank_you_dialogue")
```

每条规则只管自己的一小块逻辑，但组合起来形成复杂的涌现行为。这和传统的"写一个巨大的任务管理器"完全不同。

#### 对我们的启示

**Osiris 在我们系统中的对应物 = `BehaviorEngine`（事件状态机）+ AI Agent 叙事**

BG3 用 Osiris 做两件事：
1. 条件检查 → 触发状态变更（机械的）—— 对应我们的 `BehaviorEngine.tick()`
2. 触发叙事响应（文本的）—— 对应我们的 GM/NPC Agent

关键区别：BG3 的 Osiris 规则是预编写的（确定性），我们的 AI 叙事是实时生成的（概率性）。因此：
- **机械触发必须保留在引擎中**（不能让 AI 决定"偷东西是否导致敌对"）
- **AI 只负责"怎么呈现"这个已确定的后果**（德鲁伊变敌对了，GM 叙述这个场景）
- 我们的事件状态机需要支持类似 Osiris 的**声明式规则 + 事实广播**模式

### ❹ AI/行为层——无 LLM 的"智能"

**性质**：基于规则的确定性 AI，不涉及任何机器学习。

#### 战斗 AI：效用评分系统（Utility Scoring）

BG3 的敌人"聪明"不是因为有 AI，而是因为它**穷举规则内的最优解**：

```
每个 NPC 的回合：
    1. 读取战场快照（❸ 状态层）
       - 所有角色位置、HP、状态效果
       - 环境交互物（火药桶、高地、深渊边缘）

    2. 枚举所有合法动作（❷ 规则引擎）
       - 对 A 使用近战攻击 → 命中率 70%, 预期伤害 8
       - 对 B 使用远程攻击 → 命中率 45%, 预期伤害 12
       - 移动到高地再射击 → 命中率 65%, 预期伤害 12
       - 推 A 下悬崖 → 命中率 60%, 预期伤害 ∞
       - 引爆身旁火药桶 → 命中率 100%, 波及 3 人

    3. 效用评分（❹ 打分函数）
       - 每个动作组合 = 成功率 × 预期收益 - 自身风险
       - 考虑：集火低 HP 目标、优先控制施法者、利用环境

    4. 选择最高分动作执行

    5. 写回结果到 ❸ 状态层
```

**关键点**：
- 效用评分的所有计算都依赖 ❷ 规则引擎的"假执行"（模拟计算，不实际改变状态）
- 不同怪物类型有不同的评分权重（野兽偏好近战、法师偏好远程、头目偏好集火治疗者）
- 这不是"AI 在思考"，是**穷举 + 打分 + 选最优**

#### NPC 非战斗行为：行为树（Behavior Trees）

NPC 的日常行为通过行为树定义：

```
酒馆老板行为树：
├─ 白天序列
│   ├─ 走到吧台
│   ├─ 播放擦杯动画
│   ├─ IF 玩家在附近 → 面向玩家
│   └─ 等待交互
├─ 夜晚序列
│   ├─ 走到卧室
│   └─ 不可交互
└─ 战斗触发
    ├─ IF 阵营变敌对 → 拿起武器
    └─ 执行战斗 AI
```

#### 同伴审批系统（Approval System）

BG3 的同伴好感度变化**不是 AI 判断的**，而是预设的触发条件：

```
# 预编写的审批事件
ApprovalEvent:
    trigger: PlayerAction("help_tiefling_child")
    reactions:
        shadowheart: +1    # 同情弱者
        astarion: -1       # 嫌麻烦
        laezel: 0          # 不关心
```

每个审批事件是手工编写的 `(触发条件, 角色→分值)` 元组。BG3 有数百个这样的事件。

#### 对我们的启示

- **战斗 AI**：我们的 `ai_opponent.py` 已经在做效用评分，方向正确。需要加强的是环境交互评分。
- **NPC 日程**：我们的 `TimeManager` 有 NPC 日程概念，但实现还很浅。BG3 的行为树模式值得参考。
- **同伴审批**：这是我们和 BG3 差异最大的地方。BG3 预设了所有审批事件；我们用记忆图谱 + LLM 判断同伴反应。两种方案各有优劣：
  - BG3 方案：确定性高，但需要大量人工编写
  - 我们的方案：灵活性高，但 LLM 可能产生不一致的反应
  - **折中方案**：对重要剧情节点预设审批事件（确定性），对日常交互用 LLM 生成（灵活性）

---

### ❺ 叙事/脚本层——世界的"声音"

**性质**：对已确定事实的包装呈现。负责"怎么说"，不决定"发生什么"。

#### 核心组件

1. **对话树**：手工编写的分支结构
   - 每个节点包含：文本、说话人、情感标签、分支条件（读 ❸ 标记）、后果（写 ❸ 标记）
   - 对话选项可以包含能力检定（`[说服 DC14]`），检定由 ❷ 规则引擎执行

2. **任务脚本**：Osiris 规则驱动的任务状态转换 + 关联的叙事内容

3. **同伴剧情线**：绑定在长休/特定事件上的预编写对话序列
   - 触发条件由 ❸ 标记组合判定
   - 一条剧情线通常跨越多次长休，每次解锁一段

4. **过场动画**：预渲染或实时渲染的叙事片段，在关键剧情节点播放

#### 对话中的能力检定——"按钮化"的典范

BG3 对话中的能力检定是一个极其精妙的设计：

```
对话选项列表：
  1. "我们和平解决吧。"                          ← 普通选项（无检定）
  2. [说服 DC 14] "你应该放他们走。"              ← 触发 ❷ 规则引擎 d20 检定
  3. [威吓 DC 16] "再不让开我就不客气了。"        ← 触发 ❷ 规则引擎 d20 检定
  4. [攻击] "够了，动手！"                        ← 触发 ❷ 战斗引擎
```

玩家不需要"自由输入我想威吓他"——系统已经把可用的交互方式**结构化为按钮**。这消除了歧义，同时保留了选择自由度。

#### 对我们的启示

**我们的 L1 AI 叙事层 = BG3 ❺ 叙事层的 AI 化替代**

| BG3 ❺ 层组件 | 我们的对应 | 差异 |
|--------------|-----------|------|
| 对话树（预编写） | NPC Agent 实时生成 | AI 替代手工编写 |
| 任务脚本 | 事件状态机 + GM 叙述 | 机械触发 + AI 包装 |
| 同伴剧情线 | 记忆图谱 + 队友 Agent | 关系自然生长 vs 预设 |
| 过场动画 | GM 环境叙述 | 文字替代画面 |
| 能力检定选项 | 对话选项按钮（含检定） | **应保持相同模式** |

**关键原则**：
- 对话选项中的能力检定，我们也应该做成按钮（`[说服 DC14] 让守卫通融`），点击后引擎掷骰，而不是让 AI 自己决定检定是否成功
- NPC Agent 生成对话内容，但**对话产生的机械后果由引擎执行**

---

### ❻ 表现层——半自动化的"皮肤"

**性质**：将 ❸ 状态变化和 ❺ 叙事内容渲染为玩家可感知的形式。

#### BG3 的半自动化镜头调度

面对海量的对话场景，Larian 不可能手动制作每个镜头，因此使用了**情感标签驱动的自动化系统**：

```
对话节点数据：
{
    speaker: "Shadowheart",
    text: "If you betray me, I'll make you regret it.",
    emotion_tag: "threatening",      ← 情感标签
    emphasis: "high",
    ...
}

表现层自动化：
    emotion_tag = "threatening"
    → 镜头：中景特写，仰角
    → 表情：眉头紧锁，嘴角下沉
    → 手势：手指指向玩家
    → 灯光：微暗

    之后动画师只对关键节点人工精调
```

#### 对我们的启示

**我们的表现层 = 前端 UI + 文字渲染**

虽然我们没有 3D 渲染，但情感标签的思路直接适用：
- 当前已有 `FEELING_MAP` 情感翻译层——这与 BG3 的 emotion_tag 是同一个设计模式
- 可以基于情感标签驱动前端 UI 效果（角色立绘表情切换、背景色调变化、文字排版风格）
- 详见 `表现层设计-视觉小说风格.md`

## 三、四种核心数据流

BG3 的数据流不是简单的单向传递，而是由**玩家输入（主动）+ 系统事件（被动）**双重驱动的循环。

### 数据流 1：玩家操作流（Top-Down 闭环）

**最高频的数据流。** 遵循"输入→校验→运算→状态变更→渲染"的确定性闭环。

```
  ❻ 表现层          ❸ 状态层          ❷ 规则引擎         ❸ 状态层          ❻ 表现层
  ┌──────┐         ┌──────┐         ┌──────┐          ┌──────┐         ┌──────┐
  │玩家点击│ ──────→│前置校验│ ──────→│规则运算│ ───────→│状态突变│ ──────→│表现反馈│
  │"火球术"│        │法术位？│        │8d6 伤害│         │HP 变化│        │爆炸特效│
  │       │        │行动点？│        │敏捷豁免│         │状态附加│        │飘字动画│
  └──────┘         └──────┘         └──────┘          └──────┘         └──────┘
```

**场景示例——向地精施放火球术**：
1. **UI 发起（❻）**：玩家点击"火球术"，选中目标区域
2. **前置校验（❸）**：系统查询——还有三环法术位吗？还有行动点吗？没有→红字拒绝
3. **规则运算（❷）**：读取 ❶ 火球术数据（8d6 火焰），掷骰，目标做敏捷豁免
4. **状态突变（❸）**：地精 HP 减少，附加"燃烧"状态，玩家扣法术位
5. **表现反馈（❻）**：播放爆炸特效、扣血飘字、惨叫音效

**核心特征**：
- **先执行后展示**：引擎在一帧内完成全部计算，然后才播放动画。动画是对**已发生事实的回放**
- **校验前置**：不合法的操作在进入规则引擎之前就被拦截
- 整个流程是**同步、确定性**的

**对我们的映射**：
```
按钮动作入口 → 引擎 pre-tick → 规则引擎计算 → WorldGraph 状态更新 → SSE 推送结果
                                                                    → GM Agent 叙述（异步）
```

---

### 数据流 2：Osiris 叙事事件流（Bottom-Up 蝴蝶效应）

**BG3 处理复杂叙事的核心机制。** 基于事件广播和模式匹配，产生网状连锁反应。

```
  ❸ 状态变化         Osiris 引擎        ❺ 叙事层          ❸ 状态更新
  ┌────────┐       ┌──────────┐       ┌──────┐         ┌────────┐
  │偷走神像 │ ────→ │事实广播   │ ────→ │规则A  │ ──────→ │德鲁伊   │
  │         │       │          │       │规则B  │         │变敌对   │
  │         │       │模式匹配  │       │规则C  │ ──────→ │盖尔好感 │
  │         │       │          │       │规则D  │         │-10     │
  └────────┘       └──────────┘       └──────┘         └────────┘
                                                            │
                                                            ▼ 产生新事实
                                                        ┌────────┐
                                                        │连锁触发 │
                                                        │更多规则 │
                                                        └────────┘
```

**场景示例——偷窃西凡纳斯神像**：
1. **事实生成（❸）**：玩家拿走神像 → 状态层记录 `Item_Stolen(Idol, Player_1)`
2. **事件广播（Osiris）**：向全图广播这个事实
3. **多规则匹配激活**：
   - 规则 A：`IF Item_Stolen(Idol) AND Area == DruidGrove → SetHostile(Druid_Faction)`
   - 规则 B：`IF Item_Stolen(Idol) → ModifyApproval(Gale, -10)`
   - 规则 C：`IF Item_Stolen(Idol) → SetQuestState(DruidPeace, FAILED)`
   - 规则 D：`IF FactionHostile(Druid) → TriggerDialogue(Kagha, "confrontation")`
4. **连锁反应**：德鲁伊敌对 → 守卫行为树切换到战斗模式 → 提夫林被卷入 → ...

**核心特征**：
- **非线性**：一个事实触发多条规则，每条规则可能产生新事实，继续触发
- **声明式**：规则作者不需要考虑执行顺序
- **确定性**：相同条件必定产生相同结果
- **可调试**：可以追溯任何状态变化的完整因果链

**对我们的映射**：
```
WorldGraph 状态变化 → BehaviorEngine.tick()（条件检查 + 状态变更）
                   → SceneBus 事件记录
                   → GM Agent 叙述连锁后果（AI 替代预编写文本）
```

**关键差异**：BG3 的 Osiris 规则是预编写的，我们的部分用 `BehaviorEngine` 机械执行（确定性），部分由 AI 生成叙事响应（概率性）。原则是：**因果链中的机械部分（状态变更）必须确定性，只有叙述部分可以交给 AI**。

---

### 数据流 3：AI 决策流（环境读取 + 效用穷举）

**NPC/怪物回合的数据流。** 完全在底层循环，不需要玩家输入。

```
  ❸ 状态层 + ❶ 数据层       ❹ AI 行为层         ❷ 规则引擎          ❸ 状态层
  ┌─────────────────┐     ┌───────────┐      ┌──────────┐       ┌────────┐
  │读取战场快照      │ ──→ │枚举所有    │ ←──→ │假执行计算  │       │执行最优 │
  │角色位置/HP/状态  │     │可能动作    │      │命中率     │ ────→ │动作     │
  │环境交互物       │     │           │      │预期伤害   │       │写回状态 │
  │               │     │效用打分    │      │波及范围   │       │         │
  └─────────────────┘     └───────────┘      └──────────┘       └────────┘
                               │
                          选择最高分
```

**场景示例——地精弓箭手的回合**：
1. **读取环境（❸+❶）**：战场上有 4 个玩家角色、2 个火药桶、1 个高地
2. **枚举动作 + 假执行评分（❹↔❷）**：
   - 射击法师：命中率 70% × 预期伤害 8 = 效用 5.6
   - 移动到高地射击：命中率 80% × 预期伤害 8 + 高地防御加成 = 效用 7.4
   - 引爆火药桶：命中率 100% × 预期伤害 20 × 波及 3 人 - 自身风险 = 效用 52
3. **选择最优动作**：引爆火药桶（效用 52 远高于其他）
4. **执行并写回（❸）**：火药桶爆炸，3 个角色受伤，火药桶移除

**核心特征**：
- ❹ 层和 ❷ 层之间是**高频往返**的：每个候选动作都要交给规则引擎"假执行"一次
- **"假执行"**是规则引擎无状态设计的直接红利——可以安全地模拟计算而不影响真实状态
- 不同怪物类型有不同的效用权重（体现"性格"：鲁莽的偏好高风险高回报，谨慎的偏好稳健）

**对我们的映射**：
```
我们的战斗 AI：ai_opponent.py 已有效用评分基础
我们的 NPC 非战斗行为：当前用 LLM Agent 替代行为树
                     → 对于机械性行为（日程、巡逻），应回归规则驱动
                     → 对于对话/互动，继续用 Agent
```

---

### 数据流 4：持久化/存档流（增量差异）

**BG3 的存档以体积庞大著称。** 其持久化策略是**增量差异（Diff）**。

```
  ❶ 静态初始数据                 ❸ 当前运行时状态
  ┌─────────────┐              ┌─────────────┐
  │ 杯子位置:     │              │ 杯子位置:     │
  │ (10, 20, 30)│              │ (10, 20, 40)│ ← 玩家移动了杯子
  │              │              │              │
  │ 地精A: alive │              │ 地精A: dead  │ ← 玩家杀了地精
  │              │              │              │
  │ 门A: locked  │              │ 门A: unlocked│ ← 玩家撬了锁
  └─────────────┘              └─────────────┘
         │                            │
         └──── Diff ──────────────────┘
                  │
                  ▼
         ┌──────────────┐
         │   存档文件     │
         │ 杯子: z=40    │   ← 只保存差异
         │ 地精A: dead   │
         │ 门A: unlocked │
         │ ...数千个变量  │
         └──────────────┘
```

**运作方式**：
- 游戏不保存整个世界，保存的是**当前 ❸ 与初始 ❶ 之间的差异**
- 即使是微小的变化（杯子移动 10cm、地上扔了一块奶酪）也会被记录
- 越到后期，玩家创造的差异变量指数级增长 → 存档体积膨胀

**加载流程**：
1. 加载 ❶ 静态数据层（世界初始状态）
2. 在其上叠加存档中的差异变量
3. 重建 ❸ 当前状态层

**对我们的映射**：
```
我们的持久化：Firestore（云端） + WorldGraph 快照
当前方案：SessionRuntime.persist() 全量写入
BG3 启示：可以优化为增量持久化（只写 dirty 字段）
         → 我们已有 dirty tracking 机制，方向正确
         → 但 WorldGraph 的快照粒度可能太粗，需要字段级 dirty 标记
```

## 四、从 BG3 演化到我们的架构

### 4.1 演化总纲：什么保留、什么替换

BG3 有六层。我们逐层决定：原样保留 / AI 替代 / 重新设计。

| BG3 层 | 决定 | 原因 |
|--------|------|------|
| ❶ 内容/数据层 | **保留**，数据来源改为世界书提取 | 静态只读的设计不变，只是数据生产方式不同 |
| ❷ 规则引擎层 | **保留** | 纯机械计算，和 BG3 完全一样 |
| ❸ 游戏状态层 | **保留** | 唯一真理来源，和 BG3 完全一样 |
| ❹ AI/行为层 | **保留战斗 AI**，NPC 日常行为由 Agent 替代 | 战斗效用评分是最优解；日常行为用 LLM 更灵活 |
| Osiris 引擎 | **AI 替代**→ AI Osiris（专职因果判定 LLM） | 核心洞察：手工规则→AI 推理后果 |
| ❺ 叙事/脚本层 | **AI 替代**→ GM/NPC/队友 Agent | 核心差异化：实时生成替代手工编写 |
| ❻ 表现层 | **重新设计**→ 视觉小说风格前端 | 文字+立绘+UI，不需要 3D |

### 4.2 演化后的六层架构

```
┌─────────────────────────────────────────────────────────────────┐
│ ❻ 表现层（前端）                                                 │
│   视觉小说 UI：立绘 + 文字 + 按钮面板 + 情感标签驱动的氛围切换   │
├─────────────────────────────────────────────────────────────────┤
│ ❺ AI 叙事层（L1）                                                │
│   GM Agent（纯只读叙述）、NPC Agent（对话+角色权限内操作）、       │
│   队友 Agent（对话+队友权限内操作）                                │
│   ※ 替代 BG3 的手工对话树/任务脚本/同伴剧情线                    │
│   ※ 格内即时响应：每个玩家动作后实时触发                          │
├─────────────────────────────────────────────────────────────────┤
│ ⊕ AI Osiris（因果判定 LLM）                                     │
│   每时间格结算时触发 → 批量推理本格所有状态变化的跨系统后果       │
│   → 输出结构化状态变更指令 → 引擎验证执行                        │
│   ※ 替代 BG3 的 Osiris 手工规则引擎                              │
│   ※ 后台运行，不面向玩家，输出不是叙述文本而是机械指令           │
│   ※ 格级触发（非事件级），每格只调用一次                         │
├─────────────────────────────────────────────────────────────────┤
│ ❹ 行为层（非 LLM）                                              │
│   战斗 AI（效用评分，和 BG3 一样）、NPC 日程、遭遇检定           │
├─────────────────────────────────────────────────────────────────┤
│ ❸ 游戏状态层                                                     │
│   WorldGraph（统一状态容器）、角色状态、任务进度、背包、           │
│   好感度、时间（24 时间格制）、事件标记、场景总线                 │
├─────────────────────────────────────────────────────────────────┤
│ ❷ 规则引擎层（纯机械，和 BG3 一样）                              │
│   D20 判定、战斗引擎、伤害计算、装备效果、角色成长、经济循环     │
├─────────────────────────────────────────────────────────────────┤
│ ❶ 内容/数据层（静态只读，和 BG3 一样）                           │
│   世界地图、NPC 模板、物品库、怪物库、技能库、任务模板            │
│   ※ 数据来源：世界书提取管线（而非手工编辑器）                   │
└─────────────────────────────────────────────────────────────────┘
```

与 BG3 的**结构性差异**只有两处：
1. **❺ 叙事层**：从手工脚本 → AI Agent（GM/NPC/队友）
2. **新增 ⊕ AI Osiris**：从手工声明式规则 → 专职因果判定 LLM

其余四层（❶❷❸❹）**与 BG3 完全同构**。

### 4.3 时间格：游戏的基本节拍

BG3 的 Osiris 是事件驱动的——每个状态变化瞬间触发模式匹配（微秒级）。我们的 AI Osiris 是 LLM 调用（秒级），不可能逐事件触发。

**解决方案：以时间格为节拍，分两层响应。**

时间格（玩法设计中的 24 格/天）不仅是时间经济单位，也是**管线的生命周期单位**：

```
时间格 N 的完整生命周期
═══════════════════════════════════════════════════════════

  ┌─ 即时层：格内动作循环（可重复多次）───────────────────┐
  │                                                       │
  │  玩家动作 → 引擎执行 → SceneBus → NPC/GM/队友响应     │
  │  玩家动作 → 引擎执行 → SceneBus → NPC/GM/队友响应     │
  │  玩家动作 → ...                                        │
  │                                                       │
  │  ※ 每个动作有即时的场景内响应（数据流 1+3）             │
  │  ※ 所有状态变化累积在 ❸ 中                             │
  │  ※ SceneBus 在整个时间格内持续，上下文越来越丰富       │
  │  ※ 动作计数累积，达到阈值扣 1 格                       │
  │                                                       │
  └───────────────────────────────────────────────────────┘
                          │
                    时间格扣完
                          │
                          ▼
  ┌─ 结算层：Tick 结算（每格一次）───────────────────────┐
  │                                                       │
  │  1. 收集本格内所有状态变化的摘要                        │
  │  2. ⊕ AI Osiris 批量推理跨系统后果 → 结构化指令        │
  │  3. ❷ 引擎验证并执行指令 → ❸ 状态更新                  │
  │  4. ❺ GM 叙述结算结果（如有显著变化）                   │
  │  5. 时间推进 → 检查时段切换（白天→黄昏？）              │
  │  6. SceneBus 重置，进入新格                            │
  │                                                       │
  └───────────────────────────────────────────────────────┘
                          │
                          ▼
                     时间格 N+1
```

**为什么这样设计**：

| 设计选择 | 理由 |
|---------|------|
| 即时层处理场景内直接反应 | 店主看到你偷东西当场抓人——不能等到格结算 |
| 结算层处理跨系统涟漪后果 | 商会好感 -20、盗贼公会注意到你——玩家感知不到即时性 |
| SceneBus 跨格内所有动作 | NPC/队友能看到前面所有对话，上下文连贯 |
| AI Osiris 每格只调一次 | 批量处理，上下文完整，成本可控 |

**与 BG3 的本质差异**：

BG3 的 Osiris 是**即时事件驱动**（微秒级模式匹配，无成本压力）。
我们的 AI Osiris 是**回合制结算**（秒级 LLM 调用，每格一次）。

这不是妥协，而是更好的设计——桌游 DM 也不是每个微动作都判定后果，而是在场景/回合结束时统一结算。批量推理的上下文更完整，判定质量更高。

### 4.4 演化后的三种数据流

#### 数据流 1：玩家操作 + 即时响应（格内，每动作触发）

**触发方式**：玩家点击按钮 / 输入文字

```
❻ 玩家动作（按钮 或 文字）
    │
    ├─ 按钮动作 ─────────────────────┐
    │  引擎 pre-tick 机械执行         │
    │  ❸ 校验 → ❷ 规则计算 → ❸ 写入  │
    │  结果写入 SceneBus              │
    │                                │
    ├─ 文字输入 ──────┐              │
    │  玩家发言写入    │              │
    │  SceneBus       │              │
    │                 │              │
    └─────────────────┴──────────────┘
                      │
                      ▼
              SceneBus（格内共享）
                      │
                      ▼
              ❺ NPC Agent 读 SceneBus
              即时回应 + 角色权限内工具调用
              结果写入 SceneBus
                      │
                      ▼
              ❺ GM Agent 读 SceneBus
              叙述环境（大多数时候 [PASS]）
                      │
                      ▼
              ❺ 队友 Agent 依次读 SceneBus
              决定是否发言（顺序感知）
                      │

              ❻ SSE 推送本次动作的所有响应

    ※ 状态变化累积在 ❸，等格结算时交给 AI Osiris
    ※ SceneBus 不重置，继续积累到格结束
```

**核心不变**：先执行后展示。GM 叙述的是已发生的事实。

#### 数据流 2：AI Osiris 结算流（格结束时触发，每格一次）

**触发方式**：时间格扣完 → 自动进入 Tick 结算

BG3 的 Osiris 逐事件即时匹配规则。我们的 AI Osiris 按时间格批量结算——一格内的所有状态变化，打包给 LLM 统一推理。

```
时间格扣完
        │
        ▼
收集本格状态变化摘要
    例（一格内发生了这些事）：
    - 玩家与商人交易，买了一把匕首
    - 玩家和酒馆老板对话，得知西边牧场被袭击
    - 玩家在神庙偷了祭品（潜行成功，无人目击）
    - 队友审判骑士目击了偷窃行为
        │
        ▼
⊕ AI Osiris（因果判定 LLM）
    输入：
      - 本格状态变化摘要（上面这些）
      - 当前世界状态快照：位置、阵营关系、任务进度...
      - 世界规则上下文：各势力设定、重要物品标记...

    推理："这一格发生的这些事，会产生什么跨系统后果？"

    输出：结构化指令
      {
        "consequences": [
          {"type": "set_flag", "key": "temple_offering_stolen", "value": true},
          {"type": "modify_disposition", "target": "temple_faction", "delta": -30},
          {"type": "modify_approval", "character": "paladin_companion", "delta": -15},
          {"type": "create_rumor", "content": "有人在神庙行窃", "spread_to": ["temple_district"]},
          {"type": "advance_quest", "quest": "western_farm_attack", "to_state": "DISCOVERED"}
        ]
      }
        │
        ▼
❷ 引擎验证并执行
    逐条验证指令合法性（非法指令拒绝）
    执行合法指令 → ❸ 状态写入
    ※ AI Osiris 只判，引擎才执行
        │
        ▼
❺ GM 叙述结算结果（如有玩家可感知的变化）
    例："夜风中似乎传来了一些窃窃私语，神殿区的气氛变得微妙起来..."
        │
        ▼
时间推进 → 检查时段切换 → SceneBus 重置 → 进入下一格
```

**与 BG3 Osiris 的对比**：

| | BG3 Osiris | 我们的 AI Osiris |
|---|---|---|
| 触发频率 | 每个状态变化即时触发 | **每时间格结算一次** |
| 规则来源 | 数千条手工声明式规则 | LLM 基于世界设定实时推理 |
| 输入粒度 | 单个事实 | **一格内所有变化的批量摘要** |
| 确定性 | 100% | 高度一致但非 100%（LLM 特性） |
| 覆盖范围 | 只覆盖预编写的情况 | 理论上覆盖任意情况 |
| 输出格式 | 引擎内部指令 | 结构化 JSON 指令（引擎可执行） |
| 开发成本 | 极高（百人年级） | 极低（prompt + schema 设计） |
| 推理质量 | 精确但死板 | **上下文完整，因为看到了整格的完整画面** |

**AI Osiris 的约束设计**：

```
核心约束：
  1. 输出必须是结构化指令，不是自由文本
  2. 指令必须经过 ❷ 引擎验证——非法指令被拒绝
  3. 不面向玩家——玩家看到的是 GM 叙述，不是 AI Osiris 的输出
  4. 每格只调一次——不存在链式递归问题（一次推理看到全貌）

职责边界：
  ⊕ AI Osiris: "这一格发生的事应该导致什么后果" → 判定
  ❷ 引擎:      "执行这些后果的机械操作"           → 执行
  ❺ GM Agent:  "用文学语言描述变化"               → 叙述
```

> **注意**：回合制结算还自然消除了之前设计中"链式递归深度限制"的问题。AI Osiris 一次性看到整格的全部变化，输出一批后果，不需要再链式触发自己。如果后果本身产生的新变化需要进一步推理，那是下一格结算的事了。

#### 数据流 3：Agent 行动流（格内即时，替代 BG3 的 AI 决策流）

**触发方式**：格内，轮到 NPC/队友行动时（对话轮次 / 战斗回合 / 日程触发）

**3a. 战斗场景——与 BG3 一致（效用评分）**

```
❸+❶ 读取战场快照
        │
        ▼
❹ 战斗 AI：枚举动作 + ❷ 假执行评分
        │
        ▼
选最优 → ❷ 真执行 → ❸ 状态写入 → ❻ 表现
```

不变。效用评分是战斗 AI 的最优解，不需要 LLM。

**3b. 非战斗场景——LLM Agent 即时响应**

```
SceneBus 有新内容（玩家说话 / 引擎执行结果）
        │
        ▼
❺ NPC Agent 读取：
    - SceneBus 格内全部内容（之前所有动作的上下文）
    - ❸ 自身状态 + 世界状态
    - 记忆图谱
        │
        ▼
NPC Agent 决策 + 行动：
    1. 生成对话回应 → 写入 SceneBus
    2. 可能调用角色权限内工具 → ❷ 规则引擎 → ❸ 状态写入
       ※ 工具由 RoleRegistry 按 (role, traits) 分配
       ※ 这些状态变化也累积到本格摘要，格结算时给 AI Osiris
```

**与 BG3 的对比**：

| | BG3 NPC 行为 | 我们的 NPC Agent |
|---|---|---|
| 对话内容 | 预编写对话树 | LLM 实时生成 |
| 行动决策 | 行为树，确定性 | Agent 推理，受权限沙箱约束 |
| 后果传播 | Osiris 即时触发连锁 | **累积到格结算，AI Osiris 统一处理** |

### 4.5 三种数据流的统一关系

```
    ┌──────────────── 时间格生命周期 ─────────────────────────┐
    │                                                         │
    │   格内即时响应                                           │
    │   ┌──────────┐        ┌──────────┐                      │
    │   │ 数据流 1  │        │ 数据流 3  │                      │
    │   │ 玩家操作  │        │ Agent 行动│                      │
    │   │ 按钮/文字 │        │ NPC/队友  │                      │
    │   │→引擎→状态 │        │→工具→状态 │                      │
    │   │→NPC/GM   │        │→SceneBus │                      │
    │   └────┬─────┘        └────┬─────┘                      │
    │        │                    │                            │
    │        └───── 状态变化累积 ──┘                            │
    │                    │                                     │
    ├────────────────────┼─────────── 格结算线 ────────────────┤
    │                    │                                     │
    │              ┌─────▼─────┐                               │
    │              │ 数据流 2   │                               │
    │              │ AI Osiris │                               │
    │              │ 批量推理   │                               │
    │              │→引擎执行  │                               │
    │              │→GM 叙述   │                               │
    │              └─────┬─────┘                               │
    │                    │                                     │
    │              时间推进 + SceneBus 重置                      │
    └────────────────────┼─────────────────────────────────────┘
                         ▼
                    时间格 N+1
```

**关键统一点**：
- **格内**：数据流 1+3 交替运行，即时响应，状态变化累积
- **格结算**：数据流 2 一次性处理本格全部变化的跨系统后果
- **❸ 是中心**：三种流都读写同一个 WorldGraph
- **❷ 被共用**：玩家操作用它真执行，战斗 AI 用它假执行，AI Osiris 指令也经它验证
- **SceneBus 生命周期 = 一个时间格**：格内所有动作共享上下文，格结算后重置

### 4.7 编排层：TickCoordinator + PipelineOrchestrator

编排层是把所有层串起来的胶水。核心组件关系：

```
AdminCoordinator（入口单例，HTTP 请求进入）
    │
    ▼
TickCoordinator（NEW：格生命周期管理器）
    │
    │  持有（会话级状态）：
    │  - 当前格编号 / 累积时间消耗
    │  - 本格状态变化记录（给 AI Osiris 的摘要素材）
    │  - SceneBus 引用（格级生命周期）
    │
    │  每次请求的处理流程：
    │  1. 委托 PipelineOrchestrator 处理即时响应
    │  2. 从引擎拿到本次动作的时间成本
    │  3. 累加时间，while >= 1.0 格 → tick_settlement()
    │
    ▼
PipelineOrchestrator（格内单次动作处理，不感知格边界）
    引擎执行 → SceneBus → NPC/GM/队友 → 返回响应 + 时间成本
```

#### 统一的时间成本模型

每个动作向 TickCoordinator 报告时间成本，TickCoordinator 只管累加和触发结算：

| 动作 | 时间成本 | 结算触发 |
|------|---------|---------|
| 进入/离开子地点、装备、查看 | 0 | 不触发 |
| 对话、交易、搜索、使用物品 | 1/6 格 | 累积 6 次后触发 |
| 短休息 | 1 格 | 立即触发 1 次 |
| 区域间移动 | 1-3 格（按地图边权重） | 逐格触发 |
| 战斗 | ceil(回合数/6) 格 | 战斗结束后逐格触发 |
| 长休息 | 剩余全部格 | 逐格触发 |

#### TickCoordinator 核心逻辑

```python
class TickCoordinator:

    def after_action(self, time_cost: float):
        """每个动作处理完后调用"""
        self.accumulated += time_cost

        while self.accumulated >= 1.0:
            self.accumulated -= 1.0
            self.tick_settlement()

    def tick_settlement(self):
        """每满 1 格执行一次"""
        # 1. 收集本格状态变化摘要
        changes = self.collect_state_changes()

        # 2. AI Osiris 推理跨系统后果
        instructions = self.ai_osiris.evaluate(changes, self.world_snapshot)

        # 3. 引擎验证并执行指令
        self.engine.execute_validated(instructions)

        # 4. GM 叙述结算结果（如有显著变化）
        self.gm_agent.narrate_settlement(changes, instructions)

        # 5. 时间推进
        self.time_manager.advance(1)

        # 6. 检查时段切换事件（白天→黄昏？）
        self.check_period_transition()

        # 7. SceneBus 重置
        self.scene_bus.reset()

        # 8. 重置状态变化记录
        self.reset_change_log()
```

#### 多格动作的自然涌现

逐格结算不是性能妥协，而是**玩法设计**——每格结算可以产生不同的事件：

```
场景：玩家从边境小镇移动到西部牧场（3 格）

格 1 结算（出发）：
    AI Osiris：小镇居民注意到冒险者出发了
    遭遇检定：d20 + 危险系数 → 无遭遇
    GM："你沿着西行的土路出发，午后的阳光洒在麦田上。"

格 2 结算（途中）：
    AI Osiris：路上经过猎人营地（世界数据中的中途地点）
    遭遇检定：d20 + 危险系数 → 命中！随机遭遇
    → 触发战斗 or 路人事件（猎人求助？路匪？）

格 3 结算（抵达）：
    AI Osiris：根据西部牧场当前状态（被袭击后），推理抵达时看到什么
    GM："远远地，你看到牧场的篱笆被撞开了几个大洞，空气中弥漫着焦糊味..."

场景：长休息（剩余 8 格，跳到次日 05:00）

格 1-2：普通休息结算（无事发生）
格 3：AI Osiris 触发——同伴营地对话
    "审判骑士在篝火旁坐下，欲言又止地看着你..."
格 4-7：普通休息结算
格 8：AI Osiris 触发——夜间事件检定
    遭遇检定 → 可能有夜袭、也可能平安无事
    次日 05:00，HP/资源全恢复
```

## 五、架构原则（从 BG3 演化中提炼）

### P1. 因果链完整且不跳步

```
数据(❶) → 规则(❷) → 状态(❸) → 行为(❹) / AI Osiris(⊕) → 叙事(❺) → 表现(❻)
```

每一层只依赖下层，不跳层调用。叙事层永远不直接修改规则层的数据。

### P2. 先执行后展示

引擎算完、状态已写入，然后 GM 才叙述。GM 叙述的是**已发生的事实**，不决定事实。

### P3. 状态是唯一真理来源

WorldGraph 是唯一写入点。NPC 上下文窗口是缓存，记忆图谱是持久化，冲突时以 WorldGraph 为准。

### P4. 机械确定性 + 叙事概率性 = 分层隔离

- ❶❷❸❹ 保持 100% 确定性（和 BG3 完全一样）
- ❺ 和 ⊕ 是概率性的（AI 生成），但 ⊕ 的输出必须经 ❷ 验证后才能写入 ❸
- AI 不能"幻觉"出一个机械事实——**这是最关键的架构约束**

### P5. 规则引擎无状态 → 可假执行

❷ 不持有状态，只做纯计算。战斗 AI 用它假执行评估效用，AI Osiris 的指令也经它验证。

### P6. AI Osiris 只判不执行，格级结算

AI Osiris 输出结构化指令，引擎负责执行。AI Osiris **永远不直接写 ❸**。每时间格结算一次，批量处理，不存在链式递归问题。

### P7. 按钮优先，文字仅用于说话

能做成按钮的操作就做成按钮，消除歧义。文字通道只用于对话。但保留文字自由输入能力——这是 AI-CRPG 的差异化卖点。

### P8. 即时响应 vs 结算后果 = 两层分离

格内的场景直接反应（NPC 当场回应）走即时层；跨系统的涟漪后果（阵营变化、任务推进）走格结算层。两层职责不混淆。
