## 一、遭遇生成激活（P3 §七.P3）

- **EncounterHandler 已完整实现**：encounter_check / generate_loot / clear_hostile 三个 command

### 1.2 实际 gap

| Gap | 说明 |
|-----|------|
| **默认 detector 是 no-op** | deps.py 或 runtime.py 需要将 BasicEncounterDetector 设为默认 |

| **TimeSlice.get_period_info() 未被 detector 调用** | BasicEncounterDetector 内部有 period_multiplier 映射，但不通过 get_period_info() |

### 1.3 施工方案

#### Phase 1: 激活 BasicEncounterDetector

在 `runtime.py` 或 `deps.py` 中将 EncounterHook 的 detector 从 NullEncounterDetector 改为 BasicEncounterDetector。

**变更**：deps.py 或 runtime.py 初始化代码（1 行改动）。

#### Phase 2: 数据补全

为关键区域补充 encounter_table。优先级：
1. ancient_ruins — 已有 ✅
2. abandoned_mine、goblin_nest、dark_forest — 战斗区域优先
3. 其余区域按 base_danger > 0 筛选

**变更**：data/goblin_slayer/v2/maps.json（数据工作）。

#### Phase 3: get_period_info() 消费（可选）

BasicEncounterDetector 内部已有 period_multiplier 映射（dawn=0.8, day=0.5, dusk=1.0, night=1.5）。
TimeSlice.get_period_info() 返回同样的数据但包含 danger_factor/business_state/npc_activity。

两种方式：
- A. 保持 detector 内部映射（当前状态，简洁）

**推荐 A**：detector 是可注入组件，内部映射更自洽。get_period_info() 留给其他消费者（如 NpcScheduleHook）。

### 1.4 复杂度

## 二、熟练度系统实装（P3 §七.P4）

### 2.1 现状

```python
# proficiency.py — 三个 always-True 占位
def check_weapon_proficiency(class_template, weapon_data) -> bool:
    return True  # TODO

def check_armor_proficiency(class_template, armor_data) -> bool:
    return True  # TODO

def check_save_proficiency(class_template, save_type) -> bool:
    return True  # TODO
```

数据完全就绪：
- ClassTemplate: `weapon_proficiency=["simple","martial"]`, `armor_proficiency=["light","medium","heavy","shield"]`, `save_proficiency=["str","con"]`
- WeaponData: `proficiency="simple"/"martial"`
- ArmorData: `armor_type="light"/"medium"/"heavy"/"shield"`

### 2.2 施工方案

#### Phase 1: 三个函数真实实装

```python
def check_weapon_proficiency(class_template, weapon_data) -> bool:
    prof = getattr(weapon_data, "proficiency", "")
    if not prof:
        return True  # 无 proficiency 要求的武器（如拳头）
    return prof in getattr(class_template, "weapon_proficiency", [])

def check_armor_proficiency(class_template, armor_data) -> bool:
    armor_type = getattr(armor_data, "armor_type", "")
    if not armor_type:
        return True
    return armor_type in getattr(class_template, "armor_proficiency", [])

def check_save_proficiency(class_template, save_type) -> bool:
    if not save_type:
        return True
    return save_type in getattr(class_template, "save_proficiency", [])
```

#### Phase 2: 消费端接入

**2a. CombatHandler 攻击骰**

当前 combat.py:583-585：
```python
strength_mod = state.player.get_modifier("str")
prof = state.player.proficiency_bonus
attack_total = roll_result + strength_mod + prof
```

改为：
```python
strength_mod = state.player.get_modifier("str")
prof = state.player.proficiency_bonus
# 武器熟练度检查：不熟练时不加 proficiency bonus
weapon = _get_equipped_weapon(state, world)  # 需要获取当前装备武器
if weapon and not check_weapon_proficiency(class_template, weapon.weapon_data):
    prof = 0
attack_total = roll_result + strength_mod + prof
```

**问题**：当前 CombatHandler 的攻击流程不读取玩家装备的武器。`_get_equipped_weapon` 需要实现。

**简化方案**：当前 MVP 阶段，武器信息在 cmd.params 中。如果 cmd.params 没有武器 ID，跳过检查（向后兼容）。完整装备系统实现后再接入。

**2b. SkillCheckHandler 豁免骰**

当前 skill_check.py:212-213：
```python
if ability in getattr(state.player, "save_proficiencies", []):
    modifier += state.player.proficiency_bonus
```

这里已经有熟练度加成逻辑！但使用的是 `state.player.save_proficiencies`（PlayerSlice 字段），不是 `check_save_proficiency()`。

**选择**：
- A. 保持现状（PlayerSlice.save_proficiencies 已在角色创建时从 ClassTemplate 复制）
- B. 改用 check_save_proficiency(class_template, ability)

**推荐 A**：当前实现已经正确工作（save_proficiencies 在创建时就从 ClassTemplate 初始化）。check_save_proficiency 可作为验证工具使用，不必替换现有流程。

### 2.3 复杂度

**Phase 1**：极小（3 个函数各 3 行）。
**Phase 2a**：中（需要解决"如何获取当前武器"问题。MVP 可推迟到装备系统完善后）。
**Phase 2b**：无需改动（已有等效实现）。

### 2.4 数据验证

## 三、Lore scope 过滤 + WorldRule 消费（P3 §七.P7）

### 3.1 现状

**已有 API（未被调用）：**
- `lore.get_by_tag(tag)` — 按 tag 过滤
- `lore.list_rules()` — 列出所有 WorldRule
- `lore.list_rules_by_scope(scope, scope_id)` — 按 scope 过滤 + 按 priority 排序
- `lore.get_rules_for_context(chapter_id, area_id, faction_ids)` — 合并 global + 相关 scope 的规则

**当前消费方式：**
- ContextAssembler L0: `lore.list_all()` 全量灌入，无过滤
- AI Osiris Hook: 提取 lore 传给 evaluator，但 evaluator 不消费

**数据现状（5 条 lore + 3 条 rule）：**
- 3 条 lore 有 scope（1 global, 1 faction, 1 area）
- 3 条 rule 有 priority 排序（3/4/5）

### 3.2 施工方案

#### Phase 1: L0 scope 过滤

在 ContextAssembler `_build_world_constants()` 中，将 `lore.list_all()` 替换为按当前上下文过滤：

```python
# 旧：全量
lore_entries = world.lore.list_all()

# 新：按上下文过滤
current_area = state.player.current_area if state.has_slice("player") else None
global_lore = [e for e in world.lore.list_all() if e.scope == "global" or not e.scope]
area_lore = [e for e in world.lore.list_all() if e.scope == "area" and e.scope_id == current_area] if current_area else []
lore_entries = global_lore + area_lore
```

**变更**：context_assembler.py（~5 行改动）。

#### Phase 2: WorldRule 注入 AI Osiris

AI Osiris Hook `_build_rules_context()` 已提取 faction behavioral_rules，但未提取 WorldRule。

新增：
```python
# 在 _build_rules_context() 中
if world.has_registry("lore"):
    current_area = state.player.current_area if state.has_slice("player") else None
    rules = world.lore.get_rules_for_context(area_id=current_area or "")
    context["world_rules"] = [
        {"id": r.id, "title": r.title, "description": r.description}
        for r in rules
    ]
```

**变更**：ai_osiris.py `_build_rules_context()`（~5 行新增）。

#### Phase 3: WorldRule 注入 NPC/GM prompt（可选，依赖 P2 对话优化）

在 context_builder.py 的 L0/L2 层中注入当前适用的 WorldRule，让 NPC 和 GM 能参考世界规则回复。

这与 P2（对话体验优化）的 prompt 丰富化有重叠，可合并施工。

### 3.3 复杂度

**Phase 1**：极小（5 行改动）。
**Phase 2**：极小（5 行新增）。
**Phase 3**：小，但依赖其他任务。
