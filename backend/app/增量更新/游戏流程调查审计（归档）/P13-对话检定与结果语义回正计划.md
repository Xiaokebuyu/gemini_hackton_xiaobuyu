# P13 对话检定与结果语义回正

日期：2026-03-08

## 1. 背景

实机游玩暴露了两个耦合问题：

1. GM 生成的带检定对话选项，被错误地下发为 `dispatch.kind="action"`，点击后走 `/action/stream`
2. `success` 同时承担“命令执行是否成功”和“检定/对抗是否成功”的语义，导致 Stage B、SSE、前端提示都容易误判

它们叠加后的直接表现是：

- 玩家点了 `[说服 DC14] ...`
- 系统确实掷了骰
- 但 NPC 没有把它当成“你刚刚对我说的话”，而是把它当成旁观到的一个普通动作
- failed check 还会被 `success=True` 掩盖成“执行成功”，只把真实输赢藏在 `metadata.passed`

## 2. 本轮回正内容

### 2.1 对话检定回到 `interact` 主链

- `dialogue_options` 中的 `NPC 定向 + 带 check + 有 player_message` 选项，统一下发为：
  - `dispatch.kind = "interact"`
  - payload = `InteractRequest`
  - 保留 `message + check_skill + check_dc`
- `/interact/stream` 保持现有职责：
  - 先执行 `skill_check`
  - 发出标准 `dice_roll`
  - 再把 `player_message + check_result` 送入完整 NPC 对话编排

这样 checked dialogue 不再退化成裸 `skill_check` action。

### 2.2 结果契约拆分为 `executed + outcome`

- 新增显式 `executed`
- 新增标准化 `outcome`

当前 `outcome` 结构：

```json
{
  "category": "check | contest | binary_action",
  "passed": true,
  "winner": "actor",
  "margin": 2
}
```

说明：

- `executed` 用于判断命令是否成功进入规则执行并产出结果
- `outcome` 用于判断领域层面的成败/胜负
- 编排层、SSE、前端都应优先消费这两个字段，不再把 failed check 当成 execution failure
- 2026-03-08 追加：后续 P14 已完成硬切，旧 `success` 兼容字段已从运行时代码和公共契约中移除

### 2.3 旧 handler 结果的中心化归一化

为避免漏改，本轮不是逐个业务点手搓 if/else，而是增加了统一结果语义归一化层：

- 兼容已有 `metadata.passed`
- 兼容已有 `metadata.winner`
- 兼容 `enter_hostile` 这类旧式 `metadata.success`

因此现有 outcome 型 handler 即使暂时还保留 legacy metadata，也会统一得到：

- `metadata["executed"]`
- `metadata["outcome"]`

## 3. 代码落点

主要改动落在以下层次：

1. 结果语义归一化
   - `app/game_core/result_semantics.py`
   - `ExecuteResult / PipelineResult` 自动补齐 `executed + outcome`

2. 对话选项分发
   - `app/agent_orchestration.py`
   - checked NPC dialogue option 改为 `interact` dispatch
   - opening 场景下可推断单一 NPC 时，同样保留对话语义

3. SSE / 路由
   - `app/routers/gameplay.py`
   - `action_result` 改为 `executed + outcome`
   - `dice_roll` 增加 `passed`
   - `/interact/stream` 的 `check_result` 改读标准化 outcome

4. 前端消费
   - `frontend/src/hooks/useGameStream.ts`
   - `frontend/src/types/sse.ts`
   - 前端不再只用 `success` 判断是否该弹“操作成功”
   - failed check 不再误报成系统错误，也不再误给 success toast

## 5. 设计文档冲突与陈旧项

这次调查同时暴露出几类文档问题，需要单独收口，否则后续实现很容易再次漂移。

### 5.1 真冲突：关系阶段质变由谁负责

- `❺ NPC与队友运行时规范` 前段仍写：
  - `RelationStageChecker` “由 ❷ RulesEngine 在相关事件后调用”
- 但同一文档后段又写：
  - 当前实现由 `RelationshipHook` 负责，并在 hostile/enemy 时自动触发 `force_leave_companion`

这不是单纯措辞差异，而是“责任归属”写成了两套。

### 5.2 跨文档不一致：`publish_bulletin` 的真实状态落点

- `叙事规划子系统设计规范（粗读）` 仍写：
  - `publish_bulletin -> NarrativePlanSlice.active_bulletins`
- `NarrativePlanner设计规范（已读）` 则写：
  - `publish_bulletin -> 更新公告板状态（AreaSlice）`

说明不同文档没有统一到同一个真相源。

### 5.3 文档陈旧：输入主链与对话主链表述混杂

- 较新的文档已写清：
  - NPC 定向对话 / 对话检定走 `/interact/stream`
  - 结构化动作走 `/action/stream`
- 但旧图和旧表里仍残留 `/input/stream` 作为主要对话入口的描述

这类不是“顶层设计冲突”，但会直接误导实现。

### 5.4 受控例外总表失真

- 顶层原则一直稳定：
  - 业务状态变更应走 `Command -> RulesEngine -> StateDelta`
- 但“哪些地方允许绕行”在总表中长期落后于真实实现
- 这会让开发者误以为某些旁路仍是合法设计，实际却只是历史残留

## 6. 当前剩余边界

这次回正解决的是：

- checked NPC dialogue 主链错误
- `success` 语义混用
- Stage B / SSE / 前端消费错位

暂未顺带重做：

- 更复杂的 DC 计算模型（场景证据 / NPC 性格 / 关系细粒度）
- 更细的设计文档统一修订（尤其是 `publish_bulletin`、关系跃迁责任点、旧 `/input/stream` 图示）

也就是说：主语义已经回正；P14 又进一步完成了 `success` 的全量硬切。当前剩余的主要不是运行时代码，而是文档统一和更细的规则建模。
