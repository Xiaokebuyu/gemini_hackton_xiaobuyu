### 2.4 对话路径现状

当前 4 条对话路径：

| 前端入口 | scope | 后端路径 | 管线 |
|---------|-------|---------|------|
| 场景中点"与xx对话"按钮 | public | `/interact/stream` → `run_npc_interaction()` | 6 步（NPC+GM+队友） |
| 对话中输入框打字（有 activeNpc） | public | `/interact/stream` → `run_npc_interaction()` | 6 步 |
| NPC 邀请弹窗→接受→输入框打字 | private | `/private_chat/stream` → `run_private_chat()` | 4 步（仅 NPC） |

## 三、升级设计决策

### 3.1 Planner 子系统化

**目标**：Planner 从单体 LLM 调用升级为 AI 游戏设计师系统，包含 6 个专职子系统。

**总调度**：规则分发（事件类型 → 对应子系统），不用 LLM 判断。

| 子系统 | 职责 | 触发时机 | Skills 范围 |
|--------|------|---------|------------|
| QuestManager | 任务生命周期（创建/更新面板/退役） | milestone 完成、玩家接取任务、定期检查 | quests/* |
| NpcDirector | NPC 行为编排（指令下发、对话钩子） | 场景变化、任务状态变更 | npcs/*, social/* |
| WorldBuilder | 世界填充（区域/环境/遭遇/战斗地图选择） | 玩家进入新区域、世界空旷时 | areas/*, environments/*, encounters/* |
| PacingController | 节奏控制（升级/降温/冻结） | 定期（每 N tick） | 无需 skill，规则驱动 |
| NarrativeWeaver | 叙事编织（里程碑推进、世界事件） | 关键节点完成、长期停滞 | narrative/* |
| ItemDesigner | 物品设计（武器/防具/消耗品/任务物品） | 商店刷新、任务奖励、特殊场景 | items/* |

**子系统间通信**：
- 可互相调用（如 QuestManager 创建任务后调 NpcDirector 通知柜台小姐）
- 每个子系统有**忙碌标志**，被调用时如果忙碌则请求入队
- 执行完毕后消费队列
- **禁止环形调用**（A→B→A），队列深度设上限

### 3.2 Planner 设计 Skills 体系

**方案**：多轮 Agent（方案 B），通过 `read_design_skill(category, name)` 工具按需读取设计模板文件。

**审计注（2026-03-10）**：
- **完成度判断**：基础设施已完成，完整落地约 **85%**
- **已确认完成**：
  - 多轮 Agent 主链路已接入 `AgenticNarrativePlanner`
  - `read_design_skill` / `list_design_skills` 工具已实现并注入 QuestManager / NpcDirector / WorldBuilder / NarrativeWeaver / ItemDesigner
  - `LocalDesignSkillProvider` 已可从 `data/{world_id}/planner_skills/` 读取模板
  - 当前仓库实际已有 **8 大类 54 个 skill 文件**（不是文中写的 7 类 47 个）
- **已确认边界/剩余缺口**：
  - 当前工具签名为 `read_design_skill(category, name)`，skill 选择已显式区分类别与名称
  - `items/*.md` 已能被 `ItemDesigner` 在 planner 运行时消费，但当前仍只覆盖“已有 item_id 的最小奖励/库存规划”，未扩展到自动生成新物品模板

**架构变化**：
```
当前：NarrativePlannerHook → planner.plan(context) → 单次 LLM → JSON 输出
升级：NarrativePlannerHook → 子系统 → 多轮 Agent：
  轮1: LLM 分析当前状态，决定需要设计什么
  轮2: 调 read_design_skill("quests", "hunt") 读取任务模板
  轮3: 调 read_design_skill("encounters", "goblin_encounter") 读取遭遇模板
  轮N: 输出最终 directives JSON
```

### 3.5 NPC 职责约束

**审计注（2026-03-10）**：
- **完成度判断**：约 **90%**
- **已确认完成**：
  - `context_builder` 在构建 NPC system prompt 时，已经会基于 NPC `tags` 提取职责型真理源数据并注入约束 block
  - `receptionist` 已落地：真理源来自公告板任务 + 玩家进行中任务，约束重点是不得编造不存在的任务
  - `merchant` 已落地：真理源来自 `shop_state.current_stock`，约束重点是不得编造库存和价格
  - `temple_keeper` 已落地：真理源来自 `priestess.shop.services` + 玩家 `hp/max_hp/gold/active_effects`，约束重点是不得编造服务、价格与疗效
  - `guard` 已落地：真理源来自 NPC 驻守区域、`AreaSlice.danger_level`、区域相关 `pending_events` 与按前缀过滤的通行/戒严 flags
  - 当前世界数据中已有 4 类真实 tag 样本：`guild_girl=receptionist`、`blacksmith=merchant`、`priestess=temple_keeper`、`town_guard=guard`
- **部分完成 / 未完成**：
  - 当前 `temple_keeper / guard` 仍是“truth-source + prompt 约束”层完成，还没有继续往专用交互命令或规则处理器深化
  - v2 世界中 `temple_keeper / guard` 目前各只有最小真实样本，后续主要是数据扩充而非架构缺口
- **验证情况**：
  - `tests/test_35_npc_role_constraints.py`、`tests/test_game_data_loader_v2.py`、`tests/test_36_shop_activation.py`、`tests/test_role_tool_registry.py` 当前通过（`64 passed`）

NPC 分两类，约束策略不同：

**职责型 NPC**（按 tag 通用化）：

| tag | 职责 | 真理源 | 约束规则 |
|-----|------|--------|---------|
| receptionist | 任务发布/查询/接取/报告 | board_bulletins + 玩家已接任务 | 不得编造不存在的任务 |
| merchant | 商品买卖/推荐/报价 | shop_state（库存+价格） | 不得编造库存中没有的商品 |
| temple_keeper | 治疗服务/祝福/捐赠 | `shop.services` + 玩家状态 | 不得编造服务、价格、疗效 |
| guard | 区域安全信息/通行许可 | 驻守区域 danger + pending events + filtered flags | 不得编造封锁、搜查、许可要求 |

实现方式：context_builder 构建 NPC prompt 时，根据 NPC 的 tag 注入对应数据 + 约束规则到 system prompt。

**角色型 NPC**（队友/冒险者）：
- 不加职责约束
- 靠 character profile（personality、dialogue_style、appearance）保证人设一致性
- LLM 根据人设自由发挥

### 3.7 伙伴过往背景

**决策**：不做完整伙伴剧情线（性价比不高），改为每个伙伴加一个过往背景，在合适时机自然流露。

**实现方式**：characters.json 角色模板增加 `backstory` 字段：

```json
{
  "id": "priestess",
  "backstory": {
    "summary": "初出茅庐时队伍全灭，只有她被哥布林杀手救下，从此跟随他冒险。",
    "triggers": ["ancient_ruins", "goblin"],
    "tone": "创伤但已释怀，偶尔流露感伤"
  }
}
```

- `triggers` 标记什么场景/话题会让角色提及过往
- context_builder 根据当前场景匹配 triggers，把 backstory 注入 prompt
- 零新系统，纯数据 + prompt 注入

## 四、战斗系统升级：战旗化（SRPG）

### 4.1 核心设计参数

| 参数 | 决策 |
|------|------|
| 网格类型 | 正方格 |
| 回合结构 | 按速度交替行动（非阵营分相） |
| 规则体系 | 沿用 D&D 5e（命中/伤害/AC） |
| 单位规模 | 最大 3v5（含玩家） |
| 战斗节奏 | 高攻低防，3-5 轮结束 |

### 4.2 单位 AI 分层

| 单位类型 | AI 方式 | 每轮 LLM 调用 |
|---------|---------|--------------|
| 玩家 | 手动操控（选移动位置 + 选行动 + 选目标） | 0 |
| 队友 | LLM（性格 + 关系驱动） | 1 per 队友 |
| 普通怪 | 规则 AI（A* 寻路 + 地形加权 + 打最优目标） | 0 |
| 精英/BOSS | LLM（战术决策） | 1 |

典型一轮：2-3 次 flash 调用。

**LLM AI 行动输出格式**：
```json
{"unit_id": "priestess", "move_to": [3,4], "action": "skill", "skill_id": "miracle_heal", "target": "player"}
```

Prompt 注入：当前战场状态（网格 + 各单位位置/HP/状态）、角色性格和战斗风格、与玩家的关系。

**队友 AI 行为倾向**：
- 好感高 → 更积极保护/治疗玩家
- 角色性格驱动（女神官优先治疗、妖精弓手保持距离、哥布林杀手效率至上）

**规则 AI 地形利用**：
- A* 寻路的 cost 函数按地形加权
- 选位置时偏好有利地形（弓箭手找丘陵、近战找森林）
- 避开惩罚地形（绕开沼泽）

**队友倒下**：暂时退出本场战斗（非永久死亡）。

### 4.3 地形与环境规则

**地形效果**：

| 地形 | 移动消耗 | 战斗效果 |
|------|---------|---------|
| 草地 | 1 | 无 |
| 森林 | 2 | +20% 回避 |
| 山地 | 不可通行 | — |
| 丘陵 | 2 | +1 远程攻击范围 |
| 沼泽 | 3 | -2 速度 |
| 水面 | 不可通行（浅水 2） | 浅水：火焰技能无效 |
| 石地/废墟 | 1 | +1 防御 |
| 断墙 | 不可通行 | 阻挡远程攻击 |

**全局环境效果**（天气/时间段）：

| 环境 | 效果 |
|------|------|
| 夜间 | 视野-2 格，远程命中-10% |
| 雨天 | 火焰技能伤害减半，雷电技能+50% |
| 浓雾 | 远程攻击范围-1 |

### 4.5 前端渲染

**引擎**：Phaser（内置 Tilemap + 精灵动画 + 粒子系统）。

**架构**：
```
React App（探索/对话/菜单）
  ↓ 进入战斗
Phaser Canvas 接管（战斗场景）
  ├── TilemapLayer     # 网格地图 + 地形（开源瓦片素材包）
  ├── UnitTokens       # 棋子式角色（AI 生成头像裁成圆形 + 颜色底座）
  ├── UIOverlay        # 行动菜单/HP 条/伤害数字
  ├── AnimationSystem  # 补间移动/攻击冲刺/特效粒子
  └── CameraControl    # 镜头跟随当前行动单位
  ↓ 战斗结束
React App 恢复（结算画面）
```

**美术资源方案**：
- **角色**：AI 生成头像 + 棋子风格（圆形头像 + 蓝/红底座 + HP 条），零额外美术成本
- **场景地形**：开源瓦片素材包（如 LPC / OpenGameArt），风格统一质量有保障
- **特效/UI**：Phaser 内置粒子系统 + 程序化生成

**动画效果**：
- 移动：棋子在格子间平滑滑动（补间动画）
- 攻击：棋子冲向目标 → 屏幕闪白 → 伤害飘字 → 棋子弹回 + 屏幕震动
- 技能：全屏/局部粒子特效
- 被击中：闪烁/抖动
- 击杀：消散动画
- 回合切换：镜头平移到当前行动单位

可升级路径：后续有精灵图资源时直接替换棋子为精灵动画。

## 九、验收标准

1. 进入边境小镇 → 公告板上有可接取的中文任务（有标题、描述、目标、奖励）

7. 3-5 轮结束战斗 → 结算画面（战利品 + XP）
8. 返回城镇 → 商店有适合当前等级的装备
9. 里程碑条件满足 → 自动推进，GM 有叙事反馈
10. NPC 在合适场景自然提及过往背景
