# P21 运行时闭环补全执行计划

## 1. 目的

这份文档不是继续扩设计，而是把已经有雏形的 `3.1-3.6` 收口成一条稳定可玩的运行时闭环。

当前最核心的问题不是“没有系统”，而是：

- 有些系统只完成了基础设施，没有稳定进入主游戏循环
- 有些能力已经存在，但入口还停留在只读或半闭环状态
- 有些设计文档里的理想结构，当前不值得优先实现

本计划的目标是先补齐最短可玩路径，再决定是否继续做结构重构和内容扩写。

---

## 2. 当前基线

基于 `游戏流程调查审计（归档）.md` 的 2026-03-10 审计结果：

- `3.1 Planner 子系统化`：内核基本成形
  - `PlannerDispatcher` 已有分发、busy-lock、队列、环调用阻断
  - 六个子系统都已注册到运行时
- `3.2 Planner Skills`：基础设施基本完成
  - 多轮 Agent + design skill provider 已接通
  - `ItemDesigner` 已 agent 化并接入 `items` skill
- `3.3 任务数据源`：数据基础已补，但开场投递和内容规模不足
- `3.4 任务面板`：接口已在，但引导任务与更新链路不稳定
- `3.5 NPC 职责约束`：4 类职责型 NPC 已全部接通，后续仅剩内容扩充与交互深化
- `3.6 商店与物品系统`：规则链和最小 planner 闭环已通，主剩项以数据扩充为主

结论：

- 不需要先扩架构
- 需要先补“运行时主链稳定性”

---

## 3. 总体策略

### 3.1 主目标

先收口两条玩家可见主链：

1. 任务链  
   建角 → 开场引导 → 公告板 / 柜台小姐 → 接任务 → `/quests` 指引 → 完成 / 汇报

2. 商店链  
   商人展示 → 买卖 → 刷新 → 动态库存 / 任务奖励扩展

### 3.2 优先级决策

| 决策 | 结论 | 理由 |
|---|---|---|
| D1 | 先修运行时闭环，再扩内容 | 当前缺的是稳定体验，不是更多静态数据 |
| D2 | 暂不先拆 `quest_tracking` slice | 现阶段先做稳定读模型和更新链，收益更高 |
| D3 | 柜台小姐接任务/汇报与公告板共享 offer/report 语义，但走独立 receptionist commands | 保持同一任务状态机，不再让 NPC 入口退化成只读 |
| D4 | 暂不单独做 `/shop` panel | 当前 `shop_snapshot` 已足够支撑交互闭环 |
| D5 | `ItemDesigner` 先补最小可用，不先做自动写 `items.json` | 先打通奖励/库存动态闭环 |
| D6 | 角色职责约束优先补纯规则 truth-source 注入 | 成本低，收益直接，可立即提升 NPC 一致性 |

### 3.3 非目标

本轮不做：

- `3.7` 伙伴过往背景
- lorebook 自动扩写 `items.json`
- 大规模章节内容扩展
- 完整独立商店前端面板
- 彻底重做 Planner 总架构

## 4. 分阶段执行

### Phase 0：建立稳定基线

目标：

- 把当前“什么是真正阻塞主链”的回归项固定成测试基线

动作：

- 复核并记录以下关键测试
  - 建角后开场任务是否稳定出现
  - `/quests` 是否稳定出现引导任务
  - 公告板是否稳定有条目
  - 柜台小姐是否能读到 board + active quest
  - 商店 browse / buy / sell / refresh 是否保持通过

验收：

- 有一组可以反复跑的最小回归集合
- 失败项和对应链路明确，不再靠人工记忆判断

---

### Phase 1：开场 bootstrap 稳定化

目标：

- 保证建角后“引导任务 + 公告板任务 + `/quests` 面板”确定性出现

重点问题：

- 当前建角后的 opening/bootstrap 存在不稳定
- 任务面板测试已暴露 `dynamic_quests` 为空的问题
- 公告板相关链路也有同类不稳定表现

可能涉及文件：

- `app/game_core/runtime.py`
- `app/game_core/orchestration/hooks/narrative_planner.py`
- `app/game_core/planning/semantic_events.py`
- `app/routers/panels.py`
- `tests/test_api_shell.py`

具体任务：

- 梳理建角后 opening/bootstrap 的触发顺序
- 确认 bootstrap seed event 是否稳定进入 planner
- 确认 directive 应用时机早于 `/quests` 与公告板读取
- 为“建角后立即读取 `/quests` 与公告板”的路径补充确定性保障

验收：

- 建角后读取 `/quests` 可稳定看到引导任务
- 建角后进入公告板可稳定看到初始委托
- 相关 API shell 测试稳定通过

---

### Phase 2：柜台小姐任务入口写通

目标：

- 柜台小姐不再只是“只读查询 NPC”，而成为真正的任务接取 / 汇报入口

现状：

- `receptionist` 的 truth-source 已注入 prompt
- 当前已存在 `receptionist_accept_quest / receptionist_report_quest` 独立写路径
- `accept_quest` 仍以当前区域公告板是否 offer 该任务为前置条件，`report_quest` 只处理“已完成且需汇报”的确认语义

策略：

- 不新开独立 quest 状态机
- 由交互层新增 receptionist 语义入口
- 与公告板共享同一 offer / report 语义，不并行造第二套 quest 状态写路径

可能涉及文件：

- `app/interaction_service.py`
- `app/interaction_views.py`
- `app/game_core/adapters/inbound.py`
- `app/game_core/rules/handlers/board.py`
- 相关交互测试

具体任务：

- 为柜台小姐增加 `accept_quest / report_quest` 交互归一语义
- 在交互视图中暴露可接取 / 可汇报任务线索
- 将 receptionist 入口映射为真实状态写路径
- 保证对话入口与公告板入口对同一任务状态结果一致

验收：

- 玩家可通过柜台小姐接取任务
- 玩家可通过柜台小姐报告任务
- 同一任务在柜台入口与公告板入口状态一致

## 5. 推荐执行顺序

严格按下面顺序推进：

1. Phase 0：固定回归基线
2. Phase 1：开场 bootstrap 稳定化
3. Phase 2：柜台小姐任务入口写通
4. Phase 3：任务面板稳定更新
5. Phase 4：职责型 NPC 补齐
6. Phase 5：ItemDesigner 最小闭环

理由：

- Phase 1-3 会直接提升任务主链可玩性
- Phase 4 成本低，能快速提升 NPC 表现一致性
- Phase 5 依赖前面运行时链稳定后再做，风险更低

---

## 6. 验收口径

当以下条件同时满足，才算“运行时闭环补全完成第一阶段”：

1. 建角后，初始引导任务稳定出现
2. 公告板任务可稳定浏览和接取
3. 柜台小姐可稳定执行任务查询、接取、汇报
4. `/quests` 能稳定显示执行中任务指引
5. 商店 browse / buy / sell / daily refresh 保持通过
6. `temple_keeper / guard` 职责约束补齐
7. `ItemDesigner` 至少能处理一种奖励设计和一种库存调整事件

## 7. 当前第一工作包

### WP1：开场引导与任务入口稳定化

范围：

- Phase 1
- Phase 2 的最小可用版本
- 必要时带上 Phase 3 的局部收口

完整目标：

- `G1` 开场 bootstrap 确定性
  - 修掉“建角后没有任务 / 没有公告板条目 / `/quests` 为空”的不稳定问题
  - 保证建角完成后，不依赖额外手动触发，也能稳定进入 opening/bootstrap 结果态
- `G2` 初始任务投递一致性
  - 保证初始引导任务、公告板任务、`/quests` 面板三者读取到的是同一批运行时结果
  - 保证玩家在建角后立刻访问 `/quests`、公告板、柜台小姐时，看到的不是三套互相漂移的数据
- `G3` 柜台小姐任务入口写通
  - 柜台小姐不再只是任务查询入口
  - 至少支持“接取任务”的真实写路径
  - 如果当前任务状态链允许，顺带补齐“汇报任务”最小闭环
- `G4` 任务面板最小可用
  - active 动态任务在 `/quests` 中可稳定显示
  - 至少具备 `status / title / summary / current_step / next_steps / hints` 这类执行期指引字段中的最小有效集

本工作包完成定义：

- 建角后立即读取 `/quests`，能稳定看到引导任务或至少一条 active 动态任务
- 建角后立即浏览公告板，能稳定看到初始委托条目
- 玩家可通过柜台小姐完成至少一次“接任务”动作，并写入真实任务状态
- 柜台入口接取后的结果，和公告板入口读取到的任务状态保持一致
- 不允许出现“公告板有任务但 `/quests` 空”“柜台小姐能说有任务但实际无法接取”这类显式漂移

本工作包不要求：

- 先落地独立 `quest_tracking` slice

## 8. 执行备注

这轮执行优先保证：

- 主链稳定
- 状态写路径统一
- 回归测试可重复

而不是优先保证：

- 文档中的理想数据形态
- 一次性把所有模块都做满
- 大规模内容扩展

后续实际编码以本计划为准；如果实现中发现更低成本的收口方式，可以调整实现细节，但不能反转本计划的优先级。
