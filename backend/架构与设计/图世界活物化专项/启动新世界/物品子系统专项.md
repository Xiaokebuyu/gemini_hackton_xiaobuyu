## 一、系统总览

物品子系统是一组**独立但协作的子系统链**，构成游戏经济和角色装配的底层基础设施。每个子系统有明确的职责边界和接口，任何上层系统（商店、战斗、任务、制作）都通过这些接口消费物品能力。

### 1.1 生产者/消费者链

```
┌──────────────────────────────────────────────────────────────────┐
│ 上层消费方                                                        │
│   商店系统 · 战斗掉落 · 任务奖励 · GM 工具 · 制作系统(未来)          │
├──────────────────────────────────────────────────────────────────┤
│ D. 物品效果引擎     使用消耗品 → 状态变化（HP/状态/增益）            │
│      ↑ 消费 B（移除已用物品）                                      │
├──────────────────────────────────────────────────────────────────┤
│ C. 装备系统         穿戴/卸下 → 属性重算（AC/攻击/伤害）            │
│      ↑↓ 与 B 双向（装备从背包取出，卸下放回背包）                    │
├──────────────────────────────────────────────────────────────────┤
│ B. 背包系统         持有层 — 增删查改玩家持有的物品                   │
│      ↑ 消费 A（物品定义 + 堆叠规则）                                │
├──────────────────────────────────────────────────────────────────┤
│ A. 物品注册表       定义层 — 世界中存在哪些物品，只读                 │
│      数据源: items.json                                           │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 三层架构对齐

每个子系统都遵循三层架构：

| 子系统 | 底层引擎（纯机械） | 中层（SessionRuntime） | 顶层（REST API / 工具） |
|--------|-------------------|----------------------|----------------------|
| A. 物品注册表 | ItemRegistry | — | GET .../items/* |
| B. 背包 | PlayerCharacter.inventory 方法 | session.add_item/remove_item | GET/POST .../inventory/* |
| C. 装备 | EquipEngine + AC 重算 | session.equip/unequip | GET/POST .../equipment/* |
| D. 物品效果 | ItemEffectEngine | session.use_item | POST .../inventory/use |

**附属模块**：
- **价格解析器**：将 items.json 中的价格字符串（"30 sp"）转为数值，归属 A（物品数据处理）
- **金币系统**：StatsManager.add_gold/remove_gold，归属独立的 StatsManager（已完成）

### 价格解析器

物品价格在 items.json 中是字符串，需解析为数值（sp 单位）。

**价格格式统计**：

| 格式 | 示例 | 出现次数 |
|------|------|----------|
| `N sp` | "10 sp", "30 sp" | 31 |
| `N gp` | "25 gp" | 1 |
| `N+ gp` | "500+ gp" | 1 |
| `0` | "0" | 2 |
| `varies` | "varies" | 1 |
| 特殊 | "1 sp (6 pcs)" | 1 |

**汇率表**（D2 决策：自由币种 + 汇率映射）：

```python
CURRENCY_RATES = {
    "cp": 0.1,    # 1 cp = 0.1 sp
    "sp": 1.0,    # 基准单位
    "gp": 10.0,   # 1 gp = 10 sp
    "pp": 100.0,  # 1 pp = 100 sp
}
```

**接口**：

```python
def parse_price(price_str: str) -> Optional[int]
    # "30 sp" → 30, "25 gp" → 250, "500+ gp" → 5000
    # "varies" / None / 无法解析 → None
```

## 七、桥接层 — 与现有系统对接

基础层（A-D）让物品系统自身能运转。桥接层将物品系统与已有的战斗、角色、状态系统连通。

### E. 状态系统 (Conditions)

**现状**：PlayerCharacter 已有 `conditions: List[Dict]` 字段（`player_character.py:70`），用于 `to_summary_text()` 显示，但**无人读写**——没有添加/移除/查询状态的方法。

**为什么需要**：物品效果（解毒剂移除"中毒"、增益药水添加临时 buff）需要一个状态系统才能生效。战斗系统的 StatusEffect 是战斗内的，与 PlayerCharacter.conditions（持久状态）是两套。

**需要的接口**：

```python
# 底层（PlayerCharacter 或 stats_manager）
def add_condition(player, condition: Dict) -> Dict
    # condition: {name: "poisoned", source: "goblin_attack", duration?: 3}
    # 返回: {added, condition}

def remove_condition(player, condition_name: str) -> Dict
    # 按名称移除
    # 返回: {removed, was_present}

def has_condition(player, condition_name: str) -> bool

# 中层（SessionRuntime）
def add_condition(name, source, duration?) -> Dict
def remove_condition(name) -> Dict
def get_conditions() -> List[Dict]
```

**消费方**：
- 物品效果系统（D）的 "cure" 类型 → `remove_condition("poisoned")`
- 物品效果系统（D）的 "buff" 类型 → `add_condition({name: "strength_boost", bonus: 2, duration: 10})`
- 战斗结算 → 战后持久状态转写到 PlayerCharacter.conditions
- GM Agent → 叙事施加状态（被诅咒、中毒等）
- REST API → `GET .../conditions`（前端角色面板显示）

### F. 战斗掉落桥接 (Loot Bridge)

**现状**：
- `combat_engine._calculate_rewards()` 有 `items: list[str] = []` 和 `# TODO: 物品掉落逻辑`（`combat_engine.py:1369,1391`）
- `CombatRewards.items` 字段存在但始终为空
- `loot_events: []` 在 combat_mcp_server 中始终为空
- 怪物数据中 **119/124 有 loot 字段**，共 **336 种唯一掉落物名称**

**怪物 loot 数据示例**：
```json
{
  "id": "怪物生态_-_哥布林类",
  "loot": ["哥布林的耳朵", "粗制的武器", "肮脏的饰品", "兽骨法杖 (萨满)"]

```

**问题**：loot 是自然语言字符串列表，和 ItemRegistry 的 item_id 不对接。需要：
1. **掉落表 (Loot Table)**：怪物 → 可掉落物品列表 + 掉落概率
2. **名称 → item_id 映射**：或者为掉落物创建新的 ItemRegistry 条目
3. **战斗结算桥接**：`_calculate_rewards()` → `loot_table.roll()` → `CombatRewards.items`

**需要的接口**：

```python

    # 根据怪物 loot 配置随机掉落
    # 返回: [{item_id, name, quantity}]

# 桥接（战斗结算时）
rewards.items = roll_loot(template)  # 填充目前为空的 items 字段
# → SessionRuntime._apply_rewards() 已有 add_item 逻辑
```

**优先级判断**：这是让"战斗有实质收获"的关键桥接。但 336 个掉落物名称需要整理到 ItemRegistry，工作量大。可以先支持已有的 41 个物品作为掉落物，其余标记 TODO。

### G. 装备熟练度检查 (Proficiency)

**现状**：PlayerCharacter 已有字段（`player_character.py:56-57`）：
```python
weapon_proficiencies: List[str]   # e.g. ["simple", "martial"]
armor_proficiencies: List[str]    # e.g. ["light", "medium", "shield"]
```
但装备时**不检查熟练度**。D&D 规则：穿戴不熟练的护甲有惩罚（攻击/施法劣势），使用不熟练的武器无法加熟练加值。

**需要的接口**：

```python
# 底层（equip_engine）
def check_proficiency(player, item_info: Dict) -> Dict
    # item subtype ("light"/"medium"/"heavy") vs player.armor_proficiencies
    # 返回: {proficient: bool, penalties: [...]}
```

**影响**：装备时不阻止，但返回警告。属性重算时应用/不应用熟练加值。战斗系统的 `to_combat_player_state()` 已读取装备数据，需考虑熟练度。

**优先级**：中等。不影响核心流程，但对 D&D 体验重要。

## 八、丰富层 — 后续增强

这些系统不阻塞商店和基础物品功能，但能显著提升 CRPG 体验。

### H. 耐久/修理系统 (Durability)

**线索**：maps.json 铁匠的 `available_actions` 已有"修理装备"，裁缝有"修补皮甲"——世界设定已经预期了这个系统。

**设计思路**：
- 物品条目增加 `durability: {current: 50, max: 50}` 字段
- 战斗中受击/使用武器时消耗耐久
- 耐久归零 → 装备"损坏"（属性减半或失效）
- 修理 → 商人服务（消耗金币）或修理工具（自助）

**依赖**：背包系统（B）+ 装备系统（C）+ 商店系统的"服务"端点

### I. 负重系统 (Encumbrance)

**线索**：items.json 每个物品有 `properties.weight` 字段（"light"/"heavy"），当前未使用。

**设计思路**：
- D&D 简化负重：力量值 × 15 = 最大负重（磅）
- 超重 → 移动速度降低 / 无法拾取
- 或更简单：slot 数上限（如 20 格背包）

**依赖**：背包系统（B）+ 物品注册表（A）的 weight 数据

### J. 掉落表体系 (Loot Tables)

**线索**：monsters.json 119 个怪物有 loot，336 个唯一掉落物名称。

**设计思路**：
- 结构化 loot_table.json：`怪物类型 → [{item_id, drop_rate, min_qty, max_qty}]`
- 与 ItemRegistry 对接：掉落物必须有对应的 item_id
- 分级掉落：普通怪/精英/Boss 不同掉落池
- 当前 336 个字符串需清洗/映射到 ItemRegistry（管线工作）

**依赖**：物品注册表（A）+ 战斗掉落桥接（F）+ 管线修复

### K. 物品分级机制 (Item Quality)

**线索**：items.json 有 `rarity` 字段（common/rare），但目前不影响任何机制。

**设计思路**：
- rarity 影响：掉落概率、商店出现概率、售价倍率
- 后续可加：品质前缀（精良的/大师级的）、随机属性

## 十、实施方案

### 总览

```
Phase I: 基础层
  I-1: 物品注册表修复 + 价格解析器
  I-2: 背包 REST API + remove_gold
  I-3: 装备系统完善 + REST API
  I-4: 物品效果最小集 + use_item

Phase II: 桥接层
  II-1: 状态系统（E）— conditions CRUD
  II-2: 战斗掉落桥接（F）— _calculate_rewards 填充
  II-3: 装备熟练度（G）— proficiency 检查

  III-4: 物品分级（K）
```
