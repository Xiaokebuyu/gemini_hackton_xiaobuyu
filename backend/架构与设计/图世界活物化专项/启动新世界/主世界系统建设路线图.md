## 四、Part C — 任务池驱动的主线系统 ⏸️ 挂起

> 最大的架构变更。概念设计完成，需细化后实施。

### C1: 设计哲学

**当前线性系统的问题**:
- 8 个事件按顺序触发，像在走剧本
- 玩家自由度受限：必须按事件顺序推进
- NPC 是被动的：等事件触发才有台词
- GM 负担重：既要推进剧情又要叙述
- 偏离了 Direction A "呈现而非推进" 的原则

**任务池的核心理念**:
- 主线不是一条线，是一个**场**
- NPC 感知到主线的"压力"，自主产出任务
- 玩家通过完成任务推进完成度，**选哪些任务、什么顺序，完全自由**
- 达到里程碑阈值 → **关键剧情节点**自动触发
- GM 只负责呈现世界的变化和氛围

### C2: 概念模型

```
StorylineArc（主线弧）
  ├─ id: "arc_goblin_crisis"
  ├─ name: "哥布林危机"
  ├─ description: "边境哥布林活动日益猖獗..."
  ├─ completion: 0/100
  ├─ milestones:
  │    ├─ 25%: "线索浮现"  → 触发关键剧情
  │    ├─ 50%: "深入调查"  → 触发关键剧情
  │    ├─ 75%: "决战前夜"  → 触发关键剧情
  │    └─ 100%: "危机解除" → 触发章节转换
  └─ context_tags: ["goblin", "frontier", "danger", "guild"]

Quest（任务）
  ├─ id: "quest_goblin_patrol_01"
  ├─ source_npc: "guild_girl"          ← 发布者
  ├─ arc_id: "arc_goblin_crisis"       ← 所属主线弧
  ├─ completion_value: 15              ← 完成贡献
  ├─ description: "最近西部牧场遭到哥布林袭击..."
  ├─ requirements: {min_level: 1}
  ├─ rewards: {gold: 50, xp: 100, items: ["healing_potion"]}
  ├─ status: available | accepted | completed | failed | expired
  └─ generated_by: "npc_agent"         ← LLM 生成标记
```

### C3: NPC 作为任务源

```
NPC Agent 感知：
  1. 当前 StorylineArc 的上下文 + 完成度
  2. 自己的角色定位（occupation, personality, motivation）
  3. 当前区域的状态（时间、最近事件、其他任务）

NPC Agent 输出：
  → guild_girl 发布正式公告类任务
  → goblin_slayer 发布高难度清巢任务
  → priestess 发布护送/治疗类任务

触发时机：
  → 玩家进入 NPC 所在子地点时
  → 定期刷新（game_time 推进时）
  → 主线完成度变化时
```

### D1: 商店 = NPC 对话的购买模式（AD9）

**设计理念**：商店不是独立系统，而是 NPC 交互的一种模式。玩家点击铁匠 → 发起对话 → NPC Agent 识别购买意图 → 展示货架 → 执行交易。

```
玩家: "我想买把好点的剑"
forge_master (NPC Agent):
  → 感知：自己是铁匠，当前在铁匠铺，inventory 有 [longsword, short_sword, ...]
  → 回复："好眼光！我这里有两把不错的——精钢长剑(50gp)和矮人短剑(35gp)。你看看？"
  → 调用工具：show_shop_inventory(npc_id="forge_master", category="weapon")

玩家: "我要那把长剑"
forge_master:
  → 调用工具：sell_item(item_id="longsword", price=50, buyer="player")
  → 引擎执行：player.gold -= 50, player.add_item("longsword")
  → 回复："成交！这把精钢长剑可是我的得意之作，好好使。"
```

```python
# buy_item: 玩家从商人处购买（商人 NPC 调用）
@immersive_tool(roles={"merchant"}, desc="Sell an item from your shop to the customer")
async def sell_to_customer(ctx: AgenticContext, item_id: str, quantity: int = 1) -> Dict:
    """
    1. 检查：玩家是否在商店子地点？商店是否营业？
    2. 检查：ItemRegistry 中是否有此物品？
    3. 检查：玩家金币是否足够？
    4. 执行：session.remove_gold(price * quantity) + session.add_item(item_id)
    5. 返回：交易结果
    """

# sell_item: 玩家向商人出售
@immersive_tool(roles={"merchant"}, desc="Buy an item from the customer")
async def buy_from_customer(ctx: AgenticContext, item_id: str, quantity: int = 1) -> Dict:
    """
    1. 检查：玩家背包中是否有此物品？
    2. 计算：售价 = 原价 * sell_ratio（默认 0.5）
    3. 执行：session.remove_item(item_id) + session.add_gold(sell_price)
    4. 返回：交易结果
```

### F1: 升级机制（AD11）

当前 `StatsManager.add_xp()` 检查 XP 阈值并自动升级，但升级时**只加 level + proficiency_bonus**，不更新其他属性。

**需要实现的升级效果**：

```python
def level_up(player: PlayerCharacter):
    player.level += 1
    player.proficiency_bonus = 2 + (player.level - 1) // 4  # D&D 5e 标准

    # HP 增长 = hit_die_avg + CON_mod
    hit_die = CLASS_HIT_DIE[player.character_class]  # fighter:d10, mage:d6...
    hp_gain = hit_die_avg(hit_die) + player.ability_modifier("con")
    player.max_hp += hp_gain
    player.current_hp += hp_gain  # 升级时回满

    # 法术位增长（施法职业）
    if player.character_class in SPELLCASTER_CLASSES:
        player.spell_slots = SPELL_SLOTS_BY_LEVEL[player.level]

    # 每 4 级属性提升（4/8/12/16/19）
    if player.level in [4, 8, 12, 16, 19]:
        # 标记待分配：引擎通知前端选择 +2/+1+1 属性提升
        player.pending_asi = True
```

## 十b、World 初始化管线现状（2026-02-22 审计）

> 代码位置：`app/tools/worldbook_graphizer/`（统一管线）+ `app/tools/init_world_cli.py`（CLI）
> 数据样本：`data/goblin_slayer/structured_new/`（哥布林杀手世界）

### 10b.1 管线流程

```
Lorebook JSON
  ↓ TavernCardParser
WorldbookEntry 列表
  ↓ Markdown 格式化（8000 char/条上限）
  ↓
┌──────────────────────────────────────┐
│ Step 3a: MapExtractor (LLM)          │  → maps.json（7 地图 × 子地点/NPC/连接）
│ Step 3b: GraphExtractor (LLM+Batch)  │  → world_graph.json（1453 节点 × 2412 边）
│ Step 4:  NPCClassifier (LLM)         │  → characters.json（131 角色: 7 main + 124 secondary）
│ Step 4b: ReconcileCharacters         │  → 回填图谱中遗漏的角色
│ Step 5:  WorldMapGenerator (规则)     │  → world_map.json
│ Step 6:  CharacterProfiles (规则)     │  → character_profiles.json
└──────────────────────────────────────┘
  ↓ 保存中间文件
  ↓
GraphPrefiller → prefilled_graph.json（1264 节点 × 1974 边，v2 MemoryNode/Edge schema）
  ↓ [可选] --relabel-edges → 边类型重标注（270 unknown → 0）
  ↓ [可选] --enrich-entities → D&D 实体提取（monsters/items/skills）
  ↓
init_world_cli load → Firestore → WorldInstance 缓存
```

双执行模式：Batch API（50% 成本优惠，需等待队列）或 `--direct`（实时 LLM，无等待）。

### 10b.2 输出质量评估

**做得好的**：
- 角色画像丰富：主角 16/16 字段完整（personality/backstory/relationships/speech_pattern/example_dialogue）
- 地图结构完整：子地点含 interaction_type(shop/rest/quest/visit)、resident_npcs、passerby_spawn_rate
- 知识图谱覆盖广：8 种节点类型（character/concept/deity/faction/race/monster/item/location）
- 叙事指令全覆盖：82 章 × 323 事件均有 narrative_directive

**关键缺口**：

| # | 问题 | 严重度 | 影响范围 | 阻塞子系统 |
|---|------|--------|----------|-----------|
| P1 | **82 章全部缺失 `available_areas`**（空数组） | 🔴 阻塞 | 运行时无法知道每章开放哪些地图 | Part C 任务池 |
| P2 | **323 事件全部缺失 `activation_type`** | 🟠 高 | 无法区分自动/NPC发布/探索/事件驱动 | Part C 任务池 |
| P3 | **路人层 0 个角色**（只有模板，无个体） | 🟡 中 | 7 main + 124 secondary + 0 passerby | Part B NPC 列表 |
| P4 | **D&D 实体偏少**（41 怪物 / 7 物品 / 19 技能） | 🟡 中 | 关键词匹配不足，遗漏大量实体 | Part E 物品系统 |
| P5 | **不支持增量更新**（改一个角色需全量重跑） | 🔵 低 | 迭代效率低 | — |
| P6 | **提示模板无版本控制 + 输出无 schema 校验** | 🔵 低 | LLM 输出格式变化无感知 | — |

### 10b.3 优先级判定：子系统优先，管线后补

P1/P2 是管线最严重的问题，但仅影响**章节切换 + 事件触发**，属于 Part C（任务池）的前置依赖。当前子系统建设（Part D 商店、Part E 物品、Part F 角色成长）不依赖这两个字段。

**实施顺序**：先完成 Phase 2-4 子系统建设 → 再修复管线 P1-P4 → 最后建设 Part C 任务池。管线修复自然成为任务池的前置准备工作。
