## 架构边界（P23 §1.1 摘录，本轮所有修复必须遵守）

> 来自 `P23-二次审计与实施偏差清单.md §1.1`。P21 以后所有修复的硬性约束。

| # | 规则 | 说明 |
|---|------|------|
| ❶ | **内容层只读** | Registry / JSON 只提供静态模板与查询 API。运行时不得回写 registry、world data 或 JSON 文件 |
| ❷ | **状态变更走主路径** | 新修复必须经 `Command → Handler → StateDelta`。Hook 只能产出 directive、构造 command、调用 `context.execute_command()`，**不能直接 mutate 持久 slice** |
| ❸ | **状态层唯一真理源** | 动态任务、库存、NPC 指令等运行时状态必须落在对应 slice；不得在应用层、prompt 缓存、前端读模型中并行维护第二套真理源 |
| ❹ | **编排层薄编排** | Hook / Coordinator 只负责"何时调用谁"。奖励发放、任务完成判定、战斗计算仍属规则 / Handler 主链 |
| ❺ | **Planner 只规划不执行** | 负责"现在应该引导什么"，不负责因果推理、任务状态机、奖励数值计算、GM 叙述 |
| ❻ | **directive 受 contract 约束** | 所有 directive 先过 `directive_contracts.py` 最小 contract，再由 subsystem / `planner_*` handler 落地 |
| ❼ | **Agent 声明意图不执行结果** | LLM 可选择投递方式、读取 design skills，但不能自行认定"任务已完成""奖励已发""商店已刷新" |
| ❽ | **切片归属不改写** | 任务→QuestSlice、规划→NarrativePlanSlice、商店→RelationSlice、地点→AreaSlice |

**允许**：补 command、补 handler、补 context、补 prompt、补 validator、补 trigger、补读模型。

**不允许**：在 hook / 应用层直写状态、补旁路缓存、把内容层当运行时 DB、让 LLM 直接承担规则执行。

### 4-1. 战斗掉落处理 ✅ DONE (P28 Wave 2 Track A)

**文件**：`app/game_core/rules/handlers/combat.py`

**现状**：怪物模板有 `loot_table` 和 `gold_drop` 字段，combat handler 只读 `xp_reward`。

**怪物数据结构**（monsters.json）：
```json
{
    "loot_table": [
        {"item_id": "cheap_shortsword", "chance": 0.3, "count": "1"},
        {"item_id": "healing_potion", "chance": 0.05, "count": "1"}
    ],
    "gold_drop": "1d4"
}
```

**修复**：在 `_compute_combat_xp()` 旁新增 `_compute_combat_loot(participants, world)`：

```python
def _compute_combat_loot(
    self,
    participants: list[dict[str, Any]],
    world: WorldInstance,
) -> tuple[list[tuple[str, int]], int]:
    """Roll loot_table + gold_drop for killed monsters."""
    items: list[tuple[str, int]] = []
    gold_total = 0
    for p in participants:
        if p.get("alive") or p.get("fled"):
            continue
        monster_id = str(p.get("monster_id", ""))
        template = world.monsters.get(monster_id)
        if template is None:
            continue
        for entry in getattr(template, "loot_table", None) or []:
            chance = float(entry.get("chance", 0))
            if random.random() < chance:
                item_id = str(entry.get("item_id", ""))
                count = max(1, int(entry.get("count", 1)))
                if item_id:
                    items.append((item_id, count))
        gold_expr = getattr(template, "gold_drop", None)
        if gold_expr:
            gold_total += max(0, roll_damage_dice(str(gold_expr)))
    return items, gold_total
```

**调用位置**：`combat_cleared == True` 后（与 `_compute_combat_xp` 同处）。

**StateChange 生成**：
- 物品：构建 new_inventory 列表（合并现有 + 掉落），`StateChange("player", "set", "inventory", new_inventory)`
- 金币：`StateChange("player", "set", "gold", current_gold + gold_total)`
- 参照 `board.py:_build_reward_changes()` 的 inventory 构建模式

**metadata 追加**：`loot_items: [{item_id, count}]`, `gold_dropped: int`

**前提**：确认 `MonsterTemplate` 已有 `loot_table`/`gold_drop` 字段。如果没有，在 monsters registry 的 template dataclass 中补字段 + 加载逻辑。

**预估**：~60 行

### 4-2. 升级 SSE 通知 + ASI 引导 ✅ DONE (P28 Wave 2 Track A)

**问题**：
1. 战斗 XP 用 raw `StateChange("player", "set", "xp", ...)` 绕过 `add_xp()` 的自动升级
2. 升级后无 SSE 事件通知前端
3. ASI 可用时玩家无提示

**修复方案：XP 推进 Hook**

**文件（新建）**：`app/game_core/orchestration/hooks/xp_advancement.py`

```python
class XpAdvancementHook(NoOpSettlementHook):
    """检查 XP 阈值，自动触发 level_up + SSE 通知。"""
    HOOK_PRIORITY = 58  # 在战斗/任务结算后

    async def execute(self, context: SettlementContext) -> None:
        player = context.state.player
        threshold = player.level * 1000  # 与 GrowthHandler 一致
        if player.xp < threshold:
            return
        result = await context.execute_command(
            Command("level_up", "player", {})
        )
        if result.executed:
            meta = result.metadata or {}

            }))
```

## 6. P28-B: Task Monitor（任务完成监测器）

### 设计理念

让 Planner 为动态任务注册完成条件，复用 EventEngine 的条件评估体系（`BasicEventConditionEvaluator._condition_met()`），使动态任务也能像 Milestone 一样自动判定完成。

### 6-1. Planner directive

新增 directive kind **`set_task_monitor`**（由 QuestManager subsystem 处理）：

```json
{
    "kind": "set_task_monitor",
    "payload": {
        "quest_id": "dq_goblin_patrol",
        "conditions": [
            {"type": "kill_count", "params": {"monster_type": "goblin", "count": 3}},
            {"type": "location_visited", "params": {"area_id": "ancient_ruins"}}
        ],
        "on_complete": "auto"
    }
}
```

**`on_complete`** 选项：
- `"auto"` — 条件全满足时自动完成任务（调用 board_complete_quest 命令）
- `"notify"` — 条件全满足时通知 Planner（发 SSE + 写入 planner replay trace），由 Planner 决定下一步

### 6-2. 数据存储

**文件**：`app/game_core/state/slices/quests.py` — `QuestSlice`

动态任务的 payload dict 新增可选 key：
```python
{
    "quest_id": "dq_goblin_patrol",
    "title": "哥布林巡逻清扫",
    "status": "active",
    # ... 现有字段 ...
    "task_monitor": {  # 新增，可选
        "conditions": [...],
        "on_complete": "auto"
    }
}
```

不新建 slice，直接写入 quest payload。与现有 `board_complete_quest` 逻辑共存。

### 6-3. 评估 Hook

**文件（新建）**：`app/game_core/orchestration/hooks/task_monitor.py`

```python
class TaskMonitorHook(NoOpSettlementHook):
    """评估动态任务的 task_monitor 条件，自动完成或通知。"""
    HOOK_PRIORITY = 56  # 在 MilestoneCompletionHook(54) 之后
```

逻辑：
1. 遍历所有 `status == "active"` 的动态任务
2. 如果有 `task_monitor` 字段 → 提取 conditions
3. 用 `BasicEventConditionEvaluator._condition_met()` 逐条评估
4. 全部满足：
   - `on_complete == "auto"` → 执行 `board_complete_quest` 命令
   - `on_complete == "notify"` → 发 SSE `task_monitor_triggered` + 写入 planner trace

### 6-4. directive_contracts 验证

- `quest_id` 必须非空、对应的动态任务必须存在且 status == "active"
- `conditions` 必须是非空 list，每条含 `type` 和 `params`
- `on_complete` 必须是 `"auto"` 或 `"notify"`

### 6-5. Planner prompt 指导

```

为动态任务注册自动完成条件。条件类型与里程碑 success_conditions 相同：
- npc_talked: {"npc_id": "xxx"} — 玩家与指定 NPC 对话过
- kill_count: {"monster_type": "xxx", "count": N} — 击杀指定怪物 N 只
- location_visited: {"area_id": "xxx"} — 玩家到达指定区域
- item_obtained: {"item_id": "xxx"} — 玩家持有指定物品
- flag_set: {"flag": "xxx", "value": true} — 指定 flag 被设置

示例：巡逻任务需要击杀 3 只哥布林并返回公会报告
→ set_task_monitor(quest_id="dq_xxx", conditions=[
    {"type": "kill_count", "params": {"monster_type": "goblin", "count": 3}},
    {"type": "npc_talked", "params": {"npc_id": "guild_girl"}}
  ], on_complete="auto")
```

## 13. 架构合规性声明

本方案所有设计遵守 P23 §1.1 架构边界：

| 规则 | P28 合规性 |
|------|-----------|
| ❶ 内容层只读 | ✓ 不写 registry/JSON，CapabilityDescriptor 是运行时状态 |
| ❸ 状态层唯一真理源 | ✓ 能力存 NarrativePlanSlice，监测条件存 QuestSlice payload |
| 变更走 Command 链 | ✓ NpcDirector 用 execute_command，TaskMonitor 用 execute_command("board_complete_quest") |
| 编排层薄编排 | ✓ TaskMonitorHook 只做"检查条件→调命令"，不含业务逻辑 |

| directive 受 contract 约束 | ✓ assign_capability/set_task_monitor 都过 directive_contracts 验证 |
| 切片归属不变 | ✓ 能力→NarrativePlanSlice（规划态）、任务→QuestSlice、商店→RelationSlice |
| 战斗掉落在规则层 | ✓ CombatHandler 中处理，通过 StateChange 更新 inventory/gold |

| 里程碑奖励走 Command | ✓ Hook 调 execute_command 发放，不直接 mutate slice |

## 14. 待讨论设计决策

### D1: Functional option 点击后的交互流

玩家点击含 `functional` 的选项（如"购买补给品"）时，行为如何？

- **方案 A（确定性）**：前端直接打开交易面板，同时发 message 给 NPC 保持叙事。好处：100% 可靠，不依赖 LLM。坏处：略微机械，跳过了 NPC 回应。
- **方案 B（叙事优先）**：先发 message 给 NPC，NPC 用 offer_trade 工具回应 → 前端从工具响应中提取 shop 数据 → 自动打开交易面板。好处：自然、有 NPC 对话感。坏处：依赖 LLM 正确调用工具，可能失败。
- **方案 C（混合）**：发 message 给 NPC + 前端预加载交易面板（但不显示）。NPC 回应后显示面板；如果 NPC 超时或未调用工具，前端 fallback 强制打开。

**倾向**：C 最稳。需要确认。

### D2: Capability 与现有静态 Tool 的关系

Planner assign 的动态能力 vs `RoleToolRegistry` 的静态工具，两者什么关系？

- **方案 A（并行）**：两套独立。静态工具照常按 trait 分配，动态能力额外注入 prompt。NPC 同时看到两者。
- **方案 B（替代）**：动态能力可以覆盖/扩展静态工具。如果 Planner assign 了 `trade_browse` 能力，NPC 不再需要 `merchant` tag 也能展示商品。

**倾向**：A。静态工具是硬编码的功能（有真实代码执行），动态能力是行为指导（prompt 注入）。两者层级不同，不应互相替代。

### D3: Task Monitor 条件中的 quest_id 校验时机

`set_task_monitor` directive 中的 `quest_id` 应该在哪一步校验"必须存在且 active"？

- **方案 A（directive_contracts）**：合约层校验。但合约层没有 QuestSlice 访问权。
- **方案 B（subsystem apply）**：QuestManager 的 `_apply_set_task_monitor()` 校验。合约层只检查格式。

**倾向**：B。与现有模式一致（合约检格式，subsystem 检语义）。

### D4: 越界修复的通用 Flag Handler

V4/V5 的 FlagSlice 冷却写入 — 新建 `set_internal_flag` 通用 Handler 还是为每种用途建专用 Handler？

- **方案 A（通用）**：一个 `set_internal_flag` Handler，任何 Hook 都能设置任意 flag。灵活但失去语义约束。
- **方案 B（专用）**：`set_cooldown_flag` Handler，只处理冷却场景，校验 key 格式和 value 类型。

**倾向**：A。FlagSlice 本身就是 schemaless 的 `dict[str, Any]`，加专用 handler 是过度设计。但需要在 handler 中限制来源（只允许 internal/hook 调用，不允许外部玩家命令）。

### D5: 战斗掉落物品如何添加到背包

战斗掉落物品通过 StateChange 追加到 `player.inventory`。

- **方案 A（批量 set）**：构建完整 new_inventory 列表（合并现有 + 新物品），一次 `StateChange("player", "set", "inventory", new_inventory)`。简单，payload 稍大。
- **方案 B（逐条 add）**：每个物品一个 `StateChange("player", "add", "inventory.{item_id}", count)`。需要 PlayerSlice 支持 `add` 操作的 inventory 路径。

**决定**：B。扩展性更好（背包容量限制、选择性拾取）。给 PlayerSlice 的 `apply_state_change` 加 `"add_inventory_item"` 路径：找到同 item_id 的 stack 就 +count，没有就新建 ItemStack。~15 行。

### D6: 升级触发机制

战斗 XP 用 raw `StateChange("player", "set", "xp", ...)` 绕过了 `add_xp()` 的自动升级。如何补上升级检查？

- **方案 A（Hook）**：新建 `XpAdvancementHook`（priority 58），每 tick 检查 `xp >= threshold` → `execute_command("level_up")`。干净，遵循架构。
- **方案 B（改 combat）**：combat handler 改为调用 `execute_command("add_xp")`。但 command 嵌套 command 不常见且可能有副作用。
- **方案 C（改 PlayerSlice）**：`apply_state_change("xp", ...)` 自动检查升级。但状态层不应含业务逻辑。

**决定**：A。与 MilestoneCompletionHook 模式一致——Hook 做"检查 + 调命令"，不含规则逻辑。
