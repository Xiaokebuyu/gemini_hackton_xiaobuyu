# P6: 对话总线与角色记忆架构回正计划

> 状态：已完成（Phase 1-5 已落地）
> 创建：2026-03-05
> 目的：把当前“可运行的对话功能集合”回正到设计规范中的统一运行时模型
> 关联设计文档：编排层设计规范 / 叙事层设计规范 / ❺ NPC与队友运行时规范 / 状态层设计规范

---

## 一、当前偏差结论

本轮对齐审查后，当前实现与规范的偏差不是单点问题，而是四条链路同时存在语义偏移：

| 偏差点 | 当前状态 | 设计要求 |
|------|---------|---------|
| 对话是否进入格生命周期 | `/interact/stream` 与 `/private_chat/stream` 直接走 app layer agent orchestration，不走 `TickCoordinator` | 对话应累加 `time_cost`、触发 settlement、统一持久化 |
| SceneBus 私聊可见性 | 玩家发言是 private，但 NPC 工具写出的内容默认 public | 私聊整段内容都应是 `visibility="private"`，只对 player + 目标 NPC 可见 |
| 角色自有记忆 | `remember` 仍写入 `RelationSlice.npc_impressions`；`WorldKnowledgeGraph` 是全局共享图 | NPC 长期记忆应是角色私有的 MemoryGraph，`npc_impressions` 只承担关系/UI 摘要 |
| InstanceManager 语义 | 当前只是 `ContextWindow` LRU 缓存 | 应管理 `NPCInstance`，包含工作记忆、长期记忆、directive queue、生命周期 |
| 多 Agent 协作 | 只在 NPC interaction/private chat 路径局部存在 | 规范要求统一 SceneBus 总线，GM/NPC/队友在同一总线上按顺序协作 |
| 可见性过滤真相源 | `ContextBuilder` / `ContextAssembler` / `SceneSlice` 各自有一套过滤逻辑 | 应收口为一套统一规则，避免 private/system 语义漂移 |

---

## 二、整改原则

1. **先闭环生命周期，再深化认知架构**
   对话先回到 `TickCoordinator` 与 SceneBus 生命周期中，再改 MemoryGraph 和 NPCInstance。否则后续所有“记忆”“私聊”“冷却”“日程”都会漂浮在格系统之外。

2. **先收口可见性，再扩展能力**
   private/public/system 的语义必须先统一，否则“多 Agent 协作”会建立在错误上下文上。

3. **关系摘要与角色记忆彻底分流**
   `npc_impressions` 继续服务关系系统/UI；角色记忆进入独立 MemoryGraph 路径，避免继续混用。

4. **分阶段可验收**
   每一阶段都必须有明确验收标准和可跑的回归测试，避免再次出现“表面修复，语义没对齐”。

5. **优先兼容现有前端协议**
   SSE 事件名和前端已消费的载荷形状尽量保持稳定；内部链路回正优先，前端协议只在必要时调整。

## Phase 1: 对话生命周期闭环 + SceneBus 可见性收口

### 目标

把 `/interact/stream` 和 `/private_chat/stream` 从“直接调 agent”改回“进入格生命周期的独立对话管线”，同时修复 private 对话在 SceneBus 上泄漏的问题。

### 本阶段必须完成

1. `interact/private_chat` 触发 `time_cost=1/6`
2. 对话后执行 settlement 检查
3. `SceneBusResetHook` 能对纯对话回合生效
4. 私聊全链路都遵循 `visibility="private"` + 精确 audience
5. SceneBus 可见性过滤逻辑收口为单一真相源

### 重点改动

| 模块 | 改动 |
|------|------|
| `routers/gameplay.py` | 路由不再只做“interaction + app layer agent”，而是回到 coordinator 生命周期 |
| `agent_orchestration.py` | 从“直接驱动完整对话生命周期”收窄为“对话 agent 执行器 + SSE 转换器” |
| `tick_coordinator.py` 或新 coordinator 适配层 | 为 `interact/private_chat` 补上 `accumulate/check_settlement/export_dirty` 链路 |
| `private_chat.py` | 私聊 NPC 输出必须带 private audience |
| `character_tools.py` | `speak/emote/refuse/...` 支持从上下文传入 visibility/audience，不再一律 public |
| `scene.py` / `scene_bus.py` / `context_builder.py` / `context_assembler.py` | 抽取统一过滤逻辑，消除重复实现 |

### 验收标准

1. 连续进行 6 次对话后，time slice 正常结算
2. 私聊中产生的 NPC 文本不会被 GM/队友/其他 NPC 看见
3. `npc_wants_to_chat` 的冷却、日程推进、结算 hook 对纯对话路径生效
4. 现有前端 `talk_snapshot` / `dialogue_options` / `location_overview` 不回归

### 预估规模

- 文件数：8 到 12
- 代码量：约 400 到 800 行
- 复杂度：中

## Phase 2: NPCInstance 化 + Directive 热注入修正

### 目标

把 `InstanceManager` 从“ContextWindow 缓存”升级成真正的 `NPCInstance` 管理器，补齐 directive 生命周期和活跃实例热注入。

### 本阶段必须完成

1. 引入 `NPCInstance`
2. `InstanceManager.get_or_create()` 返回 `NPCInstance`
3. `directive_queue` 从 `ContextWindow` 外移到 `NPCInstance`
4. `direct_npc` 对已活跃实例即时生效，不必等实例重建
5. LRU 淘汰前执行强制 graphize/writeback

### 重点改动

| 模块 | 改动 |
|------|------|
| `narrative/instance_manager.py` | 从 `OrderedDict[str, ContextWindow]` 升级为 `OrderedDict[str, NPCInstance]` |
| `narrative/context_window.py` | 保持工作记忆职责，移除不该停留在这里的实例级语义 |
| `orchestration/hooks/narrative_planner.py` | `direct_npc` 下发时同时尝试热注入活跃实例 |
| `state/slices/narrative_plan.py` | directive 生命周期清理与状态写回保持一致 |
| `agent_orchestration.py` / `npc_interaction.py` / `private_chat.py` | 使用 `instance.context_window`、`instance.consume_directive()` |

### 验收标准

1. 对某 NPC 下发 `direct_npc` 后，若该 NPC 已活跃，下一次交互立即能消费 directive
2. 实例池满时淘汰旧实例会触发 graphize/writeback，而不是静默丢弃
3. directive 不会永久堆积，也不会因实例已存在而失效

### 预估规模

- 文件数：6 到 10
- 代码量：约 300 到 700 行
- 复杂度：中高

## Phase 3: 角色私有 MemoryGraph 落地

### 目标

把“角色记忆”从当前的全局 WorldKnowledgeGraph 混用状态中拆出来，形成“世界知识图 + 角色私有记忆图”的双通道。

### 本阶段必须完成

1. `remember` 不再写 `RelationSlice.npc_impressions`
2. `write_episode(actor_id, ...)` 写入 actor-specific memory store
3. `query_spread(actor_id, ...)` 能读取“世界静态知识 + 该角色动态记忆”
4. `npc_impressions` 只保留关系摘要职责
5. 为后续“主观记忆”保留扩展点

### 设计决策

- **世界图**：继续承担静态世界知识、Lore、Registry 关系
- **角色图**：单独存储 NPC/队友自己的互动记忆
- **检索层**：在 `MemoryRetriever` 内合并两类 hits，再注入 L6
- **关系摘要**：仍保留在 `RelationSlice.npc_impressions`，但不再作为 `remember` 的落点

### 重点改动

| 模块 | 改动 |
|------|------|
| `world_knowledge_graph.py` | 拆成 world graph 与 actor memory overlay，或抽出 actor graph store |
| `memory_retriever_impl.py` | 合并 world hits + actor hits |
| `character_tools.py` | `remember` 改成写角色私有记忆端口 |
| `adapters/memory_graph_port.py` | 明确区分 actor memory 的读写边界 |
| `rules/handlers/world_state.py` | `add_knowledge` 继续只服务 `npc_impressions`，不再承担角色长期记忆 |

### 验收标准

1. NPC 的 `remember` 结果不会污染其他角色的检索结果
2. 两个不同 NPC 围绕同一话题检索到的动态记忆可以不同
3. `npc_impressions` UI/关系判断仍正常工作

### 预估规模

- 文件数：8 到 12
- 代码量：约 500 到 900 行
- 复杂度：高

## Phase 4: 主流程多 Agent 总线协作回正

### 目标

把“总线中的多 Agent 协作”从局部对话管线，扩展回规范中的统一运行时：GM、NPC、队友在主流程中共享 SceneBus，并按固定顺序协作。

### 本阶段必须完成

1. 主流程具备可注册的 Agent pipeline hooks
2. `GM -> NPC -> 队友` 顺序在主流程中可执行
3. 每个 Agent 能看到前序 Agent 写入的 SceneBus 内容
4. L6 不再只在 interaction 路径存在，主流程 agent 也能走统一记忆注入

### 重点改动

| 模块 | 改动 |
|------|------|
| `orchestration/pipeline.py` | 补足真正的 after_engine / after_agents 协作链路 |
| `orchestration/defaults.py` | 注册默认 agent hooks |
| `orchestration/context_assembler.py` | 移除 L6 stub-only 状态，接入真实 role context 组装 |
| `narrative/context_builder.py` | 与 ContextAssembler 的职责边界重新划定，避免双份上下文模型 |

### 验收标准

1. 主流程动作后，GM/NPC/队友的协作不再只存在于 interaction 特化路径
2. SceneBus 中新增内容按顺序对后续 Agent 可见
3. 现有 settlement hook 与 agent pipeline 不重复消费、不双写

### 预估规模

- 文件数：6 到 10
- 代码量：约 400 到 800 行
- 复杂度：高

## 五、本轮实施建议

下一轮直接落地 **Phase 1**，原因如下：

1. 这是当前所有偏差的上游
2. 风险最高，且回报最大
3. 不先修这个，后面所有关于记忆/总线/私聊/冷却/日程的行为都不可信

**Phase 1 完成后，预期系统状态：**

- 对话重新成为“格内动作”
- SceneBus 生命周期重新成立
- 私聊真正成为 private
- 后续 `NPCInstance` 与角色私有记忆改造可以在正确运行时之上继续推进

---

## 六、暂不纳入 Phase 1 的内容

以下内容故意后置，不在第一阶段内混做：

1. 完整主流程 GM/NPC/队友总线协作
2. 主观记忆图谱化（同一事件多角色不同版本）
3. MemoryGraph 持久化目录结构与外部存储适配
4. 更复杂的私聊叙事增强（romance 精细表现、营火衍生）
5. 前端对新 memory/agent 语义的额外展示

---

## 七、风险提示

1. `interact/private_chat` 一旦回到 tick 生命周期，可能暴露此前被掩盖的时间结算 bug
2. private/public 语义收口后，部分现有 prompt 行为可能变化，因为 agent 真正看不到不该看到的内容了
3. `remember` 脱离 `npc_impressions` 后，若 UI 或关系逻辑偷用了这条路径，会暴露隐性耦合
4. `NPCInstance` 改造会碰到 app layer 与 game_core 的边界，需要控制好依赖方向

---

## 八、完成定义

当以下条件全部满足时，可认为“架构回正”进入稳定阶段：

1. 对话和私聊都进入格生命周期
2. SceneBus 可见性模型只有一套实现
3. `InstanceManager` 管理的是 `NPCInstance`，不是裸 `ContextWindow`
4. `remember` 与 `write_episode` 进入角色私有记忆路径
5. 主流程和专门对话路径都建立在同一总线语义之上
