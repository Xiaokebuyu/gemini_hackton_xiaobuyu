## 1. 背景

P21 收口了运行时主链，P22 打磨了读模型和数据契约。功能表面上都"实现了"，但实际体验仍不理想。本轮审计的目标是找出**实施偏差、静默失败、未被正确使用的功能**，为二次实施提供精确清单。

审计范围：`游戏流程调查审计（归档）.md` §3.1-3.6 的所有子系统。

## 1.1 架构边界（2026-03-11 补记，本轮修复必须遵守）

本轮所有修复（含 §13 并行实施方案）必须继续服从 `app/博德之门3架构设计规范/` 的分层边界。并行修不等于可以越层修；任何“快修”都不能把旁路重新引回系统。

- **❶ 内容层只读**：`QuestRegistry / ItemRegistry / CharacterRegistry / MapRegistry / LoreRegistry` 只提供静态模板与查询 API。运行时可以读取，但不得回写 registry、world data 或 JSON 文件；`ItemDesigner` 可以从已有 `item_id` 候选中选择，不得在运行时动态造新品模板并写回 `items.json`。
- **❸ 状态层是唯一真理源**：动态任务、商店库存、敌对子地点、NPC 指令、story_facts 等运行时现实必须落在对应 slice 中；不得在应用层、prompt 缓存、前端读模型或临时 dict 中并行维护第二套真理源。
- **所有持久状态变更走 ❷ 主路径**：新修复默认必须经过 `Command -> Handler -> StateDelta`。Planner / Agent / SettlementHook 只能产出 directive、构造 command、调用 `context.execute_command()`，不能直接 mutate 持久 slice。
- **受控例外不扩张**：当前允许的例外仅限 `SceneBus` / system entry 这类格级临时缓冲，以及规范表中已登记的编排层内部调度；它们不是持久真理源。本轮不新增新的受控例外。
- **编排层保持薄编排**：`NarrativePlannerHook`、其他 Hook 和 Coordinator 只负责“何时调用谁”。奖励发放、任务完成判定、商店刷新、战斗规则计算仍属于既有规则/事件/Handler 主链，不能为了省事塞回 hook 内。
- **NarrativePlanner 只做主动规划与投递**：它负责“现在应该引导什么”，不负责因果推理、任务状态机、任务完成判定、奖励数值计算、GM 叙述文本生成。动态任务完成仍由 `EventEngine + QuestSlice`，奖励兑现仍由对应 domain handler / command 主链负责。
- **Planner 输出必须是受约束的 directive，不是任意状态写入**：所有 directive 先过 `directive_contracts.py` 最小 contract，再由对应 subsystem / `planner_*` handler 落地；repair 方向应是补 validator、补 handler、补 trigger、补 context，而不是绕过 contract 直接改状态。
- **❺ Agent / Planner agent 只声明意图，不直接执行机械结果**：LLM 可以选择投递方式、选择 reward/shop candidates、读取 design skills，但不能自行认定“任务已完成”“奖励已发”“商店已刷新”“战斗应结束”。
- **切片归属不改写**：任务生命周期与动态任务数据继续归 `QuestSlice`，规划态/strategy/story_facts/npc_directives 归 `NarrativePlanSlice`，商店运行时库存归 `RelationSlice.shop_states`，动态地点/敌对遭遇归 `AreaSlice`。读模型可以继续打磨，但不能反客为主变成真理源。
- **允许的修法**：补 command、补 handler、补 context、补 prompt、补 validator、补 trigger、补读模型。
- **不允许的修法**：在 hook / 应用层 / 面板层偷偷直写状态、补一套旁路缓存、把静态内容层当运行时数据库、让 LLM 直接承担规则执行职责。

## 12. 跨子系统因果链分析

69 个问题分布在三大域：Planner 生态（§3.1-3.6, §五, 42 个）、战斗系统后端（§4.1-4.4, 22 个）、前端（§4.5, 5 个）。Planner 域形成 5 条因果链，战斗后端 2 条，前端 1 条独立链。逐个修不如**按因果链修**——修链头解锁整串下游。

### 链 1："什么都没发生"

```
S1-01/02/03（Planner 静默空转）
  → 无 directive 产出
    → S3-04（create_quest 后无 publish_bulletin）
    → S4-01（无 update_quest → 面板无导航）
    → S2-01/02/03（Skills 死 → agent 输出更差）
```

**根因**：Planner 输出不可靠（无 LLM / LLM 失败 / JSON 坏），下游全部饥饿。
**修复策略**：保障 Planner 至少有确定性兜底输出（无 LLM 时走规则，有 LLM 时做好错误恢复）。

### 链 2："奖励黑洞"

```
Planner create_quest
  → ItemDesigner design_reward 写入 rewards.items（S6-06 无 SSE）
    → 玩家完成任务
      → board_complete / receptionist_report 都不调 _apply_quest_rewards（S3-01 + S6-02）
        → ask_reward 展示了奖励但拿不到（S6-08）
```

**根因**：奖励发放函数 `_apply_quest_rewards()` 只在 event-driven 里程碑路径被调用，动态任务的两个完成入口都没接上。
**修复策略**：在 board_complete_quest / receptionist_report_quest 中接入奖励发放，或新增显式 `claim_reward` 命令。

### 链 3："商店冷启动"

```
shop_state lazy init（S6-01）
  → 首次 browse 空库存
    → merchant context_builder 读到空数据（S5-07）→ LLM 无库存信息
    → curate_shop 被拒（S6-03 shop 未初始化）
    → 物品只有 id 无描述（S5-08）
```

**根因**：shop 初始化发生在首次 trade_buy / refresh_shop，但多个消费者（browse、context_builder、curate_shop）在这之前就需要数据。
**修复策略**：world bootstrap 阶段预初始化所有有 `shop_inventory` 的商人 shop_state。一步解锁链上所有下游。

### 链 4："盲人 Planner"

```
context 稀疏（S1-06）→ 决策差
  → 失败但静默（S1-04/05）→ 不知道为什么失败
    → 无反馈闭环（S1-08）→ 下轮无上轮结果
      → 重复投递坏决策 → context 窗口驱逐（S1-07）→ 彻底遗忘
        → ItemDesigner 也缺 context（S6-05）
        → story_facts 写了但 NPC 不消费（S1-13）
```

**根因**：Planner 无记忆、无反馈、无学习。输出的 directive 成功还是失败，下一轮完全不知道。
**修复策略**：在 Planner context 中注入上轮 directive 执行结果摘要（最近 N 条成功/失败 + 原因）。

### 链 5："孤儿任务"

```
create_quest 不保证 publish_bulletin（S3-04）
  → 或 bulletin 引用不存在的 quest（S3-03）
    → receptionist 读到幽灵公告推荐无法接取的任务（S5-06）
      → 即使推荐成功，receptionist_accept 要求 quest 在公告板上（S3-05）
        → 无 quest discovery UI（S3-07）
```

**根因**：任务生命周期的 create→publish→discover→accept 四步之间是松散的 LLM 级联，任何一步的缺失都导致后续全断。
**修复策略**：create_quest 自动触发 publish_bulletin（原子绑定），publish_bulletin 校验 quest_id 存在。

### 链 6："战斗不可玩"（§4.2 深挖后升级为阻塞链）

```
Combat router action 名称不匹配（B2-01）→ REST API 400 错误
  + 无 combat_move / combat_end_turn 端点（B2-02）→ 玩家无法完成基本回合
    + NPC 回合无自动推进（B2-03）→ 战斗卡在 NPC 回合
      → 战斗流程完全卡死

即使流程跑通：
队友 ai_personality=None（B2-05）→ 全部 aggressive → 无性格差异
  + LLM AI 从未调用（B1-01）→ 队友无智能
    + 玩家死亡无处理（B1-02）→ 战斗永不结束
      + 队友 HP=0 无恢复（B2-06）→ 后续战斗缺人
```

**根因**：战斗核心规则（命中/伤害/AC/地形 AC+range）扎实，但**战斗流程本身无法从 API 正常驱动**——router 映射错、缺关键端点、NPC 回合不自动推进。即使绕过 API 问题，AI 层（LLM 队友从未接入、性格数据缺失）和生命周期（玩家死亡、队友恢复）也未闭合。
**修复策略**：分两阶段——(1) 先让战斗可玩：修 router 映射 + 补端点 + NPC 自动推进 + 玩家死亡检测；(2) 再让战斗有趣：接通队友 LLM AI + 性格数据 + 队友恢复。

### 链 7："地形/效果半成品"

```
Swamp speed_penalty 定义但未消费（B1-04）
浅水地形完全缺失（B3-01）→ 设计的浅水+火焰免疫无载体
火/雷天气伤害修正未实现（B1-05）
夜间视野缩减未实现（B3-02）+ 命中计算偏差（B3-03）
MonsterTemplate.preferred_terrain 死字段（B2-04）
5/10 战斗地图缺失（B1-07）→ 大量场景 fallback 到默认草地
近战不偏好森林（B1-08）+ AI 不避沼泽（B1-09）+ 目标选择无地形（B1-10）
unit_defeated SSE 信息过少（B2-07）
```

**根因**：地形系统在基础层（AC/range/move_cost/LoS）正确消费，但更高层（AI 决策、天气伤害、speed 影响、视野、地图覆盖、浅水变体）只做了定义没做消费，或根本没定义。
**修复策略**：(1) 消费已有字段（speed_penalty、preferred_terrain、天气伤害）；(2) 新增浅水地形 + 夜间视野逻辑；(3) 补地图数据。
