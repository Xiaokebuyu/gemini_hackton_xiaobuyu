# P24-兼容层与双路径残留台账

更新时间：2026-03-12

## 1. 目的

本文件专门记录当前后端仍然存在的：

- 入口兼容层
- 存档/历史数据兼容层
- 读模型兼容层
- 运行时双路径残留

它和 `P23` 的关系是：

- `P23` 继续作为“实施偏差 / 修复验收”主文档
- 本文件作为“兼容与过渡状态”台账

结论先说：

- 当前后端**没有第二套完整主链并行跑**
- 但仍有若干**局部双路径残留**和**受控兼容层**
- 核心原则已经是：`入口可兼容，执行链统一，持久化尽量只保留新格式`

## 2. 状态总览

| 类别 | 当前状态 | 说明 |
| --- | --- | --- |
| Planner directive 入口兼容 | 存在，受控 | 用于吃旧 LLM/schema 漂移，不新增第二套执行链 |
| 存档迁移兼容 | 存在，必要 | 旧 key / 旧 history shape 仍可读 |
| 读模型兼容 | 存在，部分 active | 典型是 combat `participants` 卡片视图 |
| 运行时双路径残留 | 存在，需后续收口 | `ContextWindow graphize`、opening、`/interact/stream` |
| 第二套完整后端主链 | 不存在 | 未发现任务/战斗/商店/Planner 主链双跑 |

## 3. Planner Directive 入口兼容

这部分兼容的目标是：**只在 shared validator / normalize 入口吸收旧格式；执行链、handler、落盘仍按新 contract 走。**

### 3.1 `create_quest` 旧格式兼容

当前兼容：

- `id -> quest_id`
- `description -> summary`

原因：

- 历史 planner 输出曾使用旧字段
- 如果不做入口归一，会直接触发 `missing_quest_id`

当前状态：

- 已修复
- 归一入口：`directive_contracts.py`
- 落盘仍只保留新字段

### 3.2 `publish_bulletin` 旧格式兼容

当前兼容：

- payload 根上的 `quest_id`
- 归一到 `metadata.quest_id`

原因：

- 历史 planner 输出曾把 `quest_id` 放在 payload 根
- handler/规则层已转向 `metadata.quest_id`

当前状态：

- 已修复
- 归一入口：`directive_contracts.py`
- 规则层同时校验 root / metadata，但新写入按新格式走

### 3.3 `direct_npc` 旧格式兼容

当前兼容：

- 旧格式把 `behavior/topic/goal/interactable/...` 直接挂在 payload 根
- 新格式要求：
  `{"npc_id":"...", "directive": {...}, "priority":"..."}`

当前兼容动作：

- 自动把根上的旧字段收拢进 `payload.directive`
- 若缺 `directive.kind`，自动补默认值
  - `interactable=true` → `kind="talk"`
  - 否则 → `kind="react"`

原因：

- 这是目前真实运行里最活跃的一类 contract 漂移
- 接任务后切换地点等高触发场景会连续命中
- 不兼容时会出现多条 `invalid_contract(missing_directive)` warning

当前状态：

- 已修复入口兼容
- subsystem prompt 已同步到新格式
- 执行链仍只消费 `payload.directive`

### 3.4 `plant_encounter` 旧字段兼容

当前兼容：

- `location_id -> sub_area_id`

同时补齐：

- `plant_encounter` 已正式纳入 shared directive contract

原因：

- prompt / subsystem / handler 已经支持该指令
- shared validator 曾漏登记，属于 surface 漂移
- 旧输出还可能使用 `location_id`

当前状态：

- 已修复
- 当前正确 contract 是：
  `area_id + sub_area_id + monster_ids`

### 3.5 `adjust_pacing` 的处理原则

这一项**没有**放宽兼容。

现状：

- 运行时只接受 `{"frozen": true|false}`
- 不兼容 `pacing_factor` / `slowdown` / `pace_score` 之类旧语义

处理策略：

- 不扩大 validator 兼容面
- 只在 subsystem prompt 明确约束模型输出

原因：

- 这类旧字段不是简单 schema 漂移，而是语义已经不同
- 如果把它也兼容进来，会把旧 contract 继续合法化

### 3.6 `WorldBuilder` 旧数组 payload 兼容

当前兼容：

- `fill_area` 的旧格式：
  - `payload.locations = [{id/name/description/traits...}, ...]`
  - `payload.elements = [{id/name/description...}, ...]`
- `plant_environmental` 的旧格式：
  - `payload.elements = [{id/name/description/persistence...}, ...]`

当前兼容动作：

- 在 planner directive 入口先展开为多条**规范单指令**
- 每个地点/线索各自变成一条 canonical directive
- 例如：
  - `locations[3]` → 3 条 `fill_area`
  - `elements[2]` → 2 条 `plant_environmental`

原因：

- 旧数组 payload 在之前的 contract 下会被记成 `applied`
- 但 handler 实际只消费单个 `id/label/description` 或 `clue_id/description`
- 结果是“看起来执行成功，但大部分内容静默丢失”，会生成空白动态地点/线索

当前状态：

- 已修复入口展开
- `fill_area / plant_environmental` 现在也不再接受只有 `area_id` 的空 payload
- `WorldBuilder` prompt 已明确要求：
  - 一条 directive 只创建一个地点或一个线索
  - 多个地点/线索必须拆成多条 directives
  - 不再使用 `locations / elements` 数组

### 3.7 Planner prompt contract 收紧

当前状态：

- `_SYSTEM_PROMPT` 已移除旧的 `modify_location` 指引，改为 `fill_area / plant_environmental`
- `QuestManager / WorldBuilder / ItemDesigner` prompt 已补齐当前 runtime contract 示例
- `WorldBuilder` prompt 现在明确禁止把日常 NPC 场景伪装成 `plant_encounter`

原因：

- 有些 schema 漂移并不是 handler 缺失，而是 prompt 仍在暗示旧输出
- 这类问题如果只靠 validator 兼容，会不断产生新的边缘形态

## 4. 存档与历史数据兼容

### 4.1 Planner 历史 key 兼容

当前兼容：

- `__planner__ -> __planner_blackboard__`

用途：

- 读取旧存档中的 planner history

当前状态：

- 读取兼容仍保留
- 新持久化路径应使用新 key

### 4.2 Planner / GM 旧 history shape 兼容

当前兼容：

- 旧 `{role, text}` message shape

用途：

- 旧上下文窗口数据恢复

当前状态：

- 读取兼容仍保留
- 新数据应使用当前 `ContextWindow` message 结构

### 4.3 旧坏档不会自动自愈

这一点单独记录：

- 兼容层的职责是“让新输入不再坏”
- 不是“自动修复已经写坏的旧 state”

例如：

- 某次历史 planner 因 contract 漂移没成功写入 dynamic quest
- 新兼容层不会凭空为旧存档补出那条任务

## 5. 运行时双路径残留

这部分不是“兼容单字段”，而是**系统内部仍保留两条局部路径**。

### 5.1 `ContextWindow -> graphize`

当前状态：`active dual-path`

新路径：

- `should_graphize -> collect_for_graphize()`

旧路径：

- `NpcInteractionCoordinator`
- `PrivateChatCoordinator`
- `InstanceManager eviction`
- 仍在调用 deprecated 的 `pop_oldest_for_graphize()`

风险：

- graphize 触发机制不统一
- 新旧语义混用
- 后续最值得优先收口

### 5.2 Opening 生成链

当前状态：`active hybrid`

现状：

- 先尝试 agent opening
- narration/comment/options 任一缺失时，分别回退到 deterministic `opening_views`

结果：

- 一次 opening 可能是混合产物
- 例如 agent narration + deterministic comment/options

风险：

- 表现一致性差
- 调试时不容易判断到底是哪条路径在生效

### 5.3 `/interact/stream`

当前状态：`entry-level hybrid`

现状：

- speech-like 请求优先走 `UtteranceOrchestrator`
- 同一路由内仍保留旧 `input_port -> interaction_service -> agent_svc.run_*` 分支

结论：

- 正常请求通常不会同一次双执行
- 但路由层仍是新旧混合入口

风险：

- 路由复杂度高
- 维护成本高
- 容易让将来的修复落到错误分支

## 6. 读模型兼容

### 6.1 Combat `participants` 卡片视图

当前状态：`active read-model compatibility`

执行真相：

- 战斗执行主链已经是 `grid/units/turn_order`

兼容读模型：

- router 仍从 hostile payload 里组装 `participants` 卡片
- 主要服务旧前端 / 旧展示事件

结论：

- 这不是两套战斗规则并行
- 这是新执行模型外面包了一层旧展示兼容

风险：

- 前端若长期只消费 `participants`
- 后端的空间/位置能力会继续被浪费

## 7. 非主链兼容残留

### 7.1 老的单步 NPC 接口

当前状态：

- `generate_npc_response()` 仍在
- 当前主要由测试使用

结论：

- 属于兼容残留
- 不是 live runtime 主链

### 7.2 Planner single-shot fallback

当前状态：

- `AgenticNarrativePlanner` 仍保留 single-shot `llm.generate()` fallback

结论：

- 当前 app 组装以 executor 路径为主
- 这一分支更像 fallback / 测试兼容，不是主执行链

### 7.3 World loader 双入口

当前状态：

- `v2` 与旧 loader 都还保留

结论：

- 运行时是二选一，不是双加载
- 这是数据迁移兼容，不是 live dual-path

## 8. 当前策略

当前兼容策略可以概括为三句：

- **入口兼容**：允许 shared validator 吃掉已知旧格式
- **执行统一**：dispatcher / handler / state change 只保留新主链
- **持久化收敛**：新写入尽量只保留新字段

换句话说：

- 兼容层是过渡设施
- 不是长期维护两套并行后端

## 9. 后续收口优先级

建议优先级：

1. `ContextWindow graphize` 双路径收口
2. opening agent/deterministic 混拼收口
3. `/interact/stream` 路由收口
4. 视观察结果逐步缩小 planner directive 入口兼容面

## 10. 与 P23 的边界

为了避免 `P23` 持续膨胀：

- `P23` 只保留兼容问题的摘要和当前状态
- 兼容细节、双路径残留、迁移层说明全部收拢到本文件

后续若再发现新的兼容层或双路径残留，应优先更新本文件。
