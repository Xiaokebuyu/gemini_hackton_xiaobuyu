## 一、架构总览

```
┌─────────────────────────────────────────┐
│  上层：居民（Players / Agents）          │
│  GM Agent / NPC Agent / 队友 Agent / 玩家 │
│  只看到"我能做什么"，通过沉浸式接口行动    │
├─────────────────────────────────────────┤
│  中层：世界规则接口（World API）          │
│  SessionRuntime = 唯一真理源              │
│  权限控制 / 动作验证 / 结果包装           │
├─────────────────────────────────────────┤
│  底层：游戏世界引擎（World Engine）       │
│  WorldGraph + BehaviorEngine + 导航 +     │
│  经济 + 时间 + 事件 + 战斗 + 物品 + ...  │
│  机械真理源，零 AI，纯规则/状态/计算       │
└─────────────────────────────────────────┘
```

**核心原则**：
- **底层** = Strandbeest 的机械结构（纯规则，零 AI，`app/world/` 零 LLM 依赖）
- **中层** = 机械结构暴露给外界的操作面板（SessionRuntime 统一 API）
- **上层** = 风（玩家操作 + Agent AI 决策，通过 AgenticExecutor + RoleRegistry 沉浸式工具）

### 1.2 代码组织规则

**`app/models/`** — 纯 Pydantic 数据模型，跨组件共享（147 处 import / 83 文件引用，不做迁移）

| 文件 | 内容 |
|------|------|
| `player_character.py` | 玩家角色模型 |
| `item.py` | 物品模型（BG3/D&D 5e 对齐） |
| `npc_instance.py` | NPC 实例模型 |
| `state_delta.py` | 状态增量 |
| `graph_scope.py` | 图谱寻址 |
| `party.py` | 队伍模型 |
| ... | 其余 20+ 模型文件 |

**`app/world/`** — 底层引擎，按**组件功能**分包，每包一个独立子系统

| 包 | 职责 | 说明 |
|----|------|------|
| `player/` | 玩家机械 | stats, operations, ability_check, node_view, constants |
| `item/` | 物品子系统 | registry（只读数据源）、效果引擎（待建） |
| `npc/` | NPC 系统 | instance_manager, context_window, visibility |
| `party/` | 队伍系统 | party_service |
| `combat/` | 战斗规则 | rules（D20 判定、效果表） |
| `events/` | 事件引擎 | behavior_engine, condition_evaluator, action_executor |
| `narrative/` | 叙事系统 | narrative_service, narrative_parser |
| `graph/` | 知识图谱 | builder, snapshot, schema, event_behaviors |
| `memory/` | 记忆系统 | graph_writer, recall, activation |
| `intent/` | 意图解析 | resolver, executor |
| `scene/` | 场景总线 | scene_bus |
| `time/` | 时间管理 | time_manager |

**`app/runtime/`** — 中层运行时

| 文件 | 职责 |
|------|------|
| `session_runtime.py` | 会话运行时（中层统一 API） |
| `stat_ops.py` | 状态操作代理（底层函数 + mark_dirty） |
| `context_assembler.py` | 结构化上下文组装 |
| `world_instance.py` | 世界静态数据注册表 |
| `event_machine.py` | 事件状态机 |

**`app/agentic/`** — 上层 Agent 基础设施

| 文件 | 职责 |
|------|------|
| `agentic_executor.py` | 统一 Agent 执行器（GM/NPC/队友） |
| `immersive_tools.py` | 30 个沉浸式工具 + RoleRegistry |
| `teammate/` | 队友响应服务 |
| `prompt_loader.py` | 提示词加载 |

**`app/routers/`** — REST API 端点（game_v2 + 5 个子路由模块）

**`app/services/admin/`** — 管线编排（pipeline_orchestrator, admin_coordinator, combat/narrative coordinator）

**新组件放置原则**：
- 数据模型 → `app/models/`（Pydantic，跨组件共享）
- 底层引擎 → `app/world/{subsystem}/`（按功能独立分包，零 LLM）
- 中层包装 → `app/runtime/stat_ops.py`（统一 mark_dirty 代理）
- 顶层接线 → `app/agentic/immersive_tools.py` + `app/routers/`

### 4.4 任务池驱动的主线系统

> 最大的架构变更。概念设计完成，需细化后实施。

**设计哲学**：
- 主线不是一条线，是一个**场**
- NPC 感知到主线的"压力"，自主产出任务
- 玩家通过完成任务推进完成度，**选哪些任务、什么顺序，完全自由**
- 达到里程碑阈值 → **关键剧情节点**自动触发
- GM 只负责呈现世界的变化和氛围

**概念模型**：

```
StorylineArc（主线弧）
  ├─ id: "arc_goblin_crisis"
  ├─ name: "哥布林危机"
  ├─ description: "边境哥布林活动日益猖獗..."
  ├─ completion: 0/100
  ├─ milestones:
  │    ├─ 25%: "线索浮现"  → 触发关键剧情
  │    ├─ 50%: "深入调查"  → 触发关键剧情
  │    ├─ 75%: "决战前夜"  → 触发关键剧情
  │    └─ 100%: "危机解除" → 触发章节转换
  └─ context_tags: ["goblin", "frontier", "danger", "guild"]

Quest（任务）
  ├─ id: "quest_goblin_patrol_01"
  ├─ source_npc: "guild_girl"          ← 发布者
  ├─ arc_id: "arc_goblin_crisis"       ← 所属主线弧
  ├─ completion_value: 15              ← 完成贡献
  ├─ description: "最近西部牧场遭到哥布林袭击..."
  ├─ requirements: {min_level: 1}
  ├─ rewards: {gold: 50, xp: 100, items: ["healing_potion"]}
  ├─ status: available | accepted | completed | failed | expired
  └─ generated_by: "npc_agent"         ← LLM 生成标记
```

**NPC 作为任务源**：

```
NPC Agent 感知：
  1. 当前 StorylineArc 的上下文 + 完成度
  2. 自己的角色定位（occupation, personality, motivation）
  3. 当前区域的状态（时间、最近事件、其他任务）

NPC Agent 输出：
  → guild_girl 发布正式公告类任务
  → goblin_slayer 发布高难度清巢任务
  → priestess 发布护送/治疗类任务

触发时机：
  → 玩家进入 NPC 所在子地点时
  → 定期刷新（game_time 推进时）
  → 主线完成度变化时
```

**与现有系统的关系**：

| 升级属性 → 战斗数值 | 成长 → 战斗 | `to_combat_player_state()` 自动反映 |
| 商店购买 → AC/攻击 | 商店 → 战斗 | `_recalculate_ac()` |
