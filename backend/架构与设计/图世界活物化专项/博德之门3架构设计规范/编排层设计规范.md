# 编排层设计规范

创建时间：2026-02-26
状态：设计中
前置文档：博德之门3架构深度分析、❶ 内容层、❷ 规则引擎、❸ 状态层、⊕ AI Osiris、❺ 叙事层

> 编排层是六层架构的"胶水"——不拥有业务逻辑，只负责按正确顺序、在正确时机调用正确的层。
>
> 核心隐喻：编排层 = 交响乐指挥。乐器（❶❷❸⊕❺）自己会演奏，指挥只管何时谁进、何时谁停。

---

## 一、定位与职责

### 做什么

1. **格生命周期管理**：时间累积 → 格结算触发 → SceneBus 重置
2. **格内动作处理**：A/B/C 三阶段管线 + 2 条独立管线（交互/私聊）
3. **格结算编排**：按优先级执行 SettlementHook 链（AI Osiris → 遭遇 → 事件 → 时间推进 → GM 叙述）
4. **扩展点注册**：PipelineHook + SettlementHook，新子系统零侵入接入
5. **会话生命周期**：创建 → 恢复 → 持久化

### 不做什么

| 职责 | 归属 | 编排层只做 |
|------|------|-----------|
| 规则计算 | ❷ RulesEngine | 调用 `execute()` / `batch_execute()` |
| 状态持有 | ❸ StateContainer | 读快照、写回 delta |
| 叙述生成 | ❺ AgenticExecutor | 传入上下文，接收输出 |
| 因果推理 | ⊕ AI Osiris | 传入摘要，接收指令 |
| 事件条件评估 | EventEngine | 在固定时机调用 |

### 设计原则

- **P1 薄编排**：编排层代码应以"调用序列"为主，不应出现业务 if-else
- **P2 确定性执行顺序**：SettlementHook 按显式优先级排序，不存在"谁先注册谁先跑"
- **P3 管线独立性**：主管线/交互管线/私聊管线各自独立，不共享内部状态
- **P4 格内无感知格边界**：PipelineOrchestrator 只返回 time_cost，不知道"还剩多少时间触发结算"
- **P5 持久化后置**：所有处理完成后由 TickCoordinator 统一 persist，管线内部不做持久化

## 二、核心组件架构

```
HTTP 路由（game_v2_router）
    │
    ▼
AdminCoordinator（入口单例）
    ├─ /input/stream     → TickCoordinator.process()
    ├─ /navigate         → TickCoordinator.process()
    ├─ /rest, /trade...  → TickCoordinator.process()
    ├─ /interact/stream  → NpcInteractionCoordinator.process()
    ├─ /private-chat     → PrivateChatCoordinator.process()
    └─ /combat/*         → CombatCoordinator（战斗子流程）

TickCoordinator（会话级单例）
    │  持有：accumulated time, SceneBus, change_log
    │  职责：时间累积 + 格结算触发 + 统一持久化
    │
    ├─ PipelineOrchestrator（主管线，无状态）
    │     A → B → C → 返回 (response, time_cost)
    │
    ├─ NpcInteractionCoordinator（交互管线，无状态）
    │     Setup → NPC Agent → GM Observe → Teammate → Options → Persist
    │
    └─ PrivateChatCoordinator（私聊管线，无状态）
          Setup → NPC Agent → Options → Persist
```

### §2.1 AdminCoordinator — 入口路由

最薄的一层。只做：请求解析 → 获取 TickCoordinator → 路由到对应管线。

```python
class AdminCoordinator:
    """入口单例。HTTP 请求 → 内部编排。"""

    # 会话级 TickCoordinator 缓存
    _tick_coordinators: dict[str, TickCoordinator]

    async def process_player_input(self, session_id, input) -> SSEStream:
        tc = self._get_or_create_tick_coordinator(session_id)
        return await tc.process(input)

    async def process_interact(self, session_id, npc_id, input) -> SSEStream:
        tc = self._get_or_create_tick_coordinator(session_id)
        coordinator = NpcInteractionCoordinator(tc.shared_context)
        result = await coordinator.process(npc_id, input)
        tc.accumulate(result.time_cost)
        await tc.check_settlement()
        await tc.persist()
        return result.sse_stream

    async def process_private_chat(self, session_id, npc_id, input) -> SSEStream:
        tc = self._get_or_create_tick_coordinator(session_id)
        coordinator = PrivateChatCoordinator(tc.shared_context)
        result = await coordinator.process(npc_id, input)
        tc.accumulate(result.time_cost)
        await tc.check_settlement()
        await tc.persist()
        return result.sse_stream
```

### §2.2 TickCoordinator — 格生命周期管理器

编排层的核心。会话级单例，管理时间格的完整生命周期。

```python
class TickCoordinator:
    """格生命周期管理器。每个会话一个实例。"""

    # === 依赖注入 ===
    world: WorldInstance              # ❶ 静态数据
    state: StateContainer             # ❸ 运行时状态
    rules_engine: RulesEngine         # ❷ 规则引擎
    ai_osiris: AIOsiris               # ⊕ 因果判定
    event_engine: EventEngine         # 事件状态机

    # === 子管线 ===
    pipeline: PipelineOrchestrator

    # === 注册表 ===
    settlement_hooks: list[SettlementHook]   # 已按优先级排序

    # === 格级状态 ===
    scene_bus: SceneBus                # 格级生命周期
    change_log: list[StateChange]      # 本格状态变化记录

    # === 共享上下文（供独立管线使用）===
    @property
    def shared_context(self) -> SharedContext:
        return SharedContext(
            world=self.world,
            state=self.state,
            rules_engine=self.rules_engine,
            scene_bus=self.scene_bus,
        )

    async def process(self, input) -> SSEStream:
        """主入口：处理玩家动作 → 检查结算 → 持久化"""

        # 1. 委托 PipelineOrchestrator 处理即时响应
        result = await self.pipeline.process(input, self.shared_context)

        # 2. 记录状态变化
        self.change_log.extend(result.state_changes)

        # 3. 累加时间 + 检查结算
        self.accumulate(result.time_cost)
        await self.check_settlement()

        # 4. 统一持久化
        await self.persist()

        return result.sse_stream

    def accumulate(self, time_cost: float):
        """累加时间消耗。"""
        self.state.time_slice.accumulate(time_cost)

    async def check_settlement(self):
        """检查是否触发格结算。"""
        while self.state.time_slice.accumulated >= 1.0:
            self.state.time_slice.accumulated -= 1.0
            await self._tick_settlement()

    async def _tick_settlement(self):
        """每满 1 格执行一次。按 SettlementHook 优先级链执行。"""
        for hook in self.settlement_hooks:
            if hook.should_skip(self.change_log):
                continue
            hook_result = await hook.execute(
                change_log=self.change_log,
                state=self.state,
                world=self.world,
                rules_engine=self.rules_engine,
                scene_bus=self.scene_bus,
            )
            # Hook 可能产生新的 Command → ❷ 执行 → delta 应用
            if hook_result.commands:
                for cmd in hook_result.commands:
                    exec_result = self.rules_engine.execute(cmd, self.state, self.world)
                    if exec_result.success:
                        self.state.apply(exec_result.delta)

        # 格级数据重置
        self.scene_bus.reset()
        self.change_log.clear()

    async def persist(self):
        """统一持久化。本地优先，云端异步。"""
        for name, slice in self.state.all_slices():
            if slice.dirty:
                # 1. 本地存档（同步，零延迟）
                self._save_store.write_local(self.session_id, name, slice.serialize())
                slice.clear_dirty()
        # SceneSlice 不持久化（格级生命周期）

        # 2. 云端同步（异步，不阻塞游戏循环）
        self._save_store.schedule_cloud_sync(self.session_id)
```

### §2.3 PipelineOrchestrator — 主管线

格内单次动作处理。无状态，不感知格边界。

```python
class PipelineOrchestrator:
    """主管线：A/B/C 三阶段处理。无状态。"""

    # === 注册表 ===
    pipeline_hooks: dict[str, list[PipelineHook]]  # extension_point → hooks（已排序）

    async def process(self, input, ctx: SharedContext) -> PipelineResult:
        # === A 阶段：上下文组装 + 引擎执行 ===
        snapshot = await self._stage_a(input, ctx)

        # === B 阶段：Agentic 会话 ===
        agent_result = await self._stage_b(snapshot, ctx)

        # === C 阶段：后处理 ===
        return await self._stage_c(agent_result, ctx)
```

## 三、格生命周期

### §3.1 时间累积模型

```
玩家动作 → 管线返回 time_cost
         → TickCoordinator.accumulate(time_cost)
         → while accumulated >= 1.0:
               accumulated -= 1.0
               tick_settlement()
```

**统一时间成本表**（❷ RulesEngine 各 Handler 计算并返回）：

| 动作类型 | time_cost | 来源 Handler | 备注 |
|---------|-----------|-------------|------|
| 查看/装备/背包/地图 | 0 | InventoryHandler | 纯 UI 操作 |
| 进入/离开子地点 | 0 | NavigationHandler | 同区域免费 |
| 经验/升级 | 0 | GrowthHandler | 引擎内部操作 |
| AI Osiris 指令 | 0 | WorldStateHandler | 结算层操作 |
| 对话 | 1/6 | — | 管线直接返回 |
| 交易 | 1/6 | EconomyHandler | 一次买卖 |
| 搜索/调查 | 1/6 | SkillCheckHandler | 一次检定 |
| 使用物品 | 1/6 | InventoryHandler | 战斗外使用 |
| 偷窃/撬锁 | 1/6 | CrimeHandler | 一次尝试 |
| 短休息 | 1 | RestHandler | 恢复 25% HP |
| 区域间移动 | 1-3 | NavigationHandler | `travel_slots`（❶ MapRegistry 边权重）|
| 战斗 | ceil(rounds/6) | CombatHandler | 每 6 回合 = 1 格 |
| 长休息 | 剩余全部格 | RestHandler | 跳到次日 05:00 |

**有意义交互计数**：cost = 1/6 的动作累积到 TimeSlice.accumulated，6 次 = 1.0 格 → 触发结算。

### §3.2 tick_settlement() — 完整流程

格结算是编排层最关键的序列。9 个内置 SettlementHook 按优先级**严格顺序**执行：

```
tick_settlement()
    │
    ├─ P10: ScheduledEventHook
    │       检查 AI Osiris 上格安排的延时事件是否触发
    │       读 EventSlice.pending_events → 条件匹配 → 转为 active
    │
    ├─ P20: StatusEffectHook
    │       状态效果逐格 tick（中毒扣 HP、燃烧扣 HP、眩晕解除...）
    │       产生 Command → ❷ 执行 → delta 应用
    │
    ├─ P30: AIOsirisHook  ★ 核心
    │       收集 change_log → 构建世界快照 → AI Osiris 推理
    │       → 结构化指令 → ❷.batch_execute() 验证执行
    │       ※ 平凡格跳过（见 §3.5）
    │
    ├─ P35: NarrativePlannerHook  ★ 叙事规划
    │       主动叙事引导：故事里程碑 + 玩家行为 → 动态任务生成
    │       条件触发（里程碑变化/区域变化/停滞检测）+ 每 6 格兜底
    │       → 任务创建/路人 NPC 投递/NPC 指令/环境线索
    │       详见 `NarrativePlanner设计规范.md`
    │
    ├─ P40: EncounterHook
    │       遭遇检定：probability = area.danger_level × period_multiplier
    │       ※ AI Osiris 可能刚改了 danger_level，所以排在 P30 之后
    │       → 触发遭遇时产生 Command → ❷ 执行
    │
    ├─ P50: EventConditionHook
    │       EventEngine.check_conditions()
    │       ※ AI Osiris 可能设了新 flag / 推进了任务，触发新事件
    │
    ├─ P60: NpcScheduleHook
    │       NPC 日程更新（如果时段即将变化）
    │       NPC 位置/状态调整
    │
    ├─ P70: TimeAdvanceHook
    │       时间推进 1 格
    │       检查时段切换（dawn/day/dusk/night）
    │       → 时段切换时广播 period_changed 事件
    │
    ├─ P80: GmNarrationHook
    │       GM 叙述结算结果（如有玩家可感知的显著变化）
    │       例："夜风中传来窃窃私语，神殿区的气氛变得微妙..."
    │       → SSE gm_narration 事件
    │       ※ 无显著变化时 [PASS]
    │
    └─ P90: SceneBusResetHook
            SceneBus 重置，进入新格
            change_log 清空
```

**为什么这个顺序**：

| 顺序 | 理由 |
|------|------|
| P10 → P20 | 延时事件可能改变角色状态，状态效果需要在最新状态上 tick |
| P20 → P30 | AI Osiris 需要看到 tick 后的最新状态（如：中毒扣血后 HP 很低） |
| P30 → P35 | NarrativePlanner 需要看到 AI Osiris 本格输出（新 flag/任务推进） |
| P35 → P40 | NarrativePlanner 的 escalate 可能改变 danger_level，影响遭遇概率 |
| P30 → P50 | AI Osiris 可能 set_flag / advance_quest，触发新事件 |
| P40 → P50 | 遭遇结果可能触发事件（如：击杀遭遇怪物完成任务目标） |
| P50 → P60 | 事件可能影响 NPC 行为（如：NPC 收到消息改变日程） |
| P60 → P70 | 先更新 NPC 行为再推进时间（确保推进后状态一致） |
| P70 → P80 | GM 知道新时间和新时段，叙述更准确 |
| P80 → P90 | GM 叙述写入当前 SceneBus（作为本格最后记录），然后重置 |

### §3.3 多格动作处理

时间成本 > 1 的动作会触发多次结算。每格结算可能产生不同事件（涌现性）。

**区域间移动（1-3 格）**：

```
move_area(town → goblin_forest, cost=2)
  → PipelineOrchestrator 返回 time_cost=2
  → TickCoordinator.accumulate(2)
  → tick_settlement() #1（途中）
     P10-P20: 常规处理
     P30: AI Osiris 推理途中情况
     P40: 遭遇检定 → d20 + danger → 可能触发战斗/路人事件
     P70: 时间推进 1 格
     P80: GM 旅途叙述："你沿着西行的土路出发，午后阳光洒在麦田上。"
  → tick_settlement() #2（抵达）
     P30: AI Osiris 推理抵达场景
     P40: 遭遇检定（新区域 danger_level）
     P50: 进入新区域可能触发事件
     P70: 时间推进 1 格
     P80: GM 抵达叙述："远远地，你看到牧场的篱笆被撞开了几个大洞..."
```

**长休息（跳到次日 05:00）**：

```
rest_long(remaining_slots=8)
  → 逐格结算 × 8
     格 1-2: 普通休息（无显著事件）
     格 3:   AI Osiris 触发同伴营地对话
             "审判骑士在篝火旁坐下，欲言又止地看着你..."
     格 4-7: 普通休息
     格 8:   守夜检定（EncounterHook，夜间 danger × 1.5）
             HP/法术位全恢复（RestHandler 在格结算前已执行）
             次日 05:00，进入新的一天
```

**战斗结束（ceil(rounds/6) 格）**：

```
combat_end(total_rounds=10, cost=ceil(10/6)=2)
  → 战斗结束后逐格结算 × 2
     格 1: 战后即时（战利品分配、XP 分发）
     格 2: AI Osiris 推理战斗后果
           例：敌方势力收到消息、附近 NPC 反应、区域 danger 调整
```

### §3.4 平凡格优化

来自 AI Osiris 设计规范 Q5：纯 0 成本动作不触发结算，但即使触发了结算，如果本格只有 0 成本动作，AI Osiris 可以跳过。

```python
class AIOsirisHook(SettlementHook):
    priority = 30
    name = "ai_osiris"

    def should_skip(self, change_log: list[StateChange]) -> bool:
        """平凡格跳过。只有 0 成本动作 = 无需推理。"""
        return all(c.time_cost == 0 for c in change_log) or len(change_log) == 0
```

平凡格时 P30 跳过，其余 Hook 正常执行。节省约 80% 的 AI Osiris LLM 调用。

## 四、主管线详解（A/B/C 三阶段）

### §4.1 A 阶段：上下文组装 + 引擎执行

```
A 阶段
    │
    ├─ A1: WorldInstance 读取
    │       GameRuntime.get_world() → ❶ 静态数据注册表（缓存命中）
    │
    ├─ A2: StateContainer 加载
    │       SessionRuntime.restore() → ❸ 9 个 Slice
    │       已加载则跳过（会话级缓存）
    │
    ├─ A3: ContextAssembler 组装 7 层上下文
    │       L0 世界常量  ← ❶ LoreRegistry + FactionRegistry
    │       L1 章节状态  ← ❸ QuestSlice（completion%、活跃任务）
    │       L2 区域环境  ← ❶ MapRegistry + ❸ AreaSlice
    │       L3 地点细节  ← ❶ SubLocation 数据 + ❸ 探索状态
    │       L4 动态状态  ← ❸ PlayerSlice + RelationSlice + FlagSlice + PartySlice
    │       L5 场景总线  ← SceneBus 当前内容
    │       L6 记忆召回  ← MemoryGraph 扩散激活（关键词触发）
    │       L7 引擎结果  ← A4 填充
    │
    ├─ A4: Pre-tick 引擎执行
    │       解析玩家意图 → 构造 Command
    │       → ❷ RulesEngine.execute(cmd, state, world)
    │       → ExecuteResult { success, delta, narrative_hints, rolls, time_cost }
    │       → state.apply(delta)  写入 ❸
    │       → narrative_hints → L7 上下文层
    │       → rolls → SSE dice_roll 事件
    │       → 结果写入 SceneBus：[ENGINE] 执行摘要
    │
    ├─ A5: PipelineHook(after_engine) 扩展点
    │       子系统在引擎执行后做额外处理
    │       例：坐骑系统检查移动后耐力消耗
    │
    └─ A6: EventEngine.check_conditions()
            Pre-check：引擎执行后是否有事件条件被满足
            满足则转换事件状态 → 写入 SceneBus（Agent 可见）
```

### §4.2 B 阶段：Agentic 会话

```
B 阶段
    │
    ├─ B1: GM Agent
    │       AgenticExecutor.run(
    │           role="gm",
    │           system_prompt=flash_agentic_system.md,
    │           context=7 层完整上下文,
    │           tools=RoleToolRegistry.get("gm") + gm_extra_tools,
    │           exclude_tools=ENGINE_TOOL_EXCLUSIONS  # 引擎已执行的操作
    │       )
    │       输出：叙述文本 or [PASS]
    │       约束：GM 零写权限（架构硬约束）
    │       → SSE gm_narration 事件
    │
    ├─ B2: NPC Agent（如果场景中有交互 NPC）
    │       AgenticExecutor.run(
    │           role="npc",
    │           character_id=npc_id,
    │           context=NPC 视角过滤后的上下文,
    │           tools=RoleToolRegistry.get("npc"),
    │       )
    │       输出：对话 + 可选 Command（自身权限内）
    │       Command → ❷ 执行 → delta 应用 → 结果写入 SceneBus
    │       → SSE npc_response 事件
    │
    └─ B3: 队友 Agent
            TeammateResponseService.process_round()
            对每个队友：
                判断是否发言（response_tendency 阈值）
                AgenticExecutor.run(
                    role="teammate",
                    character_id=teammate_id,
                    context=队友视角上下文,
                    tools=RoleToolRegistry.get("teammate"),
                )
                输出：对话 + 可选 Command or [PASS]
                → SSE teammate_response 事件（如有）
```

**Agent 执行顺序固定**：GM → NPC → 队友（依次）。每个 Agent 能看到之前 Agent 写入 SceneBus 的内容。

### §4.3 C 阶段：后处理

```
C 阶段
    │
    ├─ C1: EventEngine.check_conditions()
    │       Post-check：B 阶段 Agent 操作可能改变了状态
    │       例：NPC 工具调用推进了任务 → 触发后续事件
    │
    ├─ C2: PipelineHook(after_agents) 扩展点
    │       子系统在所有 Agent 响应后做额外处理
    │
    ├─ C3: 同伴事件分发
    │       CompanionInstance 接收本次动作的所有事件
    │       更新同伴内部状态（记忆摘要、事件日志）
    │
    └─ C4: 汇总返回
            收集所有 state_changes → PipelineResult.state_changes
            time_cost → PipelineResult.time_cost
            SSE 流 → PipelineResult.sse_stream
            ※ 不做持久化（由 TickCoordinator 统一处理）
```

## 七、SceneBus 生命周期

SceneBus = ❸ SceneSlice 的运行时视图。**生命周期 = 一个时间格**。

### §7.1 格内累积

```
格 N 开始
    │
    ├─ SceneBus 创建（空）
    │
    ├─ 动作 1:
    │   [ENGINE] 玩家进入杂货店
    │   [NPC:merchant] "欢迎光临！"
    │   [PLAYER] "有匕首卖吗？"
    │   [NPC:merchant] "当然，这把短匕首只要 8 金币。"
    │   [GM] [PASS]
    │
    ├─ 动作 2:
    │   [ENGINE] 交易完成：短匕首 -8 金币
    │   [NPC:merchant] "好眼光。"
    │   [TEAMMATE:paladin] "我们该赶路了。"
    │
    ├─ 动作 N:
    │   ... SceneBus 持续累积，上下文越来越丰富
    │   每个 Agent 都能看到之前所有动作（视可见性而定）
    │
    ├─ tick_settlement()
    │   P80: GM 叙述结算结果（写入当前 SceneBus 作为本格最后记录）
    │   P90: SceneBus 重置
    │
    └─ 格 N+1 开始（新的空 SceneBus）
```

### §7.2 SceneEntry 格式

```python
@dataclass
class SceneEntry:
    source: str          # "ENGINE" | "PLAYER" | "NPC:{id}" | "GM" | "TEAMMATE:{id}"
    content: str         # 内容文本
    visibility: str      # "public" | "private"
    tags: list[str]      # 语义标签（可选，供 AI Osiris 使用）
    timestamp: float     # 格内相对时间
```

### §7.3 可见性控制

| 场景 | 可见性 | 谁能看到 |
|------|--------|---------|
| 正常对话 | public | 所有人 |
| 偷窃成功（未被目击） | private(player) | 仅玩家 |
| 私聊内容 | private(player, npc) | 仅玩家和该 NPC |
| 引擎执行结果 | public | 所有人（但 Agent 按各自可见性过滤） |

Agent 读取 SceneBus 时，由 ContextAssembler 按角色可见性规则过滤：
- GM：看到所有 public + 所有 private（全知视角）
- NPC：看到 public + 自己参与的 private
- 队友：看到 public + 自己参与的 private

## 八、EventEngine — 事件状态机

独立组件。不持有状态（状态在 ❸ EventSlice），被编排层在固定时机调用。

### §8.1 职责

```python
class EventEngine:
    """事件状态机。无状态，读 ❸ 检查条件。"""

    def check_conditions(
        self, state: StateContainer, world: WorldInstance
    ) -> list[EventTransition]:
        """检查所有活跃事件的条件 → 返回状态转换列表。

        被调用时机：
        - A6: 主管线 pre-check（引擎执行后）
        - C1: 主管线 post-check（Agent 操作后）
        - P50: 格结算中（AI Osiris 执行后）
        """
        ...

    def check_scheduled(
        self, state: StateContainer
    ) -> list[EventTransition]:
        """检查延时事件是否触发。

        被调用时机：P10（格结算最先执行）
        延时事件来源：AI Osiris schedule_event 指令
        """
        ...
```

### §8.2 事件状态流转

```
locked ──────→ available ──────→ active ──────→ completed
  │               │                │               │
  │  前置条件满足   │  触发条件满足    │  所有目标完成    │
  │               │                │               ↓
  │               │                └──→ failed    consequences 执行
  │               │                    (超时/条件)
  │               │                       │
  └───────────────┴───── cooldown ←───────┘  (可重复事件)
```

### §8.3 条件类型

```python
class ConditionType(Enum):
    FLAG_SET = "flag_set"                   # FlagSlice 中某标记为特定值
    LOCATION_ENTERED = "location_entered"   # 玩家在特定位置
    TIME_REACHED = "time_reached"           # 时段/日期达到
    QUEST_STATE = "quest_state"             # 任务在特定状态
    DISPOSITION_THRESHOLD = "disposition"   # NPC 好感度达到阈值
    TIME_ELAPSED = "time_elapsed"           # 延时事件：N 格后触发
    PERIOD_REACHED = "period_reached"       # 特定时段（dawn/day/dusk/night）
    CUSTOM = "custom"                       # 自定义条件（子系统扩展）
```

### §8.4 调用时机总览

| 调用点 | 方法 | 目的 |
|--------|------|------|
| A6（主管线，引擎后） | `check_conditions()` | 引擎执行后可能满足新条件 |
| C1（主管线，Agent 后） | `check_conditions()` | Agent 操作可能改变状态 |
| P10（格结算，最先） | `check_scheduled()` | 延时事件到期检查 |
| P50（格结算，Osiris 后） | `check_conditions()` | AI Osiris 可能设了新 flag |

## 九、注册式扩展

### §9.1 PipelineHook — 管线扩展

```python
class PipelineHook(ABC):
    """主管线扩展钩子。在固定扩展点执行。"""

    @property
    @abstractmethod
    def extension_point(self) -> str:
        """扩展点标识：
        - 'after_engine': A5，引擎执行后
        - 'after_agents': C2，所有 Agent 响应后
        """

    @property
    def priority(self) -> int:
        """同一扩展点内的执行优先级（小值先执行）。默认 50。"""
        return 50

    @abstractmethod
    async def execute(self, context: PipelineContext) -> None:
        """在扩展点被调用。可读 context、产生额外 Command。"""
```

**注册方式**：

```python
# 子系统初始化时
pipeline.register_hook(MountSpeedHook())      # after_engine, P30
pipeline.register_hook(WeatherVisibilityHook()) # after_engine, P40
```

### §9.2 SettlementHook — 格结算扩展

```python
class SettlementHook(ABC):
    """格结算钩子。按优先级顺序执行。"""

    @property
    @abstractmethod
    def priority(self) -> int:
        """执行优先级。约定区间：
        P10-P19: 遗留处理（延时事件、上格残余）
        P20-P29: 状态 tick（效果结算、耐力恢复）
        P30-P39: AI 推理（AI Osiris 因果判定）
        P40-P49: 随机事件（遭遇检定、天气变化）
        P50-P59: 事件状态机（条件检查、状态转换）
        P60-P69: NPC 行为（日程更新、位置调整）
        P70-P79: 时间推进（格推进、时段切换）
        P80-P89: 叙述生成（GM 结算叙述）
        P90-P99: 清理重置（SceneBus、change_log）
        """

    @property
    @abstractmethod
    def name(self) -> str:
        """钩子名称，用于日志和调试。"""

    @abstractmethod
    async def execute(
        self,
        change_log: list[StateChange],
        state: StateContainer,
        world: WorldInstance,
        rules_engine: RulesEngine,
        scene_bus: SceneBus,
    ) -> HookResult:
        """执行结算逻辑。

        返回 HookResult 可包含：
        - commands: 产生的 Command 列表（交给 ❷ 执行）
        - sse_events: 需要推送的 SSE 事件
        - skip_reason: 如果跳过执行，说明原因
        """

    def should_skip(self, change_log: list[StateChange]) -> bool:
        """是否跳过本次执行。默认 False。"""
        return False
```

**HookResult**：

```python
@dataclass
class HookResult:
    commands: list[Command] = field(default_factory=list)
    sse_events: list[SSEEvent] = field(default_factory=list)
    skip_reason: str | None = None
```

### §9.3 内置 SettlementHook 清单

| Hook 类名 | Priority | 名称 | 职责 |
|-----------|----------|------|------|
| `ScheduledEventHook` | 10 | scheduled_events | 检查 AI Osiris 安排的延时事件是否触发 |
| `StatusEffectHook` | 20 | status_effects | 状态效果逐格 tick（中毒/燃烧/眩晕...） |
| `AIOsirisHook` | 30 | ai_osiris | AI Osiris 因果推理 + 引擎执行指令 |
| `NarrativePlannerHook` | 35 | narrative_planner | 主动叙事规划：动态任务生成 + 投递（详见 `NarrativePlanner设计规范.md`） |
| `EncounterHook` | 40 | encounter | 遭遇检定（danger × period_multiplier） |
| `EventConditionHook` | 50 | event_conditions | EventEngine 条件检查 |
| `NpcScheduleHook` | 60 | npc_schedule | NPC 日程/位置更新 |
| `TimeAdvanceHook` | 70 | time_advance | 时间推进 + 时段切换检查 |
| `GmNarrationHook` | 80 | gm_narration | GM 叙述结算结果（无变化则 PASS） |
| `SceneBusResetHook` | 90 | scene_reset | SceneBus 重置 + change_log 清空 |

### §9.4 三步注册的编排层部分

新子系统接入时，编排层的注册清单：

```
Step 3（编排层注册）：

  3a. PipelineHook（如果子系统需要在格内管线中参与）
      ├─ 选择扩展点：after_engine 或 after_agents
      ├─ 分配优先级（不与已有 Hook 冲突）
      └─ 实现 execute()

  3b. SettlementHook（如果子系统需要在格结算中参与）
      ├─ 选择优先级区间（见 §9.2 约定）
      ├─ 实现 execute() + should_skip()
      └─ 返回 HookResult（可含 Command）

  3c. 联动 checklist 更新：
      □ AI Osiris 世界快照是否包含新 Slice 数据？
      □ ContextAssembler 是否组装新上下文层？
      □ Agent 可见性矩阵是否更新？
      □ 世界书提取管线是否需要新 extractor？
      □ 前端 SSE 是否需要新事件类型？
```

**示例：天气子系统接入**

```
Step 1 ❶: WeatherRegistry — 各区域/季节的天气模式模板
Step 2 ❸: WeatherSlice — 当前天气状态 { current, duration, effects }
Step 3 编排层:
  3a. PipelineHook(after_engine, P35):
      移动后检查天气对视野/行军速度的影响
  3b. SettlementHook(P45 — 随机事件区间):
      每格滚天气变化 → 可能改变 danger_level / 遭遇表
  3c. checklist:
      □ AI Osiris 快照加入天气状态 ✅
      □ ContextAssembler L2 区域层加入天气描述 ✅
      □ GM Agent 可见天气（叙述用） ✅
      □ SSE 新增 weather_change 事件 ✅
```

### §9.5 DynamicSubAreaManager — 动态子区域服务

独立模块，管理运行时动态生成的临时子区域。被 NarrativePlanner（`plant_environmental`，详见 `NarrativePlanner设计规范.md` §3.6）、AI Osiris、EventEngine 等 SettlementHook 调用。

**核心职责**：创建 / 查询 / 过期 / 清理临时子区域。

#### TemporarySubArea Schema

```python
@dataclass
class TemporarySubArea:
    """动态生成的临时子区域。❶ SubLocationTemplate schema 的运行时超集。"""

    # === SubLocationTemplate 兼容字段（❶ 内容层设计规范 §4.1）===
    id: str                          # "_temp_carriage_wreck"（自动生成，_temp_ 前缀）
    name: str                        # "路边的马车残骸"
    description: str                 # 叙事描述
    tags: list[str]                  # [CLUE, GOBLIN, COMBAT_AFTERMATH]
    type: str                        # discovery / encounter / event_site
    available_hours: tuple[int,int]  # 默认 (0, 24) — 临时子区域通常全天可用
    resident_npcs: list[str]         # 临时 NPC ID（由 PasserbyService 生成）
    interactables: list[str]         # 可交互物件 ID

    # === 动态扩展字段 ===
    target_area: str                 # 所属区域 ID
    content_hints: dict              # LLM 辅助内容（clues, possible_npcs）
                                     # → 供 Agent 叙述时参考，不是硬编码脚本
    discovery_mode: str              # auto / check / narrated
    discovery_dc: int                # check 模式的 DC（auto/narrated 模式忽略）
    discovery_check: str             # perception / investigation / nature

    # === 关联 ===
    linked_quest_id: str | None      # 关联的动态任务 ID
    linked_milestone: str | None     # 关联的里程碑 ID
    source: str                      # 创建来源："narrative_planner" / "ai_osiris" / "event_engine"

    # === 生命周期 ===
    created_at_tick: int             # 创建时间格
    expiry_ticks: int                # 存活格数（-1 = 永不过期）
    on_expire: str                   # remove（直接移除）/ decay（描述变化但保留残骸）
    status: str                      # active / discovered / entered / expired
```

#### API

```python
class DynamicSubAreaManager:
    """动态子区域管理器。独立模块，被 SettlementHook 调用。"""

    def create(self, spec: TemporarySubArea) -> str:
        """创建临时子区域。写入 ❸ AreaSlice.temporary_sub_areas。返回生成的 ID。"""

    def list_active(self, area_id: str) -> list[TemporarySubArea]:
        """查询指定区域的活跃临时子区域。
        NavigationHandler 合并查询时调用（见下方集成说明）。"""

    def get(self, sub_area_id: str) -> TemporarySubArea | None:
        """按 ID 查询单个临时子区域。"""

    def mark_discovered(self, sub_area_id: str) -> None:
        """标记为已发现。check 模式下玩家通过检定后调用。
        status: active → discovered，出现在可用子地点列表中。"""

    def mark_entered(self, sub_area_id: str) -> None:
        """标记为已进入。玩家 enter_sub_location 时调用。
        status: discovered → entered。"""

    def expire(self, sub_area_id: str) -> None:
        """手动过期。retire_quest 级联清理时调用。
        status → expired，从活跃列表移除。"""

    def tick_cleanup(self, current_tick: int) -> list[str]:
        """格结算时调用，清理已到期的子区域。
        返回被清理的 ID 列表。挂载于 P90 SceneBusResetHook 附带执行。"""
```

#### 与 NavigationHandler 集成（❷ 规则引擎层 §3.3）

```
玩家查询可用子地点 / NavigationHandler 验证 enter_sub_location：

    MapRegistry.get_sub_locations(area_id)         ← 静态子地点（❶ 内容层）
  + DynamicSubAreaManager.list_active(area_id)     ← 动态子地点（❸ 状态层）
  ──────────────────────────────────────────────
  = 合并后的完整子地点列表

NavigationHandler 验证流程扩展：
  1. 先查 MapRegistry（静态）
  2. 未命中 → 查 DynamicSubAreaManager（动态）
  3. 均未命中 → 验证失败
  4. check 模式的子区域需 status >= discovered 才可进入
```

#### 与 ContextAssembler 集成

ContextAssembler 组装 L3（地点细节）时，对动态子区域使用 `content_hints` 作为 Agent 上下文的一部分，使 GM / NPC / 队友 Agent 知晓该子区域的叙事要素（线索、可能的 NPC、氛围），从而自然协作叙述。

#### 存储

临时子区域存储在 ❸ `AreaSlice.temporary_sub_areas: list[TemporarySubArea]`，随 session 统一持久化。

```
saves/{session_id}/state/area.json  →  { ..., temporary_sub_areas: [...] }
```

#### 生命周期图

```
NarrativePlanner / AI Osiris / EventEngine
    │
    ▼
DynamicSubAreaManager.create()
    │
    ▼
active ──(check 模式: 检定通过)──→ discovered ──(enter_sub_location)──→ entered
    │                                   │                                  │
    │                                   │                                  │
    └──────────(expiry_ticks 到期)──────┴──────────────────────────────────┘
                                        │
                                        ▼
                                     expired → tick_cleanup() 移除
```

```
    │     AreaSlice:     从 ❶ MapRegistry 初始化 base_danger / exploration
    │     EventSlice:    从 ❶ 加载初始事件定义
    │     PartySlice:    空（无队友）
    │     SceneSlice:    空
    │
    ├─ 3. 构建 TickCoordinator
    │     注入：WorldInstance + StateContainer + RulesEngine + AIOsiris + EventEngine
    │     注册 9 个内置 SettlementHook（按优先级排序）
    │     初始化 SceneBus（空）
    │
    ├─ 4. 角色创建
    │     种族/职业/背景选择（前端 UI）
    │     → 构造 Command(type="create_character", params={...})
    │     → ❷ GrowthHandler 计算初始属性/HP/AC
    │     → PlayerSlice 填充
    │     → 起始装备/金币 → InventoryHandler 执行
    │
    └─ 5. 第一个时间格
          GM 开场叙述（基于位置 + 世界书 + 角色背景）
          SceneBus 首条记录：[GM] 开场叙述
          → SSE gm_narration
          等待玩家第一次操作
```

### §10.2 会话恢复

```
POST /{world_id}/sessions/{session_id}/resume
    │
    ├─ 1. 加载世界数据
    │     GameRuntime.get_world(world_id)（可能已缓存）
    │
    ├─ 2. 恢复状态（本地优先 → 云端回退）
    │     SaveStore.load(session_id)
    │     → 优先读取本地存档 saves/{session_id}/state/
    │     → 本地不存在时回退到 Firestore 云端存档
    │     → StateContainer.restore(data)
    │     → 8 个 Slice 恢复（TimeSlice ~ PartySlice）
    │     → SceneSlice 重新创建（格级生命周期，不跨会话）
    │     → 恢复 TimeSlice.accumulated（未完成的格内累积时间）
    │
    ├─ 3. 重建 TickCoordinator
    │     注入恢复的 StateContainer
    │     注册 SettlementHook
    │     SceneBus 重新初始化
    │
    └─ 4. 恢复叙述
          GM 生成恢复描述
          "你在{location}，{time_period}的{weather}中，记忆慢慢清晰..."
```

### §10.3 持久化策略

**核心原则：本地存档优先，云端异步同步。** 对齐 BG3 的存档模式——本地即时保存，云端是备份/跨设备同步。

**双层存储架构**：

```
         ┌─────────────────────────────────────────┐
         │  游戏循环                                │
         │  TickCoordinator.persist()              │
         └──────────────┬──────────────────────────┘
                        │
              ┌─────────▼─────────┐
              │    SaveStore      │
              │  （存档管理器）     │
              └───┬───────────┬───┘
                  │           │
         同步写入 │           │ 异步上传
         (0ms)    │           │ (后台)
                  ▼           ▼
          ┌──────────┐  ┌──────────┐
          │ 本地存档  │  │ Firestore│
          │ (主存储)  │  │ (云备份) │
          └──────────┘  └──────────┘
```

**本地存档路径**：

```
saves/{session_id}/
  ├─ state/time.json        ← TimeSlice
  ├─ state/player.json      ← PlayerSlice
  ├─ state/relations.json   ← RelationSlice
  ├─ state/quests.json      ← QuestSlice
  ├─ state/flags.json       ← FlagSlice
  ├─ state/areas.json       ← AreaSlice
  ├─ state/events.json      ← EventSlice
  ├─ state/party.json       ← PartySlice
  ├─ meta.json              ← 存档元数据（世界ID、角色名、保存时间、游戏内时间）
  └─ (scene 不持久化——格级生命周期)
```

**云端路径**（Firestore，结构与本地一致）：

```
worlds/{world_id}/sessions/{session_id}/
  ├─ state/time
  ├─ state/player
  ├─ ...
  └─ meta
```

**SaveStore 核心接口**：

```python
class SaveStore:
    """存档管理器。本地优先 + 云端异步同步。"""

    def write_local(self, session_id: str, slice_name: str, data: dict) -> None:
        """同步写入本地存档。零网络延迟。"""
        path = f"saves/{session_id}/state/{slice_name}.json"
        atomic_write(path, data)  # 原子写入防损坏

    def schedule_cloud_sync(self, session_id: str) -> None:
        """安排异步云端同步。不阻塞游戏循环。
        策略：
        - 每次 persist 标记为 pending
        - 后台线程批量上传（去重，合并短时间内多次写入）
        - 失败时重试，不影响游戏进程
        """

    def load(self, session_id: str) -> dict:
        """加载存档。本地优先 → 云端回退。"""
        local = self._load_local(session_id)
        if local:
            return local
        return self._load_cloud(session_id)

    def upload_save(self, session_id: str) -> None:
        """手动上传存档到云端（玩家主动触发）。"""

    def download_save(self, session_id: str) -> None:
        """从云端下载存档到本地（跨设备恢复）。"""

    def list_saves(self) -> list[SaveMeta]:
        """列出所有本地存档。"""
```

**持久化时机**：

| 触发点 | 本地写入 | 云端同步 |
|--------|---------|---------|
| 每次 `tc.process()` 完成后 | ✅ 同步写入 | ⏳ 标记 pending |
| 每次 `interact` / `private_chat` 完成后 | ✅ 同步写入 | ⏳ 标记 pending |
| 格结算完成后 | ✅ 同步写入 | ✅ 立即同步（结算是重要节点） |
| 玩家主动保存 | ✅ 同步写入 | ✅ 立即同步 |
| 异常恢复 | ✅ try/finally | — |
| 后台定时 | — | ✅ 批量上传 pending（每 30 秒） |

**恢复优先级**：

```
1. 本地存档（最快，最新）
2. 云端存档（跨设备/本地丢失时回退）
3. 冲突处理：以时间戳较新的为准，提示用户选择
```

**离线支持**：本地存档不依赖网络，云端不可用时游戏完全不受影响。恢复网络后自动同步 pending 存档。

**层间调用规则**：

| 规则 | 说明 |
|------|------|
| 编排层 → 其他层 | 单向调用。编排层调用 ❶❷❸⊕❺ + EventEngine |
