## 一、设计文档 vs 实现对齐分析

设计文档定义了一套完整的 **三级资产解析架构（AssetResolver）**，当前实现只覆盖了其中的 L3 动态生成路径的最小子集。

### 1.1 架构对比

```
设计文档预期架构：
┌──────────────────────────────────────────────────┐
│  SSE 事件 (scene_change / character_enter)        │
│  需要资产 URL                                      │
│       ↓                                           │
│  AssetResolver.resolve(asset_key, context)        │
│       ↓                                           │
│  L1: 缓存（内存 LRU / Redis）→ 命中则返回 URL      │
│       ↓ miss                                      │
│  L2: 静态资产表（WorldInstance.visual 字段）→ URL   │
│       ↓ miss                                      │
│  L3: 动态生成 → prompt 模板 → 生图 API → 上传       │
│       → 写入缓存 → 返回 URL                        │
│       ↓ fail                                      │
│  L4: 通用占位图（fallback/forest_generic.png）      │
└──────────────────────────────────────────────────┘

当前实现：
┌──────────────────────────────────────────────────┐
│  前端组件 (SceneBackground / Portrait)            │
│       ↓                                           │
│  resource-map.ts 静态映射（≈L2，但在前端）          │
│       ↓ miss                                      │
│  POST /images/scene 或 /images/portrait            │
│       ↓                                           │
│  images.py → 拼 prompt → Gemini API → base64       │
│       ↓                                           │
│  前端模块级变量缓存（刷新即失）                       │
│       ↓ fail                                      │
│  CSS 渐变 / 字母头像                                │
└──────────────────────────────────────────────────┘
```

### 1.2 逐项对齐

| 设计文档要求 | 当前实现 | Gap |
|-------------|---------|-----|
| **P0: 数据模型加 visual 字段** | 无 — CharacterTemplate/AreaTemplate 无 visual 字段 | 完全缺失 |
| **P1: SSE 事件携带资产 URL** | scene_change 不含 background URL；character_enter 不含 sprite/emotion | SSE 事件产出时不解析资产 |
| **P2: AssetResolver 三级解析** | 无此模块（tests/test_asset_resolver.py 已写好期望） | 核心模块缺失 |
| **P2: L1 缓存（LRU/Redis）** | 无后端缓存 | 完全缺失 |
| **P2: L2 静态资产表** | 前端 resource-map.ts 承担（非后端） | 位置错误——应在后端 WorldInstance |
| **P2: L3 动态生成** | images.py MVP 可用 | 有，但无上传/缓存链路 |
| **P2: prefetch 预取** | 无 | 完全缺失 |
| **P2: 通用占位图兜底** | 前端 CSS 渐变/字母头像 | 有，但非设计文档预期的"图片占位" |
| **P3: FEELING_MAP → emotion** | 无 — 代码中不存在情感映射 | 完全缺失 |
| **Prompt 模板化构造** | images.py 硬编码字符串拼接 | 有，但缺 AssetPromptBuilder 类 |
| **时间/天气/情绪上下文** | prompt 不含 time/ambiance/emotion | 未消费 TimeSlice/area.tags/RelationSlice |
| **图片模型配置统一** | `_IMAGE_MODEL` 硬编码 | 应提取为配置常量 |
| **并发控制** | 无 Semaphore | 可能触发 rate limit |

## 二、当前实现详情

### 2.1 images.py（226 行 MVP）

- **端点**：`POST /images/scene`、`POST /images/portrait`
- **模型**：`gemini-3.1-flash-image-preview`（硬编码 L20）
- **输出**：`{image_base64, mime_type, source, error}` — base64 直接返回，不上传不缓存
- **错误处理**：silent fallback（`source: "fallback"`, `error: "..."`, `image_base64: null`）
- **Client 管理**：每次请求创建新 Client 并 close（无连接池）

### 2.2 前端资产链路

```
SceneBackground.tsx / Portrait.tsx
    ↓
resource-map.ts:
  backgrounds: Record<string, string>  (3 个静态映射)
  portraits: Record<string, string>    (1 个静态映射)
  _generatedBg: Record<string, string> (模块级变量，session 缓存)
  _generatedPortrait: Record<string, string>
    ↓
getBackground(areaId, locationId):
  1. backgrounds["area/location"]  → 静态命中
  2. backgrounds["area"]           → 区域级 fallback
  3. _generatedBg["area/location"] → session 缓存命中
  4. _generatedBg["area"]          → session 缓存 fallback
  5. '' → 触发 API 请求

getPortrait(characterId):
  1. portraits[characterId]         → 静态命中
  2. _generatedPortrait[characterId] → session 缓存
  3. '' → 触发 API 请求
```

## 三、改进项（按优先级排序 + 设计文档对齐）

### P4-A: 后端持久化缓存（最高优先级）

**问题**：每次请求都调 Gemini API，无任何持久化。同场景跨 session 重复生成。前端缓存刷新即失。

**影响**：
- API 成本浪费（每张图 ~$0.01-0.05，高频使用不可控）
- 响应延迟 2-5 秒（每次冷启动）
- 用户刷新页面 = 全部重新生成

**设计文档预期**：AssetResolver L1 缓存（内存 LRU + 可选 Redis），生成后写入缓存，后续请求命中缓存 0 延迟。

**方案选项**（见下方讨论区）

### P4-B: AssetResolver 模块实现

**问题**：设计文档 P2 核心模块完全缺失。测试已写好（test_asset_resolver.py），实现为零。

**设计文档预期**：
```python
class AssetResolver:
    async def resolve(asset_key, context) -> AssetResult   # 三级解析
    async def resolve_batch(keys, contexts) -> dict        # 批量
    async def prefetch(keys, contexts) -> None             # 预取
    def invalidate(key) -> None                            # 缓存失效

class AssetPromptBuilder:
    def build_scene_prompt(location_data) -> str
    def build_portrait_prompt(character_data, emotion) -> str
```

**与 P4-A 的关系**：AssetResolver 内部包含缓存层，P4-A 是 P4-B 的子集。可以先做 P4-A（纯缓存），再做 P4-B（完整三级解析）；也可以直接做 P4-B 一步到位。

### P4-C: Prompt 上下文丰富化

**问题**：prompt 缺少时间、天气、情绪上下文。白天和夜晚生成同一张图。

**改动**：
```python
# 场景 prompt 注入：
# - TimeSlice.period → "Time of day: dusk, orange sunset light"
# - AreaTemplate.tags → 提取 ambiance 关键词
# - AreaTemplate.terrain_type → "Terrain: dense forest"

# 立绘 prompt 注入：
# - RelationSlice → disposition → emotion_key → 表情描述
#   (需要 P4-E 的 FEELING_MAP 支持)
```

**依赖**：P4-E（FEELING_MAP）用于立绘情绪部分。场景时间部分无依赖，可独立做。

### P4-D: 并发控制

**问题**：多 NPC 同时 character_enter 会并发打 API。

**方案**：后端 `asyncio.Semaphore(3)` 限制同时生成数。前端请求队列串行化。

### P4-E: FEELING_MAP 情感映射

**问题**：设计文档 P3 要求 disposition → emotion key 映射，当前不存在。

**方案**：
```python
# 从 RelationSlice disposition 推导情感
def disposition_to_emotion(approval: int, trust: int) -> str:
    if approval > 50: return "happy"
    if approval > 20: return "neutral"
    if approval < -30: return "angry"
    if trust < -20: return "wary"
    return "neutral"
```

影响两个消费端：
1. 立绘 prompt（P4-C 消费）
2. SSE character_enter/character_emotion 事件的 emotion 字段（P1 消费）

### P4-F: 数据模型加 visual 字段

**问题**：设计文档 P0 要求 AreaTemplate 和 CharacterTemplate 加 visual 字段（background/sprite/expressions），当前无此字段。

**影响**：L2 静态资产表依赖此字段。如果始终走 AI 生成（L3），此项可后置。

### P4-G: 加载状态反馈

**问题**：图片生成期间（2-5 秒）前端无 loading 提示。

**方案**：前端骨架屏 / shimmer + 图片淡入过渡。纯前端工作。

### P4-H: 模型配置统一

**问题**：`_IMAGE_MODEL` 硬编码。

**方案**：提取为环境变量 `IMAGE_MODEL` 或配置常量。

## 四、持久化方案（已确认）

**方案：磁盘持久化 + 静态文件服务 + URL 直链**

### 4.1 存储结构

```
data/cache/images/
├── scenes/
│   └── {world_id}/
│       └── {area_id}/
│           └── {location_id}/
│               ├── dawn.png
│               ├── day.png
│               ├── dusk.png
│               └── night.png
└── portraits/
    └── {world_id}/
        └── {character_id}/
            ├── base.png          ← 基准立绘（首次生成，无参考图）
            ├── neutral.png       ← 情绪变体（以 base.png 为参考图）
            ├── happy.png
            ├── angry.png
            ├── sad.png
            └── surprised.png
```

**URL 直链**：FastAPI `StaticFiles` mount → 前端直接 `<img src="/static/images/portraits/{world_id}/priestess/happy.png">`

浏览器原生 HTTP Cache-Control，刷新页面不重新下载。后续迁移到 GCS/S3 只需替换存储层，上层逻辑不变。

### 4.2 场景背景：按时段生成变体

同一地点最多 4 张变体（dawn/day/dusk/night），通过 `TimeSlice.period` 决定使用哪张。

```python
# 场景缓存 key
def scene_cache_key(world_id: str, area_id: str, location_id: str | None, period: str) -> Path:
    loc = location_id or "_main"
    return CACHE_DIR / "scenes" / world_id / area_id / loc / f"{period}.png"
```

### 4.3 立绘：参考图一致性链

**决策：同角色后续情绪变体以首张 base portrait 为参考图生成。**

Gemini 3.1 Flash Image 支持最多 4 张角色参考图，我们只需 1 张（base portrait）即可保持一致性。

**生成流程**：

```
请求 (character_id=priestess, emotion=worried)
    │
    ├─ worried.png 存在? → 返回 URL（0ms）
    │
    ├─ base.png 存在?
    │   ├─ Yes → 调 Gemini API: contents=[emotion_prompt, Image.open(base.png)]
    │   │        保存 worried.png → 返回 URL（2-5s）
    │   │
    │   └─ No → 先生成 base.png（纯文本 prompt，无参考图）
    │            再用 base.png 生成 worried.png
    │            返回 URL（4-10s，仅首次）
    │
    └─ 生成失败 → 返回 fallback URL
```

**API 调用方式**（参考 nanobanana2.md §Character consistency）：

```python
from google import genai
from google.genai import types
from PIL import Image

client = genai.Client(api_key=api_key)

# ---- 首次：生成 base portrait（无参考图） ----
base_prompt = (
    "Create a polished anime-style vertical character portrait for a fantasy visual novel. "
    "Bust or half-body framing, expressive face, strong silhouette, clean background, "
    "no text, no UI, no speech bubble. "
    f"Character: {name}. {class_line}{tag_line}{appearance_line}"
    "Style: refined anime illustration, detailed costume rendering, warm fantasy mood."
)
response = await client.aio.models.generate_content(
    model="gemini-3.1-flash-image-preview",
    contents=[base_prompt],
    config=types.GenerateContentConfig(
        response_modalities=['TEXT', 'IMAGE'],
    ),
)
# → 提取 inline_data → 保存为 base.png

# ---- 后续：生成 emotion variant（以 base.png 为参考图） ----
base_image = Image.open(base_path)
emotion_prompt = (
    f"Generate a portrait of this exact same character with a {emotion} expression. "
    "Keep the character's appearance, outfit, hairstyle, and art style exactly the same. "
    f"Only change the facial expression to convey: {emotion}. "
    "Maintain the same framing, background style, and illustration quality."
)
response = await client.aio.models.generate_content(
    model="gemini-3.1-flash-image-preview",
    contents=[emotion_prompt, base_image],      # ← 参考图传入
    config=types.GenerateContentConfig(
        response_modalities=['TEXT', 'IMAGE'],
    ),
)
# → 提取 inline_data → 保存为 {emotion}.png
```

### 4.4 情绪集合（已确认）

固定 5 种情绪变体 + 1 个 base：

| Key | 用途 | 生成方式 |
|-----|------|---------|
| `base` | 基准参考图 | 纯文本 prompt，无参考图 |
| `neutral` | 默认表情 | base 参考 + emotion prompt |
| `happy` | 好感/开心 | base 参考 + emotion prompt |
| `angry` | 愤怒/敌意 | base 参考 + emotion prompt |
| `sad` | 悲伤/担忧 | base 参考 + emotion prompt |
| `surprised` | 惊讶/震惊 | base 参考 + emotion prompt |

### 4.5 生成时机（已确认）

**实时生成** — 首次对话/进入场景时触发，前端显示 loading 骨架屏等待。

不做预生成（pregenerate），原因：
- 会拖慢 session 创建（一个 world 可能有 20+ NPC × 6 情绪 = 120 张）
- 很多 NPC 玩家可能从不与其交互
- 实时生成只有首次慢（2-5s），后续全部命中缓存

### 4.6 用户隔离（后续）

当前每个玩家使用自己的一套 world，暂不需要 per-user 隔离。后续多用户时再加 `{user_id}` 层级。

### 4.7 云存储迁移路径

当前磁盘方案的迁移非常直接：
```
save_to_disk(path, data)      → upload_to_gcs(key, data) + 返回公开 URL
check_file_exists(path)       → check_gcs_object(key)
StaticFiles mount             → CDN 直链
```
只需替换存储层实现，上层 AssetResolver 接口不变。

## 五、实施计划

### Phase 1：持久化 + 参考图链路（核心）

改动范围：`images.py` 重写 + `main.py` 加 StaticFiles mount

1. 磁盘缓存层：`_resolve_cached_or_generate()` — 检查文件 → 命中返回 URL / miss 则生成

5. StaticFiles mount：`/static/images/` → `data/cache/images/`
6. 返回 URL 而非 base64：`{"image_url": "/static/images/...", "source": "generated|cached"}`

预估：~150 行后端改动（images.py 重写）+ ~20 行 main.py + ~30 行前端适配
