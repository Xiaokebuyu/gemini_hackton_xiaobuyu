## Phase 0 — 基座层（零外部依赖，两条线可并行）

> **目标**：建立整个架构的两个数据容器——静态世界数据和运行时可变状态。它们彼此无依赖。

### 0A. 内容层基座

| 交付物 | 说明 | 权威规范 |
|--------|------|---------|
| `ContentRegistry` ABC | `name`, `load`, `get`, `query_by_tags(match_all)`, `list_all`, `snapshot`, `validate` | 内容层 §二.1 (L56) |
| `WorldInstance` | `register(registry)`, `get_registry(name)`, `load_all(world_data)`, 便捷属性访问器 | 内容层 §二.2 (L88) |
| `TagRegistry` | 标签维度系统，**必须最先加载**（其他注册表依赖标签验证） | 内容层 §三 (L134) |

**测试边界**：
- `ContentRegistry` 子类 mock：`load()` → `get()` → `query_by_tags()` → `snapshot()` → `validate()`
- `WorldInstance.load_all()` 加载顺序：TagRegistry 先于一切
- `WorldInstance.register()` 去重 / 重名检测

### 0B. 状态层基座

| 交付物 | 说明 | 权威规范 |
|--------|------|---------|
| `StateSlice` ABC | `name`, `restore`, `serialize`, `snapshot`, `dirty` / `clear_dirty` | 状态层 §二.1 (L55) |
| `StateContainer` | `register(slice)`, `get_slice(name)`, `snapshot`, `restore`, `persist`（只序列化 dirty slice） | 状态层 §二.2 (L85) |
| `StateDelta` | `changes: list[StateChange]`，每条 `{slice, operation, path, value}` | 规则引擎 §二 |
| `StateContainer.apply(delta)` | 遍历 `delta.changes`，分发到对应 Slice 的 write API | 状态层 §二.2 |

**测试边界**：
- `StateSlice` mock 子类：`restore()` ↔ `serialize()` 往返一致性
- `StateContainer.persist()` 只输出 dirty slice
- `StateDelta.apply()` 对 mock Slice 的 write 调用正确分发

### Phase 0 完成标准

- [ ] `WorldInstance` 可注册任意 `ContentRegistry` 子类并按名称检索
- [ ] `StateContainer` 可注册任意 `StateSlice` 子类并按名称检索
- [ ] `StateDelta` 可正确 apply 到 `StateContainer`
- [ ] 两个容器各自有完整的单元测试，互不导入

## Phase 1 — 规则引擎层（依赖 Phase 0）

> **目标**：建立 Command → Handler → StateDelta 的无状态纯函数管线。引擎本身不持有任何状态——读 `StateContainer` + `WorldInstance`，返回 `StateDelta`。

| 交付物 | 说明 | 权威规范 |
|--------|------|---------|
| `Command` | `type`, `params`, `source`, `context` | 规则引擎 §2.1 |
| `ValidationResult` | `ok: bool`, `reason: str` | 规则引擎 §2.3 |
| `ExecuteResult` | `success`, `delta`, `narrative_hints`, `rolls`, `time_cost`, `errors`, `is_dry_run` | 规则引擎 §2.3 |
| `DiceRoll` | `purpose`, `dice`, `result`, `modifiers`, `total`, `critical` | 规则引擎 §2.3 |
| `CommandHandler` ABC | `command_types: list[str]`, `validate(cmd, state, world)`, `compute(cmd, state, world)` | 规则引擎 §2.4 (L173) |
| `RulesEngine` | `register(handler)` 遍历 `command_types`；`execute` / `validate` / `dry_run` / `batch_execute` | 规则引擎 §2.1 (L72) |

**关键约定**：
- Handler **只读** `StateContainer`，不调用 write API
- 所有变更通过返回 `StateDelta` 表达，由调用方 `state.apply(delta)` 执行
- `StateSnapshot` 概念已统一为 `StateContainer`（Handler 按约定只读）

**测试边界**：
- Mock Handler 注册 → `RulesEngine.execute()` 路由正确
- `command_types` 多类型注册 → 每个 type 都能路由到同一 Handler
- `validate()` 失败 → `execute()` 不执行
- `dry_run()` → `is_dry_run=True`，delta 不为空但不被 apply
- `batch_execute()` 顺序执行，前一条的 delta 影响后续

### Phase 1 完成标准

- [ ] `RulesEngine` 能注册并路由到任意 `CommandHandler` 子类
- [ ] `execute()` 返回的 `StateDelta` 可被 `StateContainer.apply()` 消费
- [ ] `DiceRoll` 生成可验证（种子化伪随机）
- [ ] 不依赖任何具体 Slice 或 Registry（全用 mock）

## Phase 2 — 编排骨架（依赖 Phase 0 + Phase 1）

> **目标**：搭建 TickCoordinator + SceneBus + SettlementHook 链的骨架。此阶段不实现具体 Hook——只建立框架，确保 Hook 能以正确优先级被调度。

> **前置拉取**：`SceneSlice` 从 Phase 3 提前到本阶段实现——SceneBus 是 SceneSlice 的运行时视图，没有 SceneSlice 就没有 SceneBus。`ContextAssembler` 在本阶段建立接口骨架（stub），Phase 3 完成后填充完整实现。

| 交付物 | 说明 | 权威规范 |
|--------|------|---------|
| **`SceneSlice`**（前置拉取） | entries: list[SceneEntry], state_changes。格级生命周期，P90 重置。**必须先于 SceneBus 实现** | 状态层 §3.9 (L673) |
| `SceneBus` | SceneSlice 的运行时视图。`add_entry` / `get_for_character` / `reset`。SceneEntry 含 visibility 三值 + audience | 编排层 §7.2 (L819) + §7.3 (L832) |
| `SettlementContext` | `change_log`, `state`, `world`, `scene_bus`, `execute_command(cmd)` — Hook 的唯一引擎入口 | 编排层 §9.2 (L955) |
| `SettlementHook` ABC | `priority`, `name`, `should_skip(change_log)`, `execute(context) → HookResult` | 编排层 §9.3 (L975) |
| `HookResult` | `commands: list[Command]`, `sse_events: list[SSEEvent]`, `skip_reason` | 编排层 §9.3 |
| `TickCoordinator` | `process(input)`, `accumulate(time_cost)`, `check_settlement()`, `_tick_settlement()`, `persist()` | 编排层 §2.2 (L111) |
| `SharedContext` | `world`, `state`, `rules_engine`, `scene_bus` — 传递给子管线 | 编排层 §2.2 |
| `PipelineOrchestrator` | A/B/C 三阶段骨架（具体实现后续填充） | 编排层 §2.3 (L211) |
| `PipelineHook` ABC | `extension_point`, `priority`, `execute(context)` | 编排层 §9.1 (L923) |
| `ActionDispatcher` | `StructuredAction → Command` 路由 | 编排层 §2.6 (L267) |
| **`ContextAssembler`**（接口骨架） | 从 StateContainer + WorldInstance 组装结构化上下文给 Agent。Phase 2 仅定义接口 + stub 返回；Phase 3 完成后填充真实组装逻辑 | 编排层 §4.1 (L577) |

**SceneBus 可见性规则**（三值 + audience）：

| visibility | audience | 谁能看到 |
|-----------|----------|---------|
| `public` | `None` | 所有人 |
| `system` | `None` | 仅引擎内部 |
| `private` | `["player", "npc:xxx"]` | 仅列表中的角色 |

**测试边界**：
- Mock Hook × 3（不同优先级）→ `_tick_settlement()` 按 P 值升序执行
- `should_skip()` 返回 True → 该 Hook 被跳过
- Hook 返回 commands → `SettlementContext.execute_command()` 经 RulesEngine → delta 被 apply
- `accumulate(0.5)` × 2 → 触发恰好 1 次 settlement
- `SceneBus.get_for_character("npc:tavern_keeper")` → 过滤 system + 不含该 NPC 的 private
- `SceneBus.reset()` → entries 清空

### Phase 2 完成标准

- [ ] SceneSlice 实现完整（restore/serialize/snapshot/reset + SceneEntry 可见性过滤）
- [ ] TickCoordinator 能按优先级驱动 Hook 链
- [ ] SceneBus 可见性过滤正确（public/system/private + audience）
- [ ] SettlementContext.execute_command() 正确调用 RulesEngine
- [ ] PipelineOrchestrator A/B/C 骨架可运行（B 阶段先 stub）

## Phase 3 — 具体 Slice 填充（依赖 Phase 0，与 Phase 2 可并行）

> **目标**：实现 9 个具体 StateSlice（SceneSlice 已在 Phase 2 前置拉取，此处不重复）。每个 Slice 是自包含数据容器，只依赖 `StateSlice` ABC——**Slice 之间无互相导入**。

> **并行策略**：9 个 Slice 完全独立，可分配给不同开发者同时实现。

> **ContextAssembler 填充**：Phase 3 完成后，Phase 2 建立的 ContextAssembler stub 可填充为完整实现（此时所有 Slice 均已就绪）。

| # | Slice | 核心 Schema | 权威规范 |
|---|-------|------------|---------|
| 1 | `TimeSlice` | day, slot, period, action_count, accumulated | 状态层 §3.1 (L134) |
| 2 | `PlayerSlice` | 角色属性 + inventory + equipment(13 槽位) + 法术 + 效果 + 职业资源 | 状态层 §3.2 (L176) |
| 3 | `RelationSlice` | npc_dispositions, relationship_stages, faction_standings, **npc_impressions**, shop_states | 状态层 §3.3 (L335) |
| 4 | `QuestSlice` | **milestone_states** (LOCKED→AVAILABLE→ACTIVE→COMPLETED/FAILED) + **dynamic_quests** + chapter_completion | 状态层 §3.4 (L410) |
| 5 | `FlagSlice` | flags: dict[str, Any] | 状态层 §3.5 (L464) |
| 6 | `AreaSlice` | AreaState（exploration, danger, containers, hostiles, discoveries, temporary_sub_areas） | 状态层 §3.6 (L489) |
| 7 | `EventSlice` | active_events(6 状态机), pending_events, rumors | 状态层 §3.7 (L586) |
| 8 | `PartySlice` | members, companion_approval, shared_experiences | 状态层 §3.8 (L637) |
| 9 | `NarrativePlanSlice` | current_chapter, current_target_milestone, strategy_notes, escalation_level, npc_directives, active_bulletins, quest_history | 叙事规划 §七 (L902) |

**QuestSlice 特别说明**（双区模型）：
- `milestone_states`：对应 ❶ `QuestRegistry` 的 `StoryMilestone`，世界初始化时根据 prerequisites 标记 LOCKED/AVAILABLE
- `dynamic_quests`：NarrativePlanner 运行时生成，不在初始化时存在
- 两个区域由不同写入者维护——前者主要由 `WorldStateHandler.advance_quest` 推进，后者由 `NarrativePlannerHook.create_quest` 写入

**NarrativePlanSlice 特别说明**：
- 权威定义在叙事规划子系统设计规范 §七（非状态层文档），因为它是 NarrativePlanner 的专属内部状态
- 不存储 `active_quests` 或 `completed_milestones` 副本——通过 `state.quests` 读取 QuestSlice
- NarrativePlannerHook (P35) 是其唯一写入者

**RelationSlice 特别说明**（npc_impressions vs MemoryGraph）：
- `npc_impressions`：简短印象摘要，AI Osiris `add_knowledge` 写入，供 UI + 关系判定
- `MemoryGraph`（Firestore 图谱）：完整语义记忆，对话图谱化 + NPC `remember` 写入，供 NPC Agent
- 两者面向不同消费者，**不需要同步**

**每个 Slice 的测试清单**：
- [ ] `restore(data)` → `serialize()` 往返一致
- [ ] `snapshot()` 返回只读副本（修改副本不影响原数据）
- [ ] 所有 Read API 在初始状态下返回合理默认值
- [ ] 所有 Write API 设置 `dirty = True`
- [ ] `clear_dirty()` 后 `persist()` 不输出该 Slice

### Phase 3 完成标准

- [ ] 9 个 Slice 全部实现 `StateSlice` ABC（加上 Phase 2 的 SceneSlice，共 10 个）
- [ ] 每个 Slice 可独立注册到 `StateContainer` 并通过便捷属性访问
- [ ] `StateContainer.snapshot()` 包含所有 10 个已注册 Slice 的快照
- [ ] 无 Slice 之间的交叉导入
- [ ] ContextAssembler 从 stub 升级为完整实现（组装所有 Slice + WorldInstance 的上下文）

**优先级排序逻辑**：
- P10→P20：延迟事件可能改变状态，效果 tick 需要最新状态
- P20→P30：AI Osiris 需要 tick 后的完整状态
- P30→P35：NarrativePlanner 需要 AI Osiris 的输出
- P30→P50：新 flag/任务可能触发事件
- P70→P80：GM 叙述需要知道新的时间
- P80→P90：GM 写入当前 SceneBus 后才重置

**推荐实施顺序**：
1. 先做 `SceneBusResetHook`（P90，最简单，验证 Hook 链运作）
2. 再做 `TimeAdvanceHook`（P70，验证时间推进）
3. `AIOsirisHook`（P30，核心智能，需要 LLM 集成）
4. 其余按需
